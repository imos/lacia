# 依頼の受付

オーナーさんからの依頼は、サーバーが受け付けて、窓口の会話へ1件ずつ渡します。依頼が届いたかどうかと、その返事は、Web の「やり取り」で確かめられます。

ローカル環境で動かすサーバーも、別の環境で動かすサーバーも、設定に `codex` か `claude` があるときに依頼を受け付けます。`state` の指定も要ります。Web はサーバーのアドレスで開き、手元の端末から `lacia ask` を使う場合は、同じ記録の書き置きか接続先の指定でサーバーへ届けます。 [接続先の見つけ方](records.md#手元のサーバーをコマンドが見つける)

## 依頼の入口

| 入口 | 送り方 |
| --- | --- |
| Web の画面 | ホームと、タスクのページにある、依頼の欄 |
| コマンド | `lacia ask [--task ID] [--keep-status] [--wait] <文章>` |
| Discord | 対応表にある人の発言（[Discord からの受付](discord.md)） |
| 相手のプロファイル | 伝言と引き継ぎ（[複数のプロファイル](profiles.md)） |
| サーバー自身 | 予約、サブエージェントの完了の知らせ、夜の書き直しの知らせ |

`lacia ask` を、Codex か Claude Code の会話が実行したときは、サーバーが、送った会話の名前（`local-codex 2` など）を依頼の `sender` に残します。受け取る会話には、「別の会話のレイシア（local-codex 2）からの依頼です」と伝え、オーナーさん本人の言葉ではないことと、外部への送信や共有の許可はこの依頼では受け取れないことを添えます。Web の「やり取り」にも、送った会話の名前を出します。人が端末から実行した依頼には、`sender` はありません。

`lacia ask` は、文章が空か `-` のときに、標準入力から読みます。`--wait` を付けると、返事が出るまで待って、返事を表示します。

## 受け付けたときに、サーバーがすること

依頼を受け付けると、サーバーは、会話へ渡す前に、次のことを済ませます。

- 依頼は1件ずつ、`state` の `requests/<年月>/<依頼のID>.json` に保存します。このファイルは Git に入りません。
- タスクの指定がある依頼では、そのタスクを進行中（`doing`）にします。もとの状態は覚えておき、質問に答えるだけで済んだときは戻すように、会話へ伝えます。
- タスクの指定がない依頼では、仮のタスクを進行中で作ります。題名は、固定の「受け付けた依頼を整理します」です。依頼の原文や送り元に含まれる秘密がGitへ入らないようにします。あとで会話が整えます。
- タスクの履歴に、依頼を受け付けたことを書きます。

サーバーが先に記録を残して状態を変えるので、オーナーさんは、会話の応答を待たずに、依頼が届いたことを画面で確かめられます。

同じ ID の依頼を同時に送っても、時間をおいて送り直しても、サーバーは最初に受け付けた依頼を返します。依頼と、それに対応するタスクは増えません。

### 途中で止まった依頼を続ける

タスクを指定したオーナーさんの依頼が `unknown` か `failed` になったときは、次のコマンドか、Webの「やり取り」にある「記録を確かめて続きを進める」ボタンで、明示的に再開できます。

```sh
lacia ask --resume <元の依頼のID> [--wait]
```

- 新しい依頼を同じタスクへ関連づけます。元の依頼の状態、原文、返事とエラーは残し、新しい依頼の `resume_of` から参照します。`/requests/<依頼のID>` と `GET /api/requests/<依頼のID>` で、50件より前の結果も参照できます。
- 原文は、Gitに入らない `state/requests/` の中でだけ再利用します。Gitへ残す受付の履歴には、原文を含めず、元と新しい依頼のIDだけを書きます。通常の受付でも、仮の題名、履歴の送り元、書き込みを止める理由には固定の表現を使います。
- 1件の依頼に対して作れる続きは1件です。複数の人が同時に再開した場合も、サーバーの再起動後に操作をやり直した場合も、同じ続きが返ります。サーバーは自動では送り直しません。続きも止まったときは、その続きの ID を指定して再開します。
- API から再開するときは、`POST /api/requests` の `resume` に元の ID を指定します。文章、タスク、領域、`status_policy` は一緒に指定できません。
- 再開できるのは、オーナーさんご本人から窓口に届いた、タスクに結び付く通常の依頼です。記録だけの依頼、システムやサブエージェントからのお知らせ、別の送り手や会話に結び付いた依頼、Discord などに返事を届ける依頼は対象外です。タスクが閉じているときや、同じタスクに処理中か順番待ちの依頼があるときも、新しい続きは作れません。
- 会話は、最初にタスクの本文、補足、履歴、成果物と元の結果を読み、済んだ操作と残りを確かめます。外部への送信、書き込み、申請、購入の結果が分からないときは繰り返さず、元のサービスで確かめ、確認できなければ本人へ尋ねます。再開を頼まれたことだけを、未確認の外部操作をもう1度行う許可にしません。

タスクを指定した通常の依頼でも、サーバーは作業の始めと区切りごとに記録を残すよう会話へ伝えます。会話は目的と完了の条件、許可の範囲、確かめたこと、次にすることとその理由を、本文、補足、履歴のうち適した場所に短く書きます。原文と秘密はGitへ写しません。途中の操作を記録するのは会話です。外部のサービスで操作が済んでいるかは、再開した会話が確かめます。

再開には、非公開の `state` の保存が必要です。記録のGitだけから原文を復元することはできません。運用では `state` を秘密として保管し、アクセスを制限してバックアップします。

### 状態を変えない依頼（`--keep-status`）

すでに終えた作業について、別の会話に記録だけを頼むときは、`--keep-status` を付けます。

```sh
lacia ask --task T1001 --keep-status "比較表とタスクの補足を読んで、判断が必要な点をまとめてください。今回は記録の更新だけをお願いします。"
```

- サーバーは、タスクを進行中に変えません。会話にも、状態を変えないように伝えます。
- タスクの指定が必要です。
- 記録だけの依頼に使います。実装や調査を始める依頼には付けません。
- 書く文章が決まっているときは、この依頼ではなく、`lacia task write` を使います。会話を通さずにサーバーが保存するので、待ち行列に並びません。[記録のリポジトリー](records.md#本文と補足をコマンドで保存する)にあります。この依頼が向いているのは、受け手に文章を考えてもらうときと、タスクのファイルのほかを直してもらうときです。
- 確認待ちのタスクの記録を直すだけで、進行中と確認待ちを行き来すると、Mac の通知が「新しく要対応になった」と知らせてしまいます。それを避けるための指定です。
- API では、`POST /api/requests` の `status_policy` に `"keep"` を指定します。

この指定は、受け手に実作業の許可を与えるものでも、状態の変更を禁じる仕組みでもありません。会話への頼み方を変えるだけです。

## 待ち行列

依頼には、2つの種類があります。

| 種類 | 中身 |
| --- | --- |
| 人からの依頼（`user`） | Web、コマンド、Discord から届いたもの |
| システムからのお知らせ（`system`） | 予約、サブエージェントの完了、夜の書き直し、相手のプロファイルからの知らせ |

順番は、次のように決まります。

- 人からの依頼を、システムからのお知らせより先に処理します。オーナーさんを、予約や完了の知らせの後ろで待たせないためです。
- 同じ種類の依頼が複数あれば、送り手について処理の記録がまだない依頼を優先します。送り手の ID がない依頼もここに含みます。ほかの依頼は、その送り手の前の依頼を処理し始めた時刻が古い順です。
- 送り手の順番が同じなら、先に届いた依頼から処理します。同じ人が続けて送った依頼も、届いた順です。

依頼の状態は、5つです。

| 状態 | 意味 |
| --- | --- |
| `queued` | 順番を待っています |
| `running` | 会話が対応しています |
| `done` | 返事があります |
| `failed` | 失敗しました |
| `unknown` | 結果が分かりません |

サーバーが再起動したときに処理の途中だった依頼は、`unknown` にします。最後まで処理されたかどうかが分からないので、自動では送り直しません。会話との接続が途中で切れたときも、同じです。順番を待っていた依頼は、再起動のあとに処理します。

待ち時間は、既存の記録の `started - created`、窓口が1件を扱った時間は `finished - started` で確かめます。子の作業が続いていても、窓口の応答を終えれば次の依頼を受けられます。

依頼と返事は、Web の「やり取り」のページ（`/requests`）で見られます。

`state` のディレクトリーに `drain` という名前のファイルを置くと、サーバーは、新しい依頼の処理と、予約と、夜の書き直しを始めません。サーバーを入れ替える前に、処理を静かに止めるための仕組みです。

## 窓口の会話と、別の会話

サーバーは、依頼の種類に応じて会話を使い分けます。

| 会話 | 受け持つもの | 続き方 |
| --- | --- | --- |
| 窓口 | 人からの依頼と、窓口で動かす予約 | 1本の会話を、何日も続けます |
| 別の会話 | `conversation: side` と書いた予約 | 毎回、新しい会話を始めます |

窓口を1本にしているのは、同じタスクを2つの会話が同時に書き換えないようにするためです。定期の処理を別の会話に分けているのは、窓口の依頼を待たせず、窓口の会話を大きくしないためです。

窓口は、判断と対話に集中します。

- どのタスクの話かを決めます。当てはまるタスクがなければ、作ります。
- タスクのIDが付いた依頼も、同じ窓口と待ち行列で受けます。サーバーがタスクごとの会話へ直接振り分ける形にはしません。
- 軽い質問と、タスクの間の優先順位や担当の調整は、その場で扱います。
- 切り出せる調査、実装、編集、検証は、着手前にサブエージェントへ渡します。これからすることを短く返事してターンを終え、次の依頼を受けられるようにします。完了を待つ操作や繰り返しの状態確認で、窓口のターンを続けません。
- 窓口はサブエージェントから完了の知らせを受けたら、結果をもとの依頼の送り先へ返します。

任されたサブエージェントは、担当するタスクの `task.md`、履歴（`lacia task note`）、成果物を、自分で書きます。状態も、`lacia task set` で自分で変えます。成果はその時点で画面に出るので、窓口がまとめ直す必要はありません。

会話への指示は、実行ファイルに入っています（`internal/codex/instructions.md`）。差し替え方は、[決まりと会話の起動](rules.md#サーバーが起動する会話)にあります。別の会話への指示は、設定では変えられません。

サーバーは、会話に、次の環境変数を渡します。

| 環境変数 | 中身 |
| --- | --- |
| `LACIA_API` | サーバーのアドレス。会話の `lacia` コマンドは、変更をここへ送ります |
| `LACIA_TASKS` | 記録のリポジトリーの場所 |
| `LACIA_USER` | オーナーさんの呼び名（設定の `user` を指定したとき） |
| `LACIA_BIN` | `lacia` の実行ファイルの場所 |
| `PATH` | 先頭に、[埋め込んであるコマンド](safety.md#実行ファイルに埋め込んだコマンド)の置き場所を足します |

### 窓口の会話を決めた時間に切り替える

使い続けて大きくなった窓口の会話を新しくしたいときは、サーバーの設定ファイルに、たとえば `window-rollover = 05:00-12:00` と書きます。コマンドラインでは `lacia serve --window-rollover 05:00-12:00` と指定できます。仕事用、家庭用、手元で動くサーバーに共通の設定です。省略するか空にすると、自動では切り替えません。

- 時刻は記録のタイムゾーンで読みます。終了が開始より早い `23:00-02:00` のような指定は、翌日の午前2時までを1つの時間帯として扱います。開始時刻から終了時刻の直前までの間に、窓口の種類ごとに1度切り替えます。同じ時間帯の切り替えは、サーバーを再起動しても繰り返しません。
- サーバーの起動時と稼働中に、現在の時刻を見て切り替えます。スリープ明けなどで時刻の確認より先に依頼が届いても、窓口がその依頼を処理する直前に、切り替えられるかを確かめます。
- 処理中の依頼と、時間帯の開始より前から待っていた依頼は、元の会話で返事の記録と送信まで行います。Codexの子が動いている間と、子の完了通知を待ち行列で扱っている間も、元の会話を続けます。時間帯の終わりまで空かなければ、次に時間帯が始まるまで待ちます。
- 切り替え中も依頼を受け付けます。届いた依頼は、切り替えが終わってから窓口で処理します。手元で直接開いた `lacia codex` や `lacia claude` の会話と、毎回新しい会話で動く `conversation: side` の予約は、それぞれの進め方で続きます。
- Codexとの再接続後に返事や子の状態を確かめられなければ、Codexの窓口の切り替えを保留します。接続とCodexの状態を確かめてから、必要なら処理が空いたときにサーバーを再起動し、同じ会話につなぎ直します。
- サーバーとCodexのapp-serverは動いたままです。次に開く窓口の会話には、その時点の決まりが届きます。以前の依頼と返事は「やり取り」で参照でき、新しい会話はタスクの記録を読んで仕事を引き継げます。

## Codex へ渡す（`codex`）

`codex = <コマンド>` と指定すると、依頼を Codex へ渡します。

- サーバーは、Codex の app-server を、自分とは切り離したプロセスとして起動します。サーバーを新しい版へ入れ替えても、Codex の会話と、動いているサブエージェントは止まりません。入れ替えのあと、サーバーは、同じソケットへつなぎ直して、同じ会話を続けます。
- 接続の情報は、`state` のディレクトリーの `codex/`（窓口）と `codex-side/`（別の会話）に置きます。
- `codex-sandbox` を指定すると、その値を Codex のサンドボックスの設定として渡します。承認は、求めない設定で動かします。
- 同時に動かせる会話は、窓口で扱う仕事では8つまで、別の会話で扱う仕事では2つまでです。どちらも、その会話とサブエージェントを合わせた数です。
- サブエージェントが終わると、サーバーが、窓口へのお知らせとして待ち行列に入れます。もとの依頼の送り先とタスクを引き継ぐので、Discord から届いた依頼の続きは、同じ場所へ返ります。

使うモデルと、考える深さは、設定の `codex-model` と `codex-effort` で決めます。書かなければ、Codex の設定のままです。

1件の依頼に、時間の上限はありません。窓口は、会話の応答が終わるまで、次の依頼へ進みません。応答が長引いた依頼だけを後回しにする仕組みは、まだありません。窓口が、実作業をサブエージェントへ任せて、早く応答を終えることで、次の依頼を受けています。

## Claude Code へ渡す（`claude`）

`claude = <コマンド>` を指定すると、Claude Code が依頼を受けられます。`codex` と両方を指定した場合は、宛先の種類に合うほうに依頼を渡します。種類の指定がないときは `default-kind` に従い、それもなければ Codex を使います。

- 依頼のたびに、`claude -p` を1回実行します。依頼の文章は、標準入力で渡します。
- 窓口の会話は、同じセッションを `--resume` で続けます。セッションの番号は、`state` のディレクトリーの `claude/session` に置きます。保存したセッションが見つからないときは、新しい会話を始めます。
- 別の会話で動かす予約は、毎回、新しい会話で実行します。
- 権限のモードは、既定では `acceptEdits` です。ファイルの編集と、`lacia` コマンドだけを、尋ねずに行います。ほかのコマンドを許すときは、記録のリポジトリーの `.claude/settings.json` に書くか、設定の `claude-permission` でモードを変えます。
- モデルは、設定の `claude-model` で指定できます。

Codex との違いは、依頼の合間に何も動いていないことです。

| | Codex | Claude Code |
| --- | --- | --- |
| 依頼の合間 | app-server が動き続けます | 何も動いていません |
| サブエージェント | 返事のあとも動き続けて、終わると知らせが届きます | その依頼の返事を書き終える前に、終わる必要があります |

サーバーは、サブエージェントを返事の前に終わらせることを、指示に足して伝えます。

Claude Code へ渡す形は、短い依頼で、タスクの作成と、前の依頼の内容を覚えていることを確かめました。長い作業と、予約の実行は、まだ確かめていません。

## 返事の行き先

- Web とコマンドからの依頼の返事は、「やり取り」のページと、`lacia ask --wait` に出ます。
- Discord からの依頼の返事は、同じチャンネルかスレッドへ投稿します。[Discord からの受付](discord.md#返事を届ける)にあります。
- システムからのお知らせへの返事が「報告はありません」で始まるときは、どこにも投稿しません。ホームの画面にも出しません。予約や完了の知らせで、伝えることがないときに、会話がこう答えます。
