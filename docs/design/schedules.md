# 定期タスクと予約

決まった時刻や間隔で繰り返す仕事は、記録のリポジトリーの `areas/<領域>/routines/S1001/routine.md` のような場所に書きます。形式1の記録では最上位の `routines/` と旧来の `schedules/` を読みます。サーバーが時刻を見て、依頼として会話へ渡します。ローカル環境でも、別の環境でサーバーを動かす場合でも、そのサーバーの会話で動かす予約は宛先を省けます。

予約が動くのは、依頼を受け付けるサーバー（設定に `codex` か `claude` があるもの）だけです。


## 書き方

1つの仕事に1つの固定IDを付けます。定義にはディレクトリー名と同じ `id` を書き、`title` は後から変えられます。古い予約を移す場合は `legacy_name` に旧名を書きます。実行IDと最後に動いた時刻を引き継ぎます。 [移行の手順](routine-migration.md)

Web の「整えた表示」で定義ファイルを開くと、冒頭の項目は「設定」を開いて読めます。「Markdown」に切り替えると、設定を含む元のファイルを表示します。移行前の予約の定義も同じように表示します。

```markdown
---
title: 朝の天気
daily: 06:30
conversation: side
---

## めざすこと

家を出る前に、きょう傘が要るかを判断できるようにします。

## ふだんの状況

オーナーさんは自宅にいます。

## すること

自宅の周辺のきょうの天気を調べてください。

## しないこと

予報を取得できなければ、推測で補いません。

## 伝え方

傘が要るかどうかを、3行までで伝えてください。
```

冒頭の項目は、次のとおりです。

| 項目 | 中身 |
| --- | --- |
| `title` | 画面に出す名前です |
| `every` | 繰り返す間隔を `90s`、`30m`、`2h` のように書きます。1分以上で、24時間を割り切れる長さを指定します。記録に設定した時間帯の0時を起点にします |
| `daily` | 毎日の時刻です。設定した時間帯の `HH:MM` で書きます。複数あるときは `09:00, 17:00` のようにコンマで区切ります |
| `conversation` | `main`（窓口の会話。既定）か、`side`（別の会話）です |
| `to` | 実行する会話の宛先です。省くと、このサーバーの既定の種類で動きます |
| `reply` | 結果を投稿する先です。`discord:<チャンネルのID>` のように書きます |
| `task` | 結び付くタスクのIDです。タスクが閉じたら、予約を実行しません |
| `enabled` | `false` にすると、止めます |

- `every` と `daily` は、どちらか1つだけを書きます。
- 1回だけ行う仕事は、予約にしません。タスクに日時を決めて、その日時にレイシアが着手するようにします（[記録の形](records.md#条件がそろったら確認待ちへ出すか着手する)）。日時、することの中身、許可の範囲が、タスクの1か所にまとまるためです。`at` を書いた定義は、誤りとして知らせます。
- 曜日は `weekdays: Mon, Wed` のように指定できます。省くと毎日が対象です。きょうの曜日は、サーバーが依頼に添えます。
- 本文が、そのまま依頼の文章になります。

本文は、例にある5つの見出しの順に書きます。最初の2つに仕事の目的とふだんの状況を書いておくと、旅先などで前提が変わった日も、会話がその日の事情に合わせられます。

`lacia schedules` は予約の定義を1行ずつ表示し、書き方に問題があれば理由を知らせます。Web の「定期タスク」（`/routines`）では、予約の定義と、サーバーが最後に扱った回の予定日時を見られます。前の回が続いていてその回を見送った場合にも、予定日時は更新されます。予約の名前を開くと、[実行の記録](#実行の記録)で、成功した回に記録された終了日時も確かめられます。

## 今回の結果を確認する

`output: matters` の定期タスクは、`lacia run report S1001 <実行ID> <JSONファイル>` で結果を保存できます。結果には `summary`、`reference`、`matters`、`unverified` を書けます。用件には `key` と `revision` を付け、同じ更新に同じ値を使います。何もなかった回は `nothing: true` を指定します。 `output: task` と `output: none` は、通常タスクを作る仕事と内部で済む仕事に使い、用件の受付は作りません。タスクを持たない記録（記録の設定が `"tasks": false`）では、`output: task` は使えません。結果をチャットへの返事で伝えて終える仕事には、`output: none` と `reply` を使います。`lacia doctor` は、タスクを持たない記録の `output: task` を知らせます。確認できた範囲は、後述の同じ結果保存で記録できます。

サーバーは同じ回の結果を保存し、実行の行を記録してから、未確認分を定期タスクごとにまとめてホームの「要対応」に出します。ホームからは最新の未確認受付を直接開けます。定期タスクのページでは、受付番号、届いた時刻、概要、確認状況を並べ、未確認の受付を先に出します。実行の履歴からも、その回に受付があれば直接開けます。

受付の本文、用件、確認できなかった範囲は、`/routines/S1001/receipts/1` のような受付ごとのページに出します。確認済みの受付も同じリンクで開けます。受付のページの「この受付を確認済みにする」は、表示した1件に効きます。定期タスクのページの「未確認分をまとめて確認する」は、その画面を開いたときまでの受付に効きます。別の回に新しい結果があれば、同じカードが表示されます。 `enabled: false` はこれからの実行を止めます。開始した回の結果は引き続き受け付けます。

`reply` に既存の返信先がある回は、その回に保存した返信先だけへ届けます。Macの定期タスク通知へ重ねて出しません。返信の送達が `sent` と記録されたあと、同じ実行の結果を通知済みとして履歴へ残します。送達の失敗や結果不明は、通知済みに読み替えず、自動で送り直しません。通知済みでも未確認分は残り、読む人の「完了」だけが確認済みの境界を進めます。

実行と確認は `areas/<領域>/routines/<ID>/runs/<年月>/` の `runs.jsonl` と `reviews.jsonl` に残ります。通知用の受け渡しも1回につき1件です。受付ページに対応したサーバーとMacの通知アプリを使うと、新しい通知は受付のページを直接開きます。アプリが同じ受付番号をもう一度受け取っても同じ通知IDを使い、通知ファイルに保存できた時点でサーバーに知らせます。

## どの会話で動かすか

| `conversation` | 動く会話 | 向いている仕事 |
| --- | --- | --- |
| `main` | 窓口の会話 | オーナーさんへ伝えることが目的のもの。窓口が、これまでのやり取りを踏まえて伝えます |
| `side` | 毎回新しく始める、別の会話 | 定期の確認や取得。窓口の依頼を待たせず、窓口の会話を大きくしません |

別の会話は、窓口のやり取りを知りません。必要な前提は、予約の本文か、[いまの状況](#いまの状況を添える)で伝えます。

伝えることがないときは、会話が「報告はありません。」と答えます。この返事は、どこにも投稿されません。

## Discordで送り先を選ぶ

予約の `reply` に、投稿を届けるチャンネルのIDを指定できます。たとえば、`reply: discord:<channel-id>` の `<channel-id>` を、利用するチャンネルの数字のIDに置き換えます。`reply` を省いた予約は、Discordへ投稿しません。

送り先は、Botに設定したDiscordサーバー内のテキスト欄を持つチャンネルです。通常のテキスト、アナウンス、ボイスとステージのテキスト欄を指定できます。 `DISCORD_MENTION_ALL_CHANNELS=true` の導入先では、受付チャンネル以外も指定できます。Discord側で、Botが送り先を閲覧・投稿できるようにしてください。 [ボイスのテキスト欄](https://support.discord.com/hc/en-us/articles/4412085582359-Text-Channels-Text-Chat-In-Voice-Channels) · [ステージのテキスト欄](https://support.discord.com/hc/en-us/articles/1500005513722-Stage-Channels-FAQ)

サーバーは投稿する前に、IDで指定したチャンネルが同じDiscordサーバーにあり、投稿できる種類かを確かめます。DM、別のDiscordサーバー、親フォーラム、スレッドは定期投稿の送り先に使えません。Discordは投稿時にアーカイブ済みのスレッドを再開する場合があるため、定期投稿ではチャンネルのテキスト欄へ届けます。[Discordのスレッド仕様](https://docs.discord.com/developers/topics/threads#active--archived-threads)を、2026-11-25に確認しました。

チャンネルが見つからないときや、Discordが投稿を拒否したときは、「やり取り」に配送の失敗が残ります。配送の失敗を記録したあとは、別のチャンネルへの振り替えや、自動での再送はありません。送り先の変更は、変更後に受け付ける実行回から適用します。

## 予約を実行する流れ

サーバーは、20秒ごとに時刻を確かめます。回が来ると、システムからのお知らせとして、待ち行列に入れます。

- 同じ予約の前の回がまだ終わっていないときは、新しく時刻を迎えた回を見送ります。間隔より長くかかる仕事が、積み重ならないようにするためです。
- 名前が `calendar` の予約は、サーバーが Google Calendar を直接読めているあいだは、実行しません。同じスナップショットを、会話が上書きしないようにするためです。

### サーバーが動いていなかったあいだの回

予約の時刻にサーバーが動いていなかったとき（サーバーのプロセスが止まっていた、動かす端末がスリープしていた）は、動きはじめたときに実行します。実行できなかった回が何回あっても、繰り返さずに、1回にまとめます。

- サーバーは、最後に予約を見た時刻を、およそ1分ごとに記録します（`state` のディレクトリーの `schedules.json`）。その時刻よりあとに来ていた回が、動いていなかったあいだの回です。
- `every` の予約は、いつも、いまの回を1回だけ実行します。
- `daily` の予約は、動いていなかったあいだに来ていた回を、どれだけ遅れていても、1回実行します。

遅れた回には、サーバーが、依頼の文章に「遅れて実行しています」という節を添えます。

- 添えるのは、`daily` の回が30分以上遅れたときと、いくつかの回をまとめたときです。
- `daily` の回が30分以上遅れたときは、予定の時刻といまの時刻を書きます。いくつかの回をまとめたときは、その回数を書きます。
- 「いまから行っても役に立たない回は見送り、そのことだけを短く書いてください。」と添えます。

朝の知らせを夕方に実行するようなときに、会話が、中身をいまの時刻に合わせるか、何もしないかを、判断できるようにするためです。

### 過ぎた時刻を書いたとき

サーバーが動いているあいだに過ぎた回は、6時間を超えていれば、実行しません。過ぎた時刻を書いた予約が、書いたとたんに動きだすことを防ぐためです。

6時間以内なら、実行します。たとえば、14時に `daily: 09:00` の予約を新しく書くと、その日の9時の回が、すぐに実行されます。

## 実行の記録

予約の結果は、サーバーが月ごとに記録します。この記録を読めば、会話が「報告はありません」と答えた回と、失敗した回や実行を見送った回を見分けられます。

### 置き場所

```
areas/<領域>/routines/<ID>/runs/<YYYY-MM>/runs.jsonl
```

予約ごとに、予定日時の属する月のファイルへ1行ずつ書き足します。年月は記録の設定にある時間帯で決めます。同じ結果が続く回や見送った回をまとめる条件は、[いつ書くか](#いつ書くか)にあります。書いた行はそのまま残り、ほかの記録と一緒に Git へ保存されます。

### 1行の中身

| 項目 | 中身 |
| --- | --- |
| `at` | その回の予定日時です |
| `started` | 依頼の処理を始めた時刻です。記録がないときは省きます |
| `finished` | 処理が終わった時刻です。終了時刻が分からないときは結果を記録した時刻、見送った回にはその扱いを記録した時刻が入ります |
| `outcome` | 結果です。下の4つのどれかです |
| `summary` | 返事やエラーで最初に内容がある行、または見送りの理由です。返事やエラーの行が120字を超えると、先頭120字に「…」を添えます。`nothing` の回は省きます |
| `late_minutes` | 本来の時刻から、待ち行列に入るまでの遅れです。30分以上のときだけ書きます |
| `count` | 実行されなかった回の行が、何回分かです。`at` は、その最初の回です |
| `request` | 依頼の ID です。返事の全文は、依頼の記録にあります |

| `outcome` | 意味 |
| --- | --- |
| `done` | 済みました。伝えることがありました |
| `nothing` | 何もありませんでした。返事が「報告はありません」で始まる回です |
| `failed` | 失敗しました。会話が処理できなかった回と、途中で接続が切れた回です |
| `missed` | 実行されませんでした |

### いつ書くか

- サーバーは、依頼を待ち行列に入れたときに、処理中の回を `state` の `schedule-runs.json` に保存します。20秒ごとに依頼の状態を確かめ、終わった回の結果を月別の記録に書きます。
- サーバーを再起動したあとも、保存してあった回の結果を確かめます。待ち行列に入れてから24時間たっても依頼の記録が見つからない回は、失敗として記録します。
- 前の回が終わらず次の回を見送ったときも、[サーバーの停止中に時刻が過ぎた回](#サーバーが動いていなかったあいだの回)をまとめて見送ったときも、`missed` として記録します。`count` は、その行が何回分の見送りに当たるかを表します。
- `every` の予約で、同じ日のうちに同じ `outcome` が続いたときは、最初の回だけを書きます。返事の文面が違っていても、結果の種類が同じなら行を増やしません。日付や結果の種類が変わったときと、実行を見送ったときは記録します。
- 記録を書けなかったときも、予約そのものは実行します。

### 見え方

予約の詳細ページ（`/routines/<名前>`）では、実行中の回と月ごとの履歴を見られます。履歴は予定日時の新しい順です。「いまの様子」の集計には、記録がある月のうち、新しいものから3か月分までを使います。

- 「記録にある最後の成功時刻」に表示するのは、成功した回（`done` か `nothing`）のうち、予定日時が最も新しい回の `finished` です。
- 失敗の件数は、新しい記録から成功の記録に行き当たるまで、`failed` の行を数えたものです。間隔予約では同じ日の失敗が1行にまとまることがあるので、実際に失敗した回数より少ない場合があります。
- 見送った回数は、最新の記録から続く `missed` が何回分あるかを数えます。1行に複数の回をまとめていれば、その `count` を足します。

### 不調を知らせる

予約が黙って止まっても、何もなかった日と見分けがつきません。そこで、次のものを「不調」として、ホームの「予約の不調」に出します。直ると、消えます。

- 定義に問題があって、動いていない予約
- 「いまの様子」で失敗の件数が2件以上の予約
- 実行の記録で、2回以上続けて見送られた予約。登録した端末の接続を前の回が待っているために、次の回を見送った場合も数えます
- 認証を待っている端末。本人の操作が要るので、1回目から出します

失敗と見送りの両方が条件に当たるときは、失敗のほうを表示します。停止中の予約（`enabled: false`）がこの一覧に出るのは、定義に問題があるときだけです。

`GET /api/schedule-troubles` が、同じ一覧を返します。`lacia agent` は、この一覧を読んで、macOS の通知アプリに新しく出た不調を1度だけ知らせます。続いているあいだは、重ねて通知しません。消えてからもう1度出たものは、あらためて通知します。

## いまの状況を添える

予約の文章は、ふだんの状況を前提に書かれています。けれども、別の会話は毎回新しく始まるので、オーナーさんが旅行に出ていることも、きょうが休みであることも、知りません。そこで、サーバーが、予約の依頼の最後に、毎回「いまの状況」を添えます。

添えるのは、次の3つです。

1. きょうの日付と曜日
2. `memory/now.md` の内容
3. きょうの状況を確かめ、前提が合わなければ目的に合わせて内容を変えるよう求める依頼

`memory/now.md` は、ふだんの前提が成り立たない期間を書いておく、短い文書です。旅行、出張、帰省、休校、体調、来客などを、1行ずつ書きます。

- 書くのは、窓口の会話です。やり取りや予定から、ふだんと違う期間が分かったら書き、期間が過ぎた行は消します。
- 文書がないとき、空のとき、読み出せなかったときは、「ふだんと違う状況について、ここに添えられる記録はありません。」と添えます。日付と、状況を確かめるよう求める依頼は、いつも添えます。
- 3000字を超えた分は、添えません。
- 場所は、設定の `now` で変えられます。

`lacia codex` と `lacia claude` で起動する会話にも、同じ内容を渡します。

### 目的に合わせる、という考え方

決まりや手順は、ふだんの状況を前提に書いてあります。大事なのは、書かれた手順をなぞることではなく、その仕事が相手の役に立つことです。たとえば、オーナーさんが旅行に出ている朝は、自宅ではなく、旅先の天気を伝えます。

- 変えたときは、何を変えたのかと理由を、1行で添えます。読んだ人が、読み違いに気づいて直せるようにするためです。
- 迷うときは、合わせた内容を主にして、ふだんの内容を短く添えます。先に尋ねて待つことはしません。朝の知らせでは、返事を待てないためです。
- 会話が自分の判断で変えてよいのは、対象、中身、重点、添える情報です。読むだけで済み、あとから直せるものに限ります。
- 許可の範囲、外部への書き込みや送信、送り先、読んでよい情報の範囲は、変えません。定例の仕事をやめることと、新しく作ることも、会話は自分では決めません。

この考え方は、実行ファイルに入っている決まり（`lacia rules` の「目的に合わせる」）にあります。案内を変えたときは、相手の反応から気づいたことを[わたしのこと](self.md)のために書き留めます。次にどこまで案内を合わせるかを考えるときに読み返せます。


## 記録の時間帯

`.lacia/config.json` の `timezone` に、IANAの名前を指定します。既定は `Asia/Tokyo` です。日付と時刻だけの予約はこの時間帯で読み、実行の月、遅れの説明、依頼へ添えるきょうの日付にも同じ設定を使います。`Local` や知らない名前は、設定を読むときに断ります。

`daily` の複数時刻は、並べ直して読みます。同じ時刻の重複は、定義の誤りとして知らせます。眠っていたあいだの回は、従来どおり最後の1回へまとめ、飛ばした回を数えます。夏時間で存在しない時刻は飛ばし、時計が戻って同じ時刻が2度現れる日も、その時刻の回は1度だけ実行します。

「いまの状況」に、`- 2026-11-23〜2026-11-24：旅行しています。` のような期間行があるときは、設定した時間帯のきょうの日付で期限を判定します。終わりの日までは添え、翌日からは添えません。未来の行や、日付として読めない行は残します。元のファイルは書き換えません。

## 実行先を選ぶ

ローカル環境で使うときは、その環境の `lacia serve` が予約を管理し、会話を起動します。別の環境でサーバーを動かす場合も、そのサーバーで実行する予約は同じ書き方です。どちらも予約の `to` を省くと、サーバーの既定の種類で動きます。

別の場所や種類で動かすときは、会話の名前と同じ `<場所>-<種類>` で書きます。種類は `codex` か `claude` です。場所だけを書くと、その場所の既定の種類で動きます。設定にない場所を指定すると、ホームの「予約の不調」に理由が出ます。

```markdown
---
title: 手元で必要な確認
daily: "06:00"
to: local-codex
conversation: side
---

手元で読める資料を確認してください。
```

### サーバーに場所を登録する

サーバー自身の場所は、起動時のプロファイル名です。プロファイルを選ばないときは `local` です。両方の種類を起動できるサーバーでは、`default-kind` で既定を選べます。省くと、Codex があれば Codex を使います。

サーバーと別の端末で会話を動かすときは、その端末の場所を、サーバーの設定ファイルの `places` に書きます。下の例の `work` はサーバー自身の場所、`local` はこの例で登録した端末の場所です。プロファイルを指定せずに起動したサーバーは、自分自身を `local` と呼びます。

```ini
[work]
places = {"local":{"device":"desk-device","default":"codex","secret_file":"/srv/lacia/secrets/desk-device"}}
```

`device` は端末の登録名、`default` は種類を省いたときに使う値です。`secret_file` は端末と共有する秘密のファイルです。ファイルの権限は0600にし、Gitの外に置きます。端末ごとに、暗号学的な乱数で作った別の秘密を使います。記録側の `.lacia/serve.conf` に `places` は書けません。

### 別の端末で予約を受け取る

登録した端末では、`lacia agent` が申し送りと予約を受け取ります。macOS の通知アプリから動かす場合は、インストール時に端末の登録名と、記録の読み取り専用のコピーを指定します。端末とサーバーには、登録時に同じ秘密を置きます。接続にはHTTPSか、信頼できる転送のループバックアドレスを使います。[Mac の通知](notifications.md#予約も受け取るとき)

会話の種類は宛先から、窓口か別の会話かは `conversation` から決まります。ログインを選ぶ必要があれば、実行する端末の `logins.json` に書きます。その端末は結果を予約のサーバーへ返し、通知先はサーバーが予約から読みます。[ログインの一覧](logins.md#別の端末で受け取る予約のログイン)

端末がつながらないときは接続待ちです。認証切れを端末で確かめられたときは認証待ちとして記録します。結果と状態は、APIへ接続できるようになったあとにも届けられます。

### 開始と結果を重ねない

サーバーは予約の名前と予定日時から `sched-<予約名>-YYYY-MM-DD-HHMM` という ID を作り、受け付けた回を1回ずつ `state/schedule-dispatch.json` に保存します。ここには、サーバーで動かす回も、端末で動かす回も入ります。実行先、端末、依頼文、受け付けた時刻、開始と終了の時刻、状態、結果を記録します。

- 実行先の設定をあとで変えても、受け付けた回には、保存してある端末、本文、送り先を使います。サーバーを再起動したときも、その回の続きに同じ設定を使います。
- 登録した端末がスリープしていたり、つながっていなかったりすると、その端末宛ての予約は接続を待ちます。別の環境のサーバーで実行する予約は、サーバーが稼働していれば進みます。ローカル環境がスリープしてサーバーが動けなかった場合は、サーバーの復帰後に遅れた実行を扱います。 [遅れた実行](#サーバーが動いていなかったあいだの回)
- 開始前の回を受け取った端末は、回ごとの取得IDを端末に保存してから、開始を申し出ます。管理側が開始を保存して返事をしたあと、端末も開始を保存して、コマンドを起動します。
- 開始の返事が失われても、同じ取得IDでの申し出だけを受け直します。同じ端末で別のプロセスが別の取得IDを送っても、同じ回を開始できません。端末の同じ状態ディレクトリーには、プロセス間のロックも掛けます。
- コマンドが終わると、端末は結果を保存してから送ります。送信に失敗したり、管理側が受け取ったという返事が届かなかったりしたときは、端末が保存した結果を送り直します。管理側は、先に受け取った結果を変えず、依頼をもう1度会話へ渡しません。
- 端末が開始後に止まり、結果を保存できなかった回は、結果不明として戻します。同じ回を自動で再実行しません。端末の状態自体を失った場合も、管理側で開始済みの回を、動き始めたプロセスが取り直すことはありません。結果の確認は、本人が行います。
- 前の回が終わっていないときは、次の回を実行せず、その回を飛ばした記録を残します。結果不明になった前の回を繰り返さず、次の日などの新しい回は進められます。

端末から届いた結果は、その回の ID を付けて共通の依頼履歴にも保存します。届け先への送信を始める前にサーバーが止まった場合は、再起動後に保存済みの結果を送れます。送信を試みたあとで届いたか分からなくなった場合は、`ClaimDelivery` の記録に従い、自動では送り直しません。

### 状態と結果を読む

`/routines/<予約名>` では、サーバーと端末の実行回を同じ表で見られます。`GET /api/schedule-runs` は中央の全実行回と端末の状態変化を返し、`?name=<予約名>` で実行回を絞れます。`executions` には実行回のID、解決した宛先（`to`）、会話の種類（`kind`）、端末（`device`）、状態、時刻と結果が入ります。以前の回の宛先は、保存したときの `target` で読みます。`device_events` は、接続待ちや認証待ちを観測した時刻と、観測した端末を残します。端末の秘密や、回の取得IDは、この一覧へ出しません。

端末用のAPIは、`POST /api/schedule-worker/<端末ID>/poll`、`/<回ID>/start`、`/<回ID>/finish` です。端末ごとの `Authorization: Bearer ...` が必要です。開始と終了には、端末で保存した回ごとの `claim` を送ります。

定期タスクの `runs/` にある月別の記録は、画面で履歴を読んだり、日次確認をまとめたりするときに使います。間隔予約で同じ結果が続いて省略された回も、受け付けた回の一覧では個別に確かめられます。実行した回の結果には、その回の ID（`request`）と宛先、端末で実行したときはその端末も残します。

日次の確認を集めるときは、実際に確認した日時と工程の範囲、根拠、実行回のIDを照合します。日本時間06:00を日付の境界にする場合も、予約の時刻や実行回のIDはずらしません。会話が正常に終わったことと、各項目の確認に成功したことは、別に扱います。

### 実行プロファイルを選ぶ

`profile: cluster-read` のように、実行端末の `logins.json` に登録した実行プロファイルを名前で選べます。未指定の起動方法は変わりません。登録の形、失敗の扱い、実行履歴は[定期タスクの実行プロファイル](logins.md#定期タスクの実行プロファイル)にあります。

### 本人への用件だけを受付にする

サーバーのプロファイルに `routine-explicit-matters = true` を設定すると、その後から受け付ける固定IDの定期タスクで、本人の対応が必要な用件だけを「要対応」に出します。設定の既定値は無効です。設定の値は実行回ごとに保存するため、進行中の回や以前の受付を判定し直すことはありません。

`output: matters`（省略時も同じ）では、`matters` の各項目に `key`、`revision`、`summary` を書きます。`summary` には、本人にしてほしいことを書きます。要約だけの回は「済みました」として、要約も用件もない正常な回は「何もありませんでした」として、実行履歴に残します。これまでの `nothing: true` も受け付けます。未確認の範囲だけがある回は、不調の集計に渡します。部分失敗の回でも、確定した用件は受付に残ります。

固定の `check_scopes` がなく、全範囲を確認した場合は `{"check_status":"complete","summary":"確認しました。新しい用件は0件です。"}` と書けます。サーバーが定期タスク全体の確認範囲を補います。未確認の範囲には理由を添えます。`check_result: true` を指定した定期では、引き続き確認結果の保存が必須です。

用件を個別のタスクに書いて読み戻した場合は、`handoffs` に `key`、`revision`、`summary`、`task_id` を書きます。サーバーは保存時に指定のタスクが存在し、開いていることを確認して、実行履歴にリンクを載せます。同じキーと更新を `matters` にも書いた場合は、明示の用件を受付に回します。タスクが見つからないか閉じられていた場合は、未確認だったことを履歴に記録し、`output: matters` では確認済みの用件を受付へ回します。`output: task` では受付を作らず、実行履歴と既存の不調の通知で分かるようにします。タスクの本文への記録は、報告を作る側が確かめます。

`output: task` と `output: none` の回は受付を作りません。設定済みの `reply` とDiscordへの送達は、会話の最終返答を使う従来の方法で動きます。確認待ちの既存タスクに追記しただけでは、通常タスクの状態が変わったときの通知は出ません。その場合に別途知らせる運用があれば、`matters` から `handoffs` に切り替える前に送達方法を確認します。

### 確認できた範囲と実行の成否

会話が正常に終わったことと、予定した範囲を確認できたことを分けます。`check_result: true` を定義に指定すると、出力が `matters`、`task`、`none` のどれでも、`lacia run report <定期タスクIDまたは旧予約名> <実行ID> <JSONファイル>` で確認結果を保存します。確認範囲が固定の予約は、`check_scopes: cluster:site-a/auth, cluster:site-b/auth, cluster:site-c/auth` のように、重複しない範囲を指定します。受付時にこの一覧を実行回へ保存し、結果に不足や余分な範囲があれば受け付けません。予約の依頼には、その回のID、固定した確認範囲と結果の書き方を添えます。この指定がない既存の予約と、既存のJSONの結果は、従来どおり受け付けます。

```json
{
  "version": 1,
  "check_status": "partial",
  "summary": "読めた新着が1件あります。",
  "checks": [
    {"scope": "service/public", "status": "verified"},
    {"scope": "service/private", "status": "unverified", "reason": "permission_denied"}
  ],
  "matters": [{"key": "service/item-1", "revision": "v1", "summary": "新しい結果です。"}]
}
```

`checks` には、手順で予定した各範囲を入れます。全範囲を確認した回は `check_status: complete`、一部を読めない回は `partial`、全範囲を読めない回は `unavailable` です。新着がなければ `nothing: true` にします。確認できなかった回にもこの値は使えますが、正常な0件になるのは `complete` の回だけです。未確認範囲は既存の `unverified` にも反映し、部分成功で読めた新着は、通常の結果の受付と「要対応」へ渡します。

`check_result: true` の回で確認結果が届かなければ、確認できたことにせず、失敗として残します。壊れたJSONや矛盾する確認結果は受け付けません。同じ結果の再送は受け付け、同じ実行IDへの異なる結果は拒みます。実行コマンド自体が失敗した回は、確認結果があっても失敗を保ちます。過去の履歴を書き換えて判定し直すことはしません。

明示した確認結果と失敗は、短い間隔の予約でも毎回記録します。正常な結果だけを省いていた過去の履歴も読めますが、今回からの失敗を省くと、連続回数を数えられなくなるためです。未確認の範囲ごとに、予定時刻の順で、同じ実行IDを重ねずに数えます。全範囲の確認不能は2回続いたとき、一部を確認できない範囲は3回続いたときに不調へ出します。途中の部分成功でほかの範囲を読めても、その範囲の未確認は解消しません。その範囲を確認できた回が来ると解消し、過去の成功が遅れて届いても、その後の失敗は解消しません。

`cause_key` は、同じ原因だと確かめられたときだけ `checks` に添えます。同じ端末、範囲、理由、原因の不調を、各定期タスクで回数を判定したあとにまとめます。端末やエラー文が同じという理由だけでは、同じ原因として扱いません。同じ不調が続くあいだの通知、復旧後の再発の通知は、既存の不調の通知経路を使います。結果の「完了」は確認済みの境界だけを進め、不調の状態を変えません。
