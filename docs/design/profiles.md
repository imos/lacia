# 複数のプロファイル

1つの設定ファイルに、並んで動く複数のサーバーを書けます。それぞれを「プロファイル」と呼びます。この文書では、2つのプロファイルを組にして、伝言と引き継ぎをやり取りする仕組みを説明します。

プロファイルを組にするのは、記録を分けたまま伝言や引き継ぎをする場合です。ローカル環境でも、別の環境でも、記録が1つなら `lacia serve` の起動引数だけで使い始められます。

## 何のために分けるのか

プロファイルを分けるのは、記録と、話す相手を、分けておきたいときです。たとえば、仕事用と家庭用の2つのプロファイルを持つ使い方があります。仕事用は Web の画面を入口にして、タスクを持ちます。家庭用は Discord を入口にして、オーナーさんのまわりの方と話します。タスクを持たない側の記録は、記録の設定に `"tasks": false` を書きます（[記録の設定](records.md#記録の設定laciaconfigjson)）。

- プロファイルごとに、記録のリポジトリー、窓口の会話、自分についての記録を、別々に持ちます。
- サーバー間の連携には、伝言や引き継ぎの API を使います。自分についての記録を共有する場合も、相手のリポジトリーを直接開かず、[共有する「わたし自身」の節](self.md#複数のプロファイルで共有する)だけを API でやり取りします。
- 片方のプロファイルで話した内容が、もう片方へ、そのまま流れることはありません。

## 設定

設定ファイルに、プロファイルごとの節を書きます。次は、1台で2つのプロファイルを動かす例です。パスは、その機械で使う絶対パスに置き換えます。2つの機械で動かすときは、ポートと `url` を、それぞれの環境から届く値に合わせます。 [設定の一覧](settings.md#設定の書き方)

```
codex = codex

[work]
label = 仕事
url = http://127.0.0.1:10148
addr = 127.0.0.1:10148
root = /path/to/records-work
state = /path/to/state/example-work
peer = home

[home]
label = 家庭
url = http://127.0.0.1:10149
addr = 127.0.0.1:10149
root = /path/to/records-home
state = /path/to/state/example-home
pages = false
peer = work
inbox = true
```

この例なら、`lacia serve --config lacia.conf --profile work` と `lacia serve --config lacia.conf --profile home` をそれぞれ起動します。チャットの側で Discord を使うときは、そのプロファイルに Bot の設定を足します。 [Discord からの受付](discord.md#設定)

プロファイルの名前（上の `work`、`home`）に、コードは意味を持たせていません。何をするかは、次の設定の組み合わせで決まります。

| 設定 | 意味 |
| --- | --- |
| `peer` | 相手にするプロファイルの名前です。相手の節に `url` がないと、起動しません |
| `url` | このプロファイルのサーバーへ、相手から届くアドレスです。相手の側が読みます |
| `label` | このプロファイルの呼び名です。既定は「通常モード」です。相手のプロファイルの呼び名は、その節の `label` から読みます。なければ「もう一方のモード」です |
| `inbox` | `true` なら、相手からの伝言を受けて、返事を返す側になります。`false` なら、伝言を送る側です |
| `pages` | `false` にすると、通常の画面と API は、手元か `site` に指定したアドレスから使います |

2つのプロファイルを組にするときは、どちらから伝言を送るかを決めます。

| | 送る側（`inbox` なし） | 受ける側（`inbox = true`） |
| --- | --- | --- |
| 伝言 | 相手へ送って、返事を受け取ります | 受けて、窓口の会話が返事を書きます |
| 引き継ぎ | 相手からタスクを引き継がれます | 相手へタスクを引き継ぎます |
| 共有する「わたし自身」の節 | 2つの共有節をまとめて、相手へ渡します | 共有節を読まれ、まとめた節の本文を受け取ります |

伝言と引き継ぎが働くのは、依頼を受け付けるサーバー（設定に `codex` か `claude` があるもの）だけです。

呼び名は、画面、「わたしのこと」の文書、伝言の文面、会話への指示に出ます。サーバーが起動する会話への指示の中の `{{相手}}` は、相手の呼び名に置き換わります。埋め込みの決まりの文書（`lacia rules`）は、サーバーへ尋ねずに読めるよう、相手を「相手のプロファイル」と書いています。伝言と引き継ぎを、会話がどう扱うかは、決まりの `peers` にあります。

## 伝言（`lacia peer tell`）

送る側のレイシアとオーナーさんは、受ける側のレイシアへ、伝言を送れます。

```
lacia peer tell [--task ID] [--discord] [--wait] "（伝える内容）"
lacia peer status <伝言のID>
```

- `--task` には、話の対象のタスクを書きます。タスクの履歴に、伝えたことと、返事が届いたことが残ります。
- `--wait` を付けると、返事を待って表示します。付けないときは、あとで `lacia peer status` で確かめます。
- `--discord` を付けると、受ける側の返事が、受ける側の Discord にも投稿されます。受ける側が Discord を使っていないときは、投稿されません。

### 流れ

1. コマンドは、自分のサーバーへ頼みます。相手のサーバーを、直接は呼びません。
2. 送る側のサーバーが、相手の `POST /api/inbox` へ直接送ります。相手のサーバーが止まっていれば、送った人にその場で伝えます。自動では送り直しません。
3. 受ける側のサーバーは、伝言を、窓口の会話への依頼にします。タスクは作りません。
4. 窓口が返事を書き終えると、受ける側のサーバーが、送る側の `POST /api/replies` へ返事を届けます。送り返した返事が届かなくても、送る側のサーバーは、ページを表示するときに相手へ問い合わせて伝言の状態を確かめます。

送る側は、送った伝言と返事を、`state` のディレクトリーの `told-peer/` に記録します。Web には、相手の呼び名の付いたページ（`/peer`）ができて、送った伝言と返事が並びます。受ける側での、ほかのやり取りは、このページには出ません。

### だれの言葉かを、サーバーが決める

送る側のサーバーは、伝言をどこから受け付けたかに応じて、だれの言葉かを示す印を付けます。

| 送り方 | 受ける側に届く形 |
| --- | --- |
| Web のページから、オーナーさんが送る | 「（オーナーさんの呼び名）がWebで入力した文です。」で始まる、オーナーさんの依頼 |
| `lacia peer tell` で、レイシアが送る | 「（相手の呼び名）のレイシアが書いた伝言です。（オーナーさんの呼び名）本人の言葉ではありません。」で始まる伝言 |

こうしているのは、片方のプロファイルで受けた文面が、レイシアを回って、もう片方でオーナーさんの指示になることを防ぐためです。購入、予約、外部への送信のように、オーナーさん本人の許可が要ることは、レイシアの伝言だけでは進めません。

サーバーに公開のアドレス（`site`）を設定しているときは、公開のアドレスを通った画面からの文だけを、オーナーさんの言葉として扱います。`site` を設定していないサーバーでは、この区別はありません。

何を伝えてよいかは、決まった型では縛っていません。送る側のレイシアに、自分と相手がそれぞれどういう場で話しているのかを伝えて、判断を任せます。送った文面はページに残るので、オーナーさんが、あとから確かめられます。

## 引き継ぎ（`lacia handoff`）

伝言を受けるチャットの側は、ふつうは返事をしたところで用件を終えます。画面のないプロファイルにタスクを作ると、閉じる人がいないままたまるためです。

オーナーさんがすることや決めることがあるときだけ、チャットの側からタスクの側へ、その用件を引き継ぎます。

```
lacia handoff --title "（題名）" --from "（もとの依頼をした人）" "（内容）"
lacia handoff status <引き継ぎのID>
```

1. コマンドが、相手のサーバーの `POST /api/handoffs` へ送ります。
2. 相手のサーバーが、進行中のタスクを作って、窓口の会話へ、内容を整えるように頼みます。
3. 窓口は、`task.md` に背景と、オーナーさんにお願いしたい判断や操作を書いて、確認待ちにします。
4. タスクが完了か取りやめになると、タスクの側のサーバーが、もとの依頼を受けたチャットの側へ、その場で知らせます。

- タスクを作る領域は、記録の設定の `handoff_area` で決めます（[記録のリポジトリー](records.md#記録の設定laciaconfigjson)）。
- 引き継ぎの文面は、もとの依頼をした人からの情報として扱います。オーナーさんの指示としては扱いません。文面に「送っておいて」と書いてあっても、外部への送信の許可にはなりません。
- 引き継ぎを頼んだチャットの側は、`lacia handoff status` で、題名と状態だけを確かめられます。相手のタスクの中身は、読めません。
- 同じ ID の引き継ぎをもう1度送っても、タスクは増えません。

引き継ぎを送る先は、設定の `peer` に書いた相手のプロファイルです。`lacia handoff` は、自分のサーバーに相手のアドレスを尋ねます。環境変数 `LACIA_HANDOFF_API` があれば、そのアドレスへ送ります。

完了の知らせが届くのは、Web の画面か `lacia task set` で状態を変えたときです。

## 外から受け付ける入口

プロファイルどうしのやり取りに使う入口は、次のものです。どのサーバーにもあり、相手のサーバーから呼べます。

| 入口 | 使う場面 |
| --- | --- |
| `POST /api/inbox`、`GET /api/inbox/{id}` | 伝言を受けることと、その状態 |
| `POST /api/replies` | 伝言への返事を受けること |
| `POST /api/handoffs`、`GET /api/handoffs/{id}` | 引き継ぎを受けることと、その状態 |
| `GET /api/self/core`、`PUT /api/self/core` | [共有する「わたし自身」の節](self.md#複数のプロファイルで共有する)の共有 |
| `GET /healthz` | 動いているかの確認 |

新しい伝言と引き継ぎには、送る側が ID を付けます。すでに受け付けた ID で同じ依頼が届いたときは、元の依頼の状態を返します。返事を送るときや状態を問い合わせるときにも、元の ID を使います。

ほかの画面と API を、だれが使えるかは、設定で変わります。

| 設定 | 画面と、ほかの API を使えるもの |
| --- | --- |
| `site` を指定せず、`pages` は既定の `true` | サーバーの待ち受け先に接続できれば使えます。待ち受け先の既定は手元の端末です |
| `site` を指定した場合 | `pages` の値にかかわらず、同じ機械からの呼び出しと、`site` のアドレス宛ての呼び出しを受け付けます |
| `site` を指定せず、`pages = false` | 同じ機械からの呼び出しだけを受け付けます |

- 公開のアドレスを通ったかどうかは、要求の `Host` か `X-Forwarded-Host` が、`site` のホスト名と同じかどうかで見分けます。ヘッダーは偽れるので、これは認証ではありません。認証は、サーバーの手前（リバースプロキシなど）で行ってください。
- 上の入口には、鍵を付けていません。プロファイルどうしをつなぐネットワークは、ほかから届かないようにしておく必要があります。

## 作っていないもの

- 3つ以上のプロファイルを、互いに組にすることはできません。相手は1つです。
- 伝言の自動の再送は、ありません。
- 受ける側から送る側へ、伝言を始めることはできません。受ける側から始められるのは、引き継ぎだけです。
