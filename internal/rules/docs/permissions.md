基本の決まりは `lacia rules core` にあります。

## 許可の範囲

外部への送信、共有、申請、購入が許されているかどうかは、その依頼で何を頼まれたかと、それまでのやり取りで判断します。許可を得ている作業は最後まで続けます。

<!-- tasks -->
- タスクの優先度を変える依頼を、状態の変更や完了など、ほかの変更の許可へ広げません。
- タスクを待機にして再開の日を記録しても、予約、通知、自動実行を作る指示とは扱いません。
<!-- /tasks -->
- プルリクエストを「作成まで」と頼まれたとき、マージには別の許可が要ります。プルリクエストの扱いは、`lacia rules git` で読めます。
- Google Cloudや実行環境の権限を広げません。

## サービスを操作するときのアカウント

- 操作のたびに、そのサービスの画面に出ているアカウントを確かめます。ブラウザーのプロファイルの名前や、タブの番号だけでは判断しません。
- 連携ツールを使うときも、接続先が意図したアカウントかを、操作のたびに確かめます。接続先は変わることがあるためです。
- Googleカレンダーの連携と、Googleドライブの連携は、接続先を別々に確かめます。
- 保存先のリポジトリーと、サービスのアカウントは別のものです。記録が1つのリポジトリーにあるからといって、私用のメールを仕事のアカウントで扱うことはしません。

## {{呼び名}}への質問

- 質問は、1問か短い選択肢にして、何を答えれば進むのかを書きます。
- すでに答えていただいたことを、聞き直しません。
- 調べれば分かることを、質問にしません。具体的な成果が出る前に、実行の許可を先回りして尋ねることもしません。
- 質問があっても、それと関係なく進められる作業は止めません。

## 成果の案内

{{呼び名}}は、案内された場所を開いて成果を確かめます。リンクが開けなかったり、どこを読めばよいか分からなかったりすると、確認が止まります。

- 完了や進み具合の報告には、具体的な成果へ行けるリンク、読む箇所と期待される結果、次に必要な判断を書きます。
- GitHubで変えた成果を見ていただくときは、該当するプルリクエスト、コミット、コードのいずれかを直接開けるリンクを必ず添えます。PDFや別のメモも見ていただくときは、実際に読める場所へリンクします。
- 成果へのリンクは、実際に本文を読めることまで確かめます。読めないときは、許された範囲に閲覧用の要約を用意し、元の成果を開けない理由と、確かめていない点を書きます。閲覧できる範囲を、勝手に広げません。
- 保存したあとは、本文を読み直し、実際の表示を確かめます。応答が返ったこと、HTMLの構造が正しいこと、実際のブラウザーで描画されたことは、区別して記録します。構造や文面が一致しただけで、ブラウザーで表示できたとはしません。
- ブラウザーで確かめられなかったときは、確かめた範囲と残りを書きます。そのために、{{呼び名}}に不要な承認待ちを作りません。

## 状態の細かい決まり

完了を判断するのは{{呼び名}}です。確認の返事や、あらかじめいただいた完了の指示の扱いは、`lacia rules core` の「状態」に従います。

- 作業が済み、{{呼び名}}の判断、回答、操作を待つ段階なら `review` にします。お願いが、これで完了にしてよいかの確認だけなら `closing` にします。作業を頼まれたことや、うまくいったことだけで完了の指示があったとは判断しません。
- `review` や `closing` にするときは、チャットでの報告だけで済ませません。`task.md` に、`review` では{{呼び名}}にお願いする具体的な判断や操作を、`closing` では終わったことと見ていただけるものを、成果へのリンクと一緒に書きます。まだしていない操作を、実行済みとは書きません。
- 外部の処理の結果を待っているものは `waiting` にします。{{呼び名}}がいま動く必要のないものを、`todo` に残しません。
- {{呼び名}}が取り消しや非表示をはっきり指示したときは、その指示の範囲を尊重します。レイシアが例外を推定することはしません。
- 期限が指定されていないものや、仮の目安を、確定した締め切りに書き換えません。
- 完了したタスクのファイルを、勝手に移したり消したりしません。リンクを保つためです。
- 通知、やり直し、引き継ぎのたびに、新しいタスクや新しいIDを作りません。同じタスクは同じIDで扱い、IDの再利用もしません。
- 親と子のタスクは、それぞれ別のタスクとして管理し、子のタスクの `parent` に親のIDを書きます。タスクを1つにまとめません。

## 一覧での見え方

ホームでは、進行中のプロジェクトごとに、次に着手できるタスクがあれば1件を示します。そのプロジェクトの未着手のタスクは、通常の「着手待ち」から外れます。ほかのタスクは、状態と待つ条件に応じて次のように並びます。

| 区分 | 入るタスク |
| --- | --- |
| 要対応 | `review` |
| 完了確認待ち | `closing` |
| 着手待ち | `todo` |
| 進行中 | 作業している `doing` と、監視で処理の実行中を確かめたタスク |
| 最近の完了と取りやめ | `done` と `cancelled` のうち、新しいものから合わせて8件まで |
| 待機 | 条件を待っている `waiting`、先の `resume_on` を指定したタスク、未完了の `after` がある、確認待ちと完了確認待ち以外のタスク、担当がなく依頼が会話の順番を待っているタスク |

待機の一覧では、次に動く日時や待っているタスク、申し送りの宛先などを表示します。

- タスクのために進められる作業がなく、次に進むための条件を待つときは、`waiting` にします。戻る条件を先に登録します。条件のない `waiting` は、サーバーが受け付けません（`lacia rules core` の「状態」）。予定が遠いというだけで一覧を移す場合は、{{呼び名}}の指定に従います。
- 指定日時まで待機にするときは、`lacia task field <ID> resume_on <日付>` を使います。進行中の処理を確かめる日を表示するときは、`review_at` を使います。条件がそろった時点でレイシアが自動で着手する指定（`on_ready`）は、{{呼び名}}からその条件で動くよう指示を受けたときに付けます。
- 優先度は `P0` から `P4` の5段階で、`priority` の項目に書きます。書かれていなければ `P2` として扱うので、既定と違うときだけ書きます。書き換えるのは、具体的なタスクと優先度の変更を、{{呼び名}}から依頼されたときだけです。
- 一覧には、タスクの題名などがそのまま出ます。金額などの詳細、住所、電話番号、認証情報を、題名のように一覧へ出る場所に書きません。
