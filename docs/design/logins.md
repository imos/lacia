# ログインの違う Codex を呼び分ける

仕事用と個人用など、1つの環境で複数のログインを使うときは、会話をどのログインで起動するか選べます。ログインが1つなら、以下の設定は必要ありません。記録を分けて使う[サーバーのプロファイル](profiles.md)との違いは、[言葉の使い分け](terms.md)にあります。

- **このマシンのログインの一覧**：ログインごとの起動方法を書いて、`lacia codex --login <名前>` で選べるようにします。ローカル環境でも、別の環境のサーバーでも使えます。
- **ログインを分けておく仕組み**（`lacia codex-login`）：1つのサーバーの中で、ログインどうしの認証情報が混ざらないように起動します。root で動くコンテナーの中のような、守りが要る環境のためのものです。

## このマシンのログインの一覧

アカウントを使い分けている人は、ログインごとの起動方法を、`~/.lacia/config/logins.json` に書きます。ディレクトリーは、環境変数 `LACIA_CONFIG_DIR` で変えられます。以前の版の場所（`~/.config/lacia/logins.json`）にだけファイルがあるときは、そちらを読みつづけます。移し方は、[道具の置き場所](settings.md#道具の置き場所)にあります。

```json
{
  "default": "work",
  "logins": {
    "work":     {"label": "仕事用", "codex": ["codex-work"], "codex_home": "~/.codex-work", "unattended": true},
    "personal": {"label": "個人用", "codex": ["codex", "--profile", "personal"], "claude": ["claude"], "codex_home": "~/.codex"}
  }
}
```

| 項目 | 意味 |
| --- | --- |
| `default` | 選ばなかったときのログインです。なければ、`codex` や `claude` を、そのまま起動します。そのログインに、起動するもの（たとえば `claude`）のコマンドがないときも、そのまま起動します |
| `label` | 一覧に出すログインの呼び名です。省くと、ログインの名前を使います |
| `codex`、`claude` | そのログインで起動するコマンドです。自分で用意したコマンド（`codex-work`）でも、フラグ（`codex --profile work`）でも、環境変数（`env CODEX_HOME=… codex`）でも、同じように書けます。どちらか片方だけでも構いません |
| `codex_home` | そのログインが Codex の設定を置くディレクトリー（`CODEX_HOME`）です。[終了を待つ仕事](waits.md#続きを始めるコマンド)が、動いている会話のログインを見分けるのに使います |
| `unattended` | `true` にすると、終了を待つ仕事の続きを、承認とサンドボックスを外して始めます |

選び方は、次のとおりです。

| 打つもの | 起動するもの |
| --- | --- |
| `lacia codex` | `default` のログイン |
| `lacia codex --login personal` | `personal` のログイン |
| `lacia codex-personal` | 同じです。`--login personal` の短い書き方です |
| `lacia codex --login personal --memory` | `personal` のログインで、その起動の自動メモリーを有効にします |

- `--login` と `--memory` は、Codex や Claude Code に渡す引数より前に書きます。
- `--yolo` は、どちらでも、承認とサンドボックスを外して起動するという意味です。Codex には、そのまま渡します。Claude Code には、同じ働きをする引数（`--dangerously-skip-permissions` と、サンドボックスを切る `--settings`）に置き換えて渡します。
- 名前に使えるのは、英小文字、数字、`-`、`_` です。`login`、`stop`、`probe` は、`lacia` のコマンド（`codex-login` など）と重なるので、使えません。
- 起動のときに、どのログインで起動するのかを、1行で表示します。`lacia who` にも、ログインの名前が出ます。
- ログインの名前は、サービスのアカウントを保証しません。操作の前に、画面に出ているアカウントを確かめる決まりは、変わりません。

## 別の端末で受け取る予約のログイン

別の端末の `lacia agent` が受け取った予約は、宛先が示す種類の会話で動きます。ローカル環境で `lacia serve` が会話を起動する場合も、別の環境のサーバーで直接起動する場合も、サーバーの `codex` か `claude` の設定を使います。ログインを使い分ける場合は、このマシンの `logins.json` に `schedule` を足します。各種類の `main` に窓口の会話、`side` に別の会話で使うログイン名を書きます。

```json
{
  "default": "desk",
  "logins": {
    "desk": {"codex": ["codex"], "claude": ["claude"]},
    "review": {"codex": ["codex", "--profile", "review"]}
  },
  "schedule": {
    "codex": {"main": "desk", "side": "review"},
    "claude": {"main": "desk", "side": "desk"}
  }
}
```

選択を省くと、その種類のコマンドを持つ既定のログインを使います。候補が1つだけなら、その候補を使います。ログインの一覧がなければ、インストール済みの `codex` か `claude` を起動します。

macOSの通知アプリから起動するときに自分で用意したコマンドを使う場合は、`codex` や `claude` の先頭にそのコマンドの絶対パスを書けます。
`lacia agent` は自分の実行ファイルの場所と `~/.local/bin` に続けて、既定のログインから順に、登録した絶対パスのあるディレクトリーをコマンドの探索先に加えます。短い名前や相対パスの指定を使うときは、もとの探索先を使います。

## ログインを分けておく仕組み

### 何のための仕組みか

サーバーは、どれか1つのログインで動きます。これを、その環境の「主」のログインと呼びます。会話の途中で、別のログインでしか見られないものを確かめたいときや、別の会話に作業を任せたいときに、次のコマンドを使います。

```
lacia codex-login <名前> [--yolo] [Codex の引数]
```

- `<名前>` は、設定に書いたログインの名前です。
- `--yolo` を付けると、承認とサンドボックスを外して起動します。名前のすぐあとに書きます。ログインを選んだだけでは、外れません。
- 処理の本体は、`internal/login/` にあります。

`lacia` は、ログインの名前も、短いコマンドの名前も、持っていません。`codex-work` のような短いコマンドは、使う環境の側に置きます。

```sh
#!/bin/sh
exec lacia codex-login work "$@"
```

たとえば、ログインの状態を確かめるときは `codex-work login status` を、別の会話として作業を任せるときは `codex-work --yolo exec -` を実行して、依頼の文章を標準入力から渡します。

### 設定のファイル

ログインは、1つの JSON のファイルに書きます。場所は、環境変数 `LACIA_LOGINS` で、絶対パスで指定します。

```json
{
  "main": "work",
  "codex": "/usr/local/bin/codex",
  "worker_root": "/scratch/workers",
  "worker_rules": "/etc/lacia/worker-rules.md",
  "logins": {
    "work": {"codex_home": "/path/to/work-home/.codex-work", "home": "/path/to/work-home"},
    "personal": {"codex_home": "/path/to/personal-home/.codex", "home": "/path/to/personal-home"}
  }
}
```

| 項目 | 意味 |
| --- | --- |
| `main` | サーバーの会話が使う、主のログインの名前です |
| `codex` | Codex の実体の絶対パスです。`lacia` 自身は、指定できません |
| `worker_root` | 作業役ごとのディレクトリーを作る場所です |
| `worker_rules` | 作業役へ渡す決まりに足す文書です。その環境だけの境界を書きます。なくても構いません |
| `drop_to` | root から呼ばれたときに下げる先の UID と GID です。省くと 65534 です。0 は書けません |
| `logins` | ログインの名前ごとに、Codex の設定のディレクトリー（`codex_home`）と、ホーム（`home`）を書きます |

- 名前に使えるのは、英小文字、数字、`-`、`_` です。ログインは、いくつ書いても構いません。
- パスは、すべて絶対パスで書きます。
- 知らない項目があるファイルは、読みません。

#### ファイルを信じる条件

root から呼ばれたときは、このファイルが、権限を下げる先と、信じるディレクトリーを決めます。そのため、root のときは、次を確かめてから読みます。`worker_rules` の文書も、同じです。

- リンクをたどった先のファイルと、その上のディレクトリーをすべて root が所有しています。
- どれも、所有者以外の利用者やグループに書き込みを許していません。読み取り専用でマウントされた場所（Kubernetes の ConfigMap など）は、権限の表示にかかわらず認めます。

root でないときは、確かめません。ファイルが指すのは、呼んだ本人がもともと触れるディレクトリーだけだからです。

### ログインを混ぜないための決まり

起動のたびに、次のことを確かめます。1つでも満たさなければ、起動しません。失敗したときは、`codex_login_failed` とだけ表示します。パス、ログインの情報、依頼の文章を、ログへ出さないためです。

- 設定ファイルがあり、使うログインの名前がそこに書かれています。
- 各ログインが、それぞれ専用のホームと設定のディレクトリーを使います。
- ホームと設定のディレクトリーは、そのログインの利用者が所有し、ほかの利用者には開いていません。どちらも、そこに至るパスにシンボリックリンクがありません。
- 起動する Codex の実体を絶対パスで指定し、そのパスは `lacia` 自身とは異なります。

主でないログインで起動するときと、別の会話を起動するときは、環境変数を、決めた一覧にあるものだけに絞ります。サーバーの持つ Git、SSH、GitHub、Google、Kubernetes などの認証は、渡しません。API キーは、どの起動でも渡しません。ログインの代わりに使われるのを防ぐためです。

#### 作業役

別の会話（`exec`、`resume`、`review`、`fork`）として起動した Codex を、「作業役」と呼びます。作業役には、さらに決まりがあります。

- 作業用のディレクトリー（`worker_root` の下）で起動します。記録のリポジトリーの中では、起動しません。
- Git のフックの置き場所を、サーバーがコマンドを書き出した場所（`LACIA_WORKER_GIT_HOOKS`）へ向けます。そこにある `pre-push` が、すべてのプッシュを断ります。フックがなければ、起動しません。成果を保存するのは、呼び出した側だけです。
- `resume` には、作業役の会話の ID をはっきり指定します。`--last` と `--all` は使えません。サーバーの会話は、再開できません。サーバーが、自分の会話の ID を置いた場所を、環境変数 `LACIA_SERVER_THREAD` で渡します。
- 作業役への注意書きを、開発者向けの指示として渡します。記録のリポジトリーへ書き込まないことと、プッシュしないことは、実行ファイルに入っています。リポジトリーの名前は、環境変数 `LACIA_DATA_REPOS` から足します。その環境だけの境界は、`worker_rules` の文書から足します。
- サーバーのアドレス（`LACIA_API`）は、渡しません。作業役は、タスクを直接は操作できません。
- モデルは、サーバーの設定の `codex-model` と `codex-effort` に従います。サーバーが、環境変数 `LACIA_CODEX_MODEL` と `LACIA_CODEX_EFFORT` で渡します。なければ、そのログインの Codex の設定のままです。

#### 権限を下げる

root から呼ばれたときは、Codex を起動する前に、UID と GID を `drop_to` へ下げます。サーバーが root で動き、ログインの情報の持ち主が別の利用者である環境に、合わせるためです。

- 下げる前に、そのログインのホームと設定のディレクトリーが、すでにあること、持ち主が下げる先の利用者であること、権限がちょうど 0700 であることを確かめます。
- 補助グループ、グループ、利用者の順に下げて、下がったことを確かめてから起動します。

## 定期タスクの実行プロファイル

予約や固定IDの定期タスクの `profile` には、実行する端末の `logins.json` に登録した名前を書けます。`to` は実行先の場所と種類を選び、`profile` はその端末で使うログインと起動引数を選びます。省いた場合は、これまでの起動方法を保ちます。

```json
{
  "logins": {"desk": {"codex": ["codex"]}},
  "execution_profiles": {
    "cluster-read": {
      "login": "desk",
      "kind": "codex",
      "args": ["--add-dir", "/home/example/.kube"]
    }
  }
}
```

これは登録の形を示す例です。端末を管理する人が、必要な書き込み先や起動引数を確かめて登録し、`lacia agent` を起動し直すと読み込みます。サーバー上で実行する場合は、サーバーが実行の直前に、その端末の一覧を読みます。`login` は登録済みのログイン名、`kind` は `codex` か `claude` です。`args` は、そのログインのコマンドに続けて渡す引数です。権限を絞れるかどうかは、端末側で登録したコマンドと設定で決まります。

```yaml
to: local-codex
profile: cluster-read
```

- 名前には英小文字、数字、`-`、`_` を使えます。最大32文字です。`default` は、未指定で実際に動いた設定を履歴に表す名前として予約しています。
- 予約の本文やサーバーから、コマンド、ログイン、引数を上書きすることはできません。不明な名前や種類が合わない指定は、通常設定へ戻さず、実行の失敗として残します。プロファイルに対応しない旧版の端末には、その指定のある実行回を渡さず、対応版への更新待ちを画面に示します。
- 明示したプロファイルの会話は、通常の会話や別のプロファイルの会話と分けて保存します。
- 結果と月ごとの実行履歴には、実際に使った端末、プロファイル名、選んだログイン名を記録します。コマンドや認証情報は記録しません。選択できずに失敗した場合は、依頼された名前を実行定義に残し、使っていないプロファイルを使用済みとは記録しません。
- プロファイルは、外部のサービスへ操作してよい範囲を広げません。認証とログインの管理は、登録する端末が受け持ちます。
