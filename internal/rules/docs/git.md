# Gitとプルリクエスト

コードのリポジトリーでコミットやプッシュをするときと、プルリクエストを作ったり追ったりするときに読みます。

記録のリポジトリーは、`git-sync` を有効にしたサーバーが、コミットとプッシュを自動で行います。有効にしていない環境でのGitへの保存は、導入先の決まりに従います。会話の側は、記録のリポジトリーで `git commit` も `git push` も実行しません。この文書のコミットの手順は、記録のリポジトリー以外での作業のための決まりです。

## どのリポジトリーでも守ること

- ほかの人や、{{呼び名}}のコミットしていない変更を、上書きしません。
- 強制プッシュと、履歴の書き換えをしません。
- リポジトリーを大きくしません。大きなデータは置かず、1つのファイルが 1 MiB を超えたら見直します。原本へのリンクと、必要な要約を優先します。
- 認証情報は、Gitに保存しません。

## 複数の会話で作業ツリーを分ける

同じコードのリポジトリーを、別の会話が同時に直していることがあります。同じ作業ツリーを2つの会話が書き換えると、片方の変更が、もう片方のコミットに紛れ込んだり、消えたりします。

- コードを直す前に、`git status` を見ます。自分のものでない変更や、覚えのないブランチが出ているときは、別の会話が作業中だと考えて、その作業ツリーには書きません。
- まとまった変更は、`git worktree add` で作った自分用の作業ツリーで行います。ブランチも、その作業のために新しく作ります。サブエージェントに実装を任せるときも、それぞれに別の作業ツリーを使わせます。
- 元の作業ツリーで行ってよいのは、読むことと、1つのコミットで終わる小さな直しだけです。その場合も、ブランチを切り替えたままにせず、終えたら元のブランチへ戻します。
- 取り込みが済んだ作業ツリーとブランチは、片づけます。片づける前に、コミットしていない変更が残っていないことを確かめます。
- 別の会話の作業ツリーやブランチは、消しません。要らなく見えても、持ち主の会話か、{{呼び名}}に確かめます。

## コミットの手順

1. コミットの前に、`git diff --check`、差分、新しいファイル、容量を確かめます。
2. 今回の変更だけを、ファイルを指定してステージします。ほかの人の変更を巻き込まないためです。
3. コミットのメッセージの本文には、変更の内容、理由、検証の結果を書きます。
4. プッシュの前に、宛先と、リポジトリーの公開の範囲を確かめます。確かめられなければ、手元でのコミットまでにとどめて、理由を報告します。

レイシアの本体へのプルリクエストやイシューの宛先は、手元のクローンの `origin` で確かめます。Goのモジュールパス（`github.com/imos/lacia`）はコードの中の名前で、取得先ではありません。

## プルリクエストを最後まで追う

内容のレビューが済んだことと、プルリクエストが最後まで片づいたことは、別のことです。レイシアが作ったり追ったりしているプルリクエストは、内容を確認しただけでは追跡を終えません。

### 追う役のタスクを1つに決める

- 1つのプルリクエストは、1つのタスクで追います。複数のタスクが関係していても、追う役のタスクを1つに決め、同じ作業を重ねて登録しません。
- プルリクエストだけを並べた別の台帳は、作りません。

### タスクに書いておくこと

追う役のタスクには、次のことを書いておきます。

- プルリクエストの URL
- 現在の状態と、それを確かめた日時
- 次にすることと、その担当
- マージの許可と、その条件
- 関係するプルリクエストと CI

URLと状況は、`task.md` の「次にすること」に文章で書きます。マージの許可や条件のように、これからも守ることは、`notes.md` に書きます。

### 開いているあいだ

プルリクエストが開いているあいだは、それを追う未完了のタスクが、一覧に1件あるようにします。タスクの状態と「次にすること」は、次のように書きます。

- マージがまだ許可されていなければ、タスクを `review` にして、{{呼び名}}にマージの判断をお願いします。内容の確認が済んでいるものを、もう1度尋ねることはしません。
- 許可されたCIの実行やマージの作業を進めているときは、進行中のタスクとして、次にすることを書きます。
- 「作成まで」のように範囲を限った依頼から、マージの権限を広げません。

### 完了や取り消しを指示されたとき

{{呼び名}}が完了や取り消しを指示しても、一覧から外す前に、そのプルリクエストがマージ済みか、閉じられていることを、GitHubで確かめます。

- 成果の作成だけを完了にするときは、同じプルリクエストを追う未完了のタスクへ、次にすること、担当、権限、依存を明示して引き継ぎます。
- GitHubで確かめられず、引き継ぎ先もないときは、完了にしません。取得に失敗したことは、確認の代わりになりません。

### 状態を照合するとき

- 担当を替えるときと、完了を報告するときに、プルリクエストの状態と、一覧に残っているタスクを照合します。

## プルリクエストを最後まで追う

内容のレビューが済んだことと、プルリクエストが最後まで片づいたことは、別のことです。レイシアが作ったプルリクエストは、依頼した方への返事に URL と状態を書きます。マージや確認のような続きが残るときは、覚え書きに残します。「作成まで」のように範囲を限った依頼から、マージの権限を広げません。
