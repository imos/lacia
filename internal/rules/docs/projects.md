# プロジェクトの決まり

プロジェクトのタスクに着手するときと、プロジェクトを作ったり、取りかかる順を決めたりするときに読みます。

プロジェクトは、いくつかのタスクを、めざすこと、進め方、取りかかる順と一緒にまとめたものです。タスクの一覧だけでは、どこから手をつければよいのかが分からないので、プロジェクトごとに「次の1件」が決まるようにしています。

## 置き場所と形

`areas/<領域>/projects/<名前>/` のディレクトリーに `project.md` を置くと、そのディレクトリーがプロジェクトになります。案件の資料も、同じディレクトリーに置きます。仕事と私用をまたぐプロジェクトは作りません。`projects/` の下には、`project.md` のないディレクトリーを置きません。

```markdown
---
title: 事務所の移転の準備
status: active
---

## めざすこと

何のためのプロジェクトで、何ができたら、めざしたことを果たしたと言えるのかを書きます。

## いまの状況

全体のどこまで進んだかと、次に何をするかを3行から5行で書きます。

## 進め方

- 移転先は、駅から歩いて10分以内に絞ります。（2026-11-12、{{呼び名}}の指示）

## 取りかかる順

1. X58 — 候補を比較する前に、移転先の条件を決めます。
2. X59
3. X64 — ほかの結果を待たずに進められます。

## いまの資料

- 2026-11-12 [候補の比較](comparison-2026-11-12.md)
```

- `status` は、`active`（進行中）、`paused`（保留）、`done`（完了）のどれかです。ホームに出るのは、進行中のものだけです。
- 見出しは、「めざすこと」「いまの状況」「進め方」「取りかかる順」「いまの資料」の5つです。この順に置きます。画面が読むのは「取りかかる順」だけなので、この名前は変えません。
- 「めざすこと」は、ほとんど変わりません。「いまの状況」は、段階が変わったときに書き直します。
- 「進め方」には、いま有効な方針だけを、箇条書きにします。出どころを、文の終わりのかっこで添えます。指示を受けた経緯と、作業の結果は書きません。方針が変わったら、古いほうを消します。
- 「いまの資料」には、プロジェクトを通して使う資料（計画、台帳、連絡先など）を並べます。
- 全体で60行ほどまでにします。細かい経緯や調査は、同じディレクトリーの資料に書いて、リンクします。

## 履歴（log.jsonl）

プロジェクトの履歴は、`project.md` と同じディレクトリーの `log.jsonl` です。形は、タスクの履歴と同じで、1行が1件の JSON です。

- 画面で順を動かすと、サーバーが自動で書きます。
- 方針や順を変えた理由は、`lacia project note <名前> "備品の整理（X64）を候補の比較（X59）より先にしました。移転先が決まる前から進められるためです。"` で書きます。`<名前>` は、プロジェクトのディレクトリーの名前です。同じ名前が別の領域にもあるときは、`<領域>/<名前>` と書きます。日時と、だれが書いたのかは、コマンドが付けます。
- `log.jsonl` を直接編集しないでください。書き換えや並べ替えはしません。

## タスクを入れる

タスクをプロジェクトに入れるときは、`lacia task field <ID> project <名前>` を実行します。`<名前>` は、プロジェクトのディレクトリーの名前です。そのうえで、`project.md` の「取りかかる順」に、そのタスクを書き足します。

- 「取りかかる順」に書かれていないタスクは、末尾に「順序が未定」として出ます。そのままにしないでください。
- 単発の用事は、プロジェクトに入れなくて構いません。
- 親のタスク（`parent`）は、1つのタスクを細かく分けるときだけに使います。まとまった仕事を束ねるときは、プロジェクトを使います。

## 取りかかる順を決める

取りかかる順は、レイシアが、進め方に沿って決めます。上にあるものほど、先に進めます。

- 行は「番号. ID — 理由」の形で書きます。なぜその順にしたかが分かりにくいときは、理由を添えます。
- **{{呼び名}}から順の指示があったときは、そのとおりに並べて、指示を「進め方」に書き残します。** あとで並べ替えるときに、指示を上書きしないためです。
- 順を変えたら、何をどう変えたのかと理由を、プロジェクトの履歴に1件で残します。
- タスクが完了しても、行は消さなくて構いません。画面では、終わったタスクは別にまとめて出ます。

## 依存を書く

あるタスクに着手する前に、別のタスクが終わるのを待つときは、待つ側のタスクに条件を書きます。たとえば `lacia task field <ID> after "X58, X61"` とすると、`<ID>` のタスクは X58 と X61 を待ちます。`project.md` には、取りかかる順を書きます。

- `after` に書いたタスクがすべて完了か取りやめになると、この条件を満たします。それまでは「次の1件」の候補から外れます。画面で、どのタスクを待っているかを確かめられます。
- 日時も指定してあれば、その日時まで待ちます。条件がすべてそろうと、通常は「要対応」に出ます。自動で着手する指定があれば、サーバーが会話に着手を依頼します。指定の仕方は `lacia rules tasks` にあります。
- `after` を指定しなければ、取りかかる順で上にあるタスクの終了を待つ必要はありません。上のタスクが止まっているあいだに、下の着手できるタスクを進められます。
- `after` には、ほかのタスクのIDを書きます。定期タスクの次の実行を待つときは `after_run` を使います。それ以外の外部の処理や人の返事を待つときは、状態を `waiting` にして、何を待つのかを「次にすること」に書きます。
- 本当に必要な依存だけを書きます。「なんとなくこの順がよい」は、取りかかる順で表します。書きすぎると、進められるタスクが見えなくなります。

## 次の1件

ホームには、進行中のプロジェクトごとに、全タスクのうち何件が完了か取りやめになったかを表示します。「次の1件」は、取りかかる順の上から見て、次の3つを満たす最初のタスクです。

- 状態は「未着手」です。
- `after` で指定したタスクは、すべて閉じています。
- `resume_on` の指定がありません。

進行中のプロジェクトに属する未着手のタスクは、プロジェクトの欄にまとめます。確認待ち、完了確認待ち、進行中のタスクは、それぞれの欄にプロジェクトの名前を添えて1件ずつ出します。

「次の1件」は、取りかかる順を示すものです。レイシアが着手するのは、{{呼び名}}から依頼があったときか、「進め方」に「続けて進めてよい」と書いてあるときです。日時やほかのタスクを条件に自動で着手するときは、タスクに `on_ready` の指定が要ります。

## プロジェクトのタスクに着手するとき

1. タスクの冒頭に `project:` があったら、`project.md` の「めざすこと」と「進め方」を読みます。
2. 頼まれたタスクが取りかかる順のどこにあるかと、`after` に書かれたタスクがすべて閉じているかを確かめます。まだ待っているタスクがあれば、そのことを{{呼び名}}に伝えてから進めます。
3. 作業の結果、取りかかる順や進め方を変えたほうがよいと分かったら、`project.md` を直して、`lacia project note` で履歴に理由を残します。

## プロジェクトを作る、閉じる

- 新しいプロジェクトは、{{呼び名}}から頼まれたときか、関連するタスクが4件以上になり、取りかかる順を決める必要が出たときに、{{呼び名}}に提案して作ります。
- めざしたことを果たしたら、{{呼び名}}に確かめてから、`status` を `done` にします。しばらく進めないときは、`paused` にします。
