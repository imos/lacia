# 固定IDの定期タスクへ移すとき

この手順は、旧来の予約名を固定IDへ変えるときに使います。固定IDを保って領域の下へ移すときは、[記録の形式2への移行](records.md#形を移すlacia-migrate)を使います。

定義ローダーは、`routines/S1001/routine.md` を読みます。`id` はディレクトリー名とそろえ、`title` を変えても保ちます。`area` は任意の表示区分で、`output` は `matters`、`task`、`none` から選びます。既存の予約を移すときは、`legacy_name` に旧名を保存します。新旧の定義が両方あっても、新しい定義だけを読みます。同じ旧名を複数の固定IDへ割り当てると、両方を無効にして誤実行を防ぎます。

`to`、時刻、停止状態、返信先と本文はそのまま引き継ぎます。今回のローダー変更だけでは、設計案にある `place` や `weekdays` を有効にしません。既存の実行先を別の項目へ置き換えないでください。

## 移す前に確かめること

旧名ごとに固定IDを割り当て、対応表を保存します。採番は移すたびにやり直さず、同じ対応表を使います。コードのリポジトリーには、個人や組織の対応表を置きません。対応表は移行する記録の成果物に置いてください。

```json
[
  {"id": "S1001", "legacy_name": "github", "area": "work", "output": "matters"},
  {"id": "S1002", "legacy_name": "calendar", "output": "none"}
]
```

`output` は、既存の本文だけから安全に決められません。移行ツールでは、明示していないものを `none` とします。読む結果を届けるものは `matters`、毎回通常タスクを作るものは `task` と指定してください。本文の報告方法も、新しい結果の受付に合わせて確かめます。

通常タスクのID、採番設定と、すでにある固定IDに衝突がないことを確かめます。仕事用と家庭用は、記録ごとに別の対応表を使います。家庭用に通常タスクがない場合も、定義、実行と確認の履歴を同じ形にそろえられます。家族への投稿と、仕事用への引き継ぎの範囲は変えません。

## 仮のコピーで試すこと

`python3 scripts/migrate-routines.py --root コピー先 --mapping 対応表.json --state-dir 状態のコピー先` で、保存や削除するファイルを確認します。`--apply` を付けない限り、ファイルを書きません。

実際に移すときは、管理するサーバーの `state/drain` を置いて、新しい予約と会話の受付、端末のPoll・開始・結果通知による状態の保存を止めます。既存の実行がある場合は、結果を端末側の送信待ちに保ち、実行IDと取得用の値を変えません。記録と状態の両方を退避してから、次のように実行します。`--stopped` は停止済みという操作者の申告で、停止する命令ではありません。対応前の版ではdrain中もPollが状態を保存します。対応版を先に配備し、drain中のPollが503で再試行になることを確かめてください。drainを置いたあとに `/routines` と `/api/schedule-runs` を読み、進行中だったtickerとdispatchの書き込みが終わるまで待ってから、状態の控えと移行を始めます。

```sh
python3 scripts/migrate-routines.py \
  --root /path/to/records --mapping /path/to/map.json \
  --state-dir /path/to/state --apply --stopped \
  --backup /path/to/records/local/routine-migration-backup-1
```

ツールは、定義、旧名の `routines/` の下にある追える履歴、Markdown内の明示的な旧パスを移します。定義内の相対リンクは、移した深さに合わせます。`archive/` は書き換えません。本文中の生のパスや、スクリプト、JSON、過去の会話の参照は、別に照合します。Git除外や権限を変えません。Git管理外の結果ファイルは、元の保存先と参照を確認してから別途移してください。

状態のコピーには、`schedules.json`、`schedule-runs.json`、`schedule-dispatch.json` をそろえます。最後に受付した時刻は旧名と新IDの両方から引けるようにし、待機中と実行中の名前だけを新IDへ移します。実行ID、取得用の値、開始時刻、結果、端末と接続や認証を待つ状態は変えません。ワーカーの状態と依頼のキューは、既存の実行IDのまま使います。

移行を終えても、drainは外しません。状態をメモリに持つサーバーを、通常の再起動で読み直します。読み直した状態と移行後のファイルが一致し、履歴と境界、実行IDが保たれていることを確かめてから、今回置いたdrainを外します。端末は保存した結果を同じ実行IDで再送します。

受付停止中に依頼や終了通知が待機すると、通常の再起動確認は通りません。業務記録と運用状態を分けて移す場合は、移行計画のうち記録側だけを先に適用し、運用状態はまだ所有プロセスと同じ内容に保ちます。受付を戻して待機のメッセージを通常処理し、依頼が空になった区切りで改めてdrainを置きます。バリアとなる2つの読み取りを終えてから、変更対象が運用状態だけであることを検査して適用し、通常の再起動へ進みます。通知を取り消したり、確認済みを作ったりして再起動確認をすり抜けません。

再実行すると、保存済みの対応表を照合します。途中まで書き込まれていても、新旧の内容が一致すれば続けられます。古い実行を新着として再受付する処理はありません。確認と通知の履歴がすでにあれば、ファイルをそのまま移します。履歴のない古い回に「確認済み」「通知済み」を作ることはありません。

## 切り替えるときに残す照合

- 移す前後の定義の数、ID、時刻、実行先、停止状態を比べます。
- 待機中、実行中、認証待ちの実行IDの集合と、それぞれの状態が同じかを比べます。
- 確認済みと通知済みの境界、未確認分、実行履歴の件数と内容を比べます。旧形式に確認の履歴がなければ、「確認できない」と書いて、未確認分を推測して復元しません。
- GitHubの確認1件で、新しい結果、新着0件、同じ回の再送、完了と次の新着が重なる場合を確かめます。
- 新旧を同時に起動せず、対応する版だけを再開します。

バックアップには、変更前の各ファイルと場所を `journal.json` に残します。途中で止まったときは、新旧の受付を止めたまま、残った一時ファイルを調べ、同じ対応表と新しいバックアップ先で再実行します。完了後に履歴が増えた状態から、バックアップで一括上書きしないでください。戻すときも、切り替え後の実行、確認と通知の履歴を保つ必要があります。旧版で新しい確認の履歴を扱えない場合は、配信を止めたまま対応する版で復旧します。

## 導入用のひな形に置く例

新しい導入では、`routines/S1001/routine.md` に、次のような停止中の架空の例を置きます。実行先と本文を埋めてから有効にしていただく形です。

```markdown
---
id: S1001
title: 予定された確認を行います
area: personal
daily: "09:00"
output: matters
conversation: side
enabled: false
---

## めざすこと

オーナーさんが、その日の対応を決めるための情報を確かめます。

## ふだんの状況

自分のアカウントで読み取りだけを行います。確認するサービスを、導入するときに書いてください。

## すること

確認する対象と、新しい結果を受け付ける手順を、導入するときに書いてください。

## しないこと

送信、購入、予約は行いません。

## 伝え方

新しい結果を定期タスクへ記録します。変化がなければ「報告はありません。」と答えます。
```

ひな形の `.gitignore` では、`routines/`、`runs.jsonl`、`reviews.jsonl` を除外しません。作業用の `local/`、認証情報と実行時の秘密は、これまでどおりGitに入れません。履歴だけでなく、対応表、定義と手順もGitで保存します。
