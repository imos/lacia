# 終了を待つ仕事

時間のかかる計算を外部で実行しているときは、終了を確かめるための「待ち」（W）を登録できます。依頼した会話を閉じても、計算が終わると「待ち」が閉じます。そのあとの作業は「申し送り」（H）として、続きを受け持つ会話に届きます。

Kubernetes の Job やファイルを見張るときは、端末の `lacia agent` が `kubectl` で対象を確かめます。ローカル環境で使うときも、別の環境でサーバーを動かすときも、申し送りの `lacia tell` はクラスタの計算と独立して使えます。クラスタの見張りを使わない場合は、設定の `waits = false` で待ちを止められます。 [申し送り](#別の会話へ依頼するlacia-tell)

## 何が起きるか

待ちを登録すると、会話を閉じても、次のことが起きます。

- 端末の `lacia agent` が、対象の状態を確かめて、サーバーへ知らせます。
- 終わると、続きを行う側へ、知らせが届きます。
- 期限までに終わらないとき、対象が消えたとき、続きが始まらないときは、タスクが確認待ちへ出て、オーナーさんへ通知が届きます。

任せたことを、忘れないための仕組みです。会話の側の使い方は、決まりの `waits`（`lacia rules waits`）にまとめています。

## 使い方

Job を投入して、同時に待ちを登録します。

```
lacia job run --task T1062 --context example-cluster -f job.yaml --by 6h \
  "終わったら、結果を回収して、比較の表を作ります。"
```

すでに動いているものには、あとから登録します。

```
lacia wait add --task T1062 --job example-cluster/team-a/score-1 --by "2026-11-19 06:00" \
  --next local-codex "終わったら、採点の結果を集計します。"
lacia wait add --task T1059 --file example-cluster/team-a/deploy/workspace:/root/run/DONE --by 3h \
  "終わったら、応答の安定性と費用を集計します。"
```

| 引数 | 意味 |
| --- | --- |
| `--task` | 対象のタスクです |
| `--job <context>/<名前空間>/<Job名>` | Kubernetes の Job の終了を待ちます |
| `--file <context>/<名前空間>/<Pod>:<パス>` | Pod の中の処理が最後に書く、「終了の印」のファイルを待ちます。ファイルの1行目が `fail` で始まると、失敗として扱います |
| `--by` | 終わる見込みの期限を必ず書きます。`6h`、`90m` のような長さか、`2026-11-19 06:00` のような日時で指定します。日時には記録の `timezone`（既定は `Asia/Tokyo`）を使います |
| `--next` | 続きの宛先です。`local-codex` などの会話名のほか、場所だけ、会話の種類だけ、あるいは `none` を指定できます。省くと、登録した会話と同じ場所と種類になります |
| 最後の文章 | 終わったらすることです |

- `--job` と `--file` は、どちらか1つを書きます。
- `--file` の Pod の部分には、`deploy/<名前>` のように、種類を付けて書けます。
- `--next none` にすると、続きの会話は始めずに、タスクを確認待ちへ出します。
- 続きの会話は、登録した会話の中身を知りません。最後の文章に、読むもの、成果物の名前、してよい範囲を書きます。足りない前提は、対象のタスクの `notes.md` へ、先に保存します。
- `lacia job run` は、YAML に Job がちょうど1つあることを確かめてから、`kubectl apply` で投入して、待ちを登録します。

登録すると、タスクは外部待ち（`waiting`）になります。ホームでは、監視で処理が実行中だと確かめたタスクを「進行中」に表示します。実行前や状態を確かめられない間は「待機」に表示し、待つ対象と確認の期限を添えます。

```
lacia wait list [--task ID] [--all]   待ちと申し送りを分けて並べる
lacia wait show <WかHのID>        対象と結果、申し送りの中身を読む
lacia wait ack <WかHのID>         申し送りを受け取ったことを知らせる
lacia wait cancel <WかHのID>      取り消す
```

タスクのページには「いま待っているもの」と「受け取りを待っている申し送り」があります。待っていた計算などが終わると、その項目は待ちの一覧から消えます。続きの依頼は申し送りの欄に出て、会話が受け取るか、見送りや取り消しになると消えます。経過はタスクの履歴で読めます。

`show W...` は、待ちの対象と結果に加え、関連する申し送りも表示します。`ack W...` は、その待ちから生まれたHへ転送します。待ちがまだ終わっていなければ、受け取れません。開いているWの `cancel` は見張りを取り消し、終了後のWでは関連する申し送りを取り消します。

## 役割の分け方

| 役割 | 受け持つ側 | 理由 |
| --- | --- | --- |
| 待ちの記録と、オーナーさんへ出す判断 | サーバー | ローカル環境でも別の環境でも、書き込める記録を持ち、動いているあいだに判断します |
| 対象の状態を見ること | 端末の `lacia agent` | 端末の `kubectl` で、権限のあるクラスタを確かめるためです |
| 続きの会話を始めること | 宛先のサーバーか、端末の `lacia agent` | 作業に要る権限を持つ場所を、登録するときに選びます |

待ちは、サーバーの `state` のディレクトリーの `waits/` に、申し送りは `handovers/` に、1件を1つの JSON として置きます。

- Wは `schema_version: 2` です。種類は `job` と `file` だけで、対象、観測、期限、結果を持ちます。`state` が `open` でなくなると `Closed()` が真になります。配信や受け取りの時刻は持ちません。
- Hは `schema_version: 1` です。届ける文章、届ける先、配信と受け取りの状態を持ちます。Wから生まれたHには `wait_id` を、Wには `handover_id` を残し、互いをたどれるようにします。`lacia tell` のHには、元のWがありません。
- タスクの履歴では、待ちに関する出来事を `wait`、申し送りの作成、配信、受け取りを `handover` で記録します。進行中のタスクがほかの状態に変わったときに残す本文の控えにも `handover` を使います。申し送りの記録には、JSON の `handover` 項目にその ID が入ります。

APIも分けます。`GET/POST /api/waits` と `GET/PATCH /api/waits/{id}` は待ちを、`GET/POST /api/handovers` と `GET/PATCH /api/handovers/{id}` は申し送りを扱います。一覧には、どちらも `task` と `all=1` を指定できます。既存の呼び出しのため、更新は `POST` でも受け付けます。`tell` はHを直接作り、端末は観測だけをWへ、配信の開始と結果をHへ送ります。

端末の見張りが動くのは、`lacia agent` の設定に `tasks_repo`（記録のリポジトリーの読み取り専用のコピー）があるときです。続きの会話を、そのディレクトリーで始めるためです。設定は、[Mac の通知](notifications.md)にあります。

## 見張り

待ちと申し送りの状態は、サーバーが持ちます。端末の `lacia agent` は、30秒ごとにサーバーへ待ちと申し送りの一覧を別々に尋ねます。開いている待ちの対象は、1分おきに `kubectl` で見ます。待ちのAPIが無効でも、申し送りの配信は続けます。端末がスリープしたり `lacia agent` が再起動したりしても、再開後に状態を確かめます。

見えた状態は、6つです。

| 状態 | 意味 |
| --- | --- |
| 開始待ち | まだ始まっていません |
| 実行中 | 動いています |
| 成功 | 終わりました |
| 失敗 | 失敗で終わりました |
| 見つからない | Job がなくなりました |
| 確かめられない | 認証切れや、通信の失敗です。終了とは扱いません |

- 見張りは、後処理を実行しません。機械的な後処理（集計、保存、終了の印を書くこと）は、ジョブ自身の最後の手順に入れます。判断の要る後処理は、続きの会話が行います。
- macOS では、待ちが開いているあいだと、続きの会話が動いているあいだ、`caffeinate -i` でスリープを抑えます。ふたを閉じた Mac のスリープは、抑えられません。

## 終わったあと

申し送りの時間を数える基準は、`lacia tell` を使ったときは登録した時刻、待ちの結果を届けるときは待ちが終わった時刻です。サーバーが停止していて申し送りを作るのが遅れても、ここから数えます。

| 起きたこと | サーバーがすること |
| --- | --- |
| 成功か失敗で終わった | Wを閉じます。続きを行う側が決まっていれば、対象、結果、観測の詳細、終わったらすることをHの文章にまとめ、サーバー自身か指定された端末が届けます |
| 期限を過ぎた | 履歴に書いて、タスクを確認待ちへ出します。続きは始めません |
| 対象が見つからなくなった | 同じです |
| 基準時刻から20分たっても、続きの会話から受け取りの知らせがない | 受け取りの遅れをタスクの履歴と申し送りの一覧に出します |
| 続きの会話が、受け取りを知らせずに終わった | 受け取りがなかったことを、その時点で記録します |

- 申し送りの配信や受け取りが遅れたときは、タスクの状態を保ちます。送り手が `--owner-action` でオーナーさんへお願いする操作を明示している場合は、履歴とタスクのページにその操作を表示し、進行中のタスクを除いて確認待ちへ出します。サーバーがタスクの状態を確認待ちに変えると、`ready_since` が付きます。すでに確認待ちなら、理由を履歴に残します。通知と、Web の「着手を頼む」のボタンは、[条件がそろったタスク](records.md#条件がそろったら確認待ちへ出すか着手する)と同じ仕組みで働きます。
- 宛先の端末がスリープしていたときは、復帰後に続きを始めます。申し送りの基準時刻から24時間を過ぎていたら、見送ります。
- 待ちを登録したあとでタスクが進行中になっていたら、サーバーはその状態を保ちます。待ちから生まれた申し送りを自動で届けるのは、進行中でなくなってからです。`lacia tell` で直接依頼した申し送りは、進行中でも届けます。

### 申し送りの状態

配信と受け取りの判断には、Hの `state` だけを使います。`started`、`acked`、`told` などの時刻や、`via` は経過を説明するための記録です。

| 状態 | 意味 |
| --- | --- |
| `queued` | まだ届けていません。指定した宛先へ配信できます |
| `delivered` | 宛先への配信を引き受けました。受け取りの知らせを待ちます |
| `acked` | 会話が受け取りました |
| `told` | 配信前に20分が過ぎ、遅れを記録しました。24時間以内なら、宛先へ配信できます |
| `told_delivered` | 配信を引き受けたあと、受け取りがないため、遅れを記録しました。再配信はしません |
| `skipped` | 24時間を過ぎたか、タスクが閉じたため、続きを始めません |
| `cancelled` | 取り消しました |

配信できるのは `queued` と `told` だけです。`acked`、`skipped`、`cancelled` でHは閉じます。配信を引き受ける更新は、サーバーが1件だけ受け付けます。届けたあとにサーバーや端末が再起動しても、同じHをもう1度届けません。

待ち（W）の終了と申し送り（H）は、別々のファイルに記録します。待ちから作る申し送りの ID は、元の待ちの ID の先頭を `W` から `H` に替えたものです。サーバーは終了した待ちを定期的に調べ、申し送りがなければ作り、`handover_id` が抜けていれば補います。申し送りを保存した直後に止まっても、同じ ID の記録を使って復旧できます。

### 続きの会話がすること

続きの会話は、最初に `lacia wait ack <HのID>` で受け取りを知らせます。元のWのIDも使えます。申し送りの内容は `lacia wait show <HのID>` で読みます。

サーバーは、受け取った会話を特定できると、その会話をタスクの担当にして、状態を進行中にします。宛先に場所と種類が記録されている場合は、その両方が一致する会話だけが受け取れます。宛先に種類だけが記録された従来の申し送りでは、サーバーが会話を特定できなければ、受け取りだけを記録します。その場合は、タスクの担当も状態も変わりません。

- サーバーが受け取りを記録するのは、最初の1回です。`ack` で、ほかの会話がすでに受け取ったと知らされたら、続きを始めません。
- Hの受け取りを保存してからタスクの担当を替えるまでのあいだに処理が止まったときは、`ClaimPending`（JSONでは `claim_pending`）を残します。同じ会話からの `ack` の再試行か、サーバーの定期の処理で、保存した受け取り先への担当変更をやり直します。
- 待ちの知らせは、新しい許可ではありません。続きは、対象のタスクの `notes.md` に書かれた許可の範囲で行います。

### 続きを届ける先

サーバー自身を宛先にした申し送りは、サーバーの依頼の待ち行列から、新しい別の会話へ届けます。登録した端末への申し送りは、その端末の `lacia agent` が届けます。

**登録した端末の Codex に任せたとき**は、その端末の記録のコピーで動いている Codex の会話へ届けます。

- 届ける先は、この12時間にコマンドを使い、プロセスが動いている会話から選びます。待ちを登録した会話が候補にあれば、その会話を優先します。そうでなければ、最後にコマンドを使った会話を選びます。タスクの担当として残っている会話も、12時間を過ぎていれば候補に入れません。共有プロセスが残っていても、会話が使われているとは限らないためです。
- 動いている会話の一覧は、サーバーが、`lacia` コマンドの呼び出しから記録しているものを使います。対象は、この12時間にコマンドを使った会話のうち、プロセスが残っているものです。
- 届けるのは、短い知らせです。
- 動いている会話がないときと、届けられなかったときは、新しい会話を始めます。

**登録した端末の Claude に任せたとき**は、新しい会話を始めます。動いている Claude Code の会話へ、外から知らせる方法は、いまはありません。

新しい会話の最初のメッセージには、待っていたもの、結果、登録した会話、終わったらすること、進める順序を書きます。どちらの形でも、登録した会話の中身は引き継がれません。つなぐのは、タスクの記録だけです。

### 続きを始めるコマンド

登録した端末の会話を始めるコマンドは、[このマシンのログインの一覧](logins.md#このマシンのログインの一覧)から選びます。一覧がなければ、インストール済みの `codex` か `claude` を使います。

Claude は、その種類のコマンドを持つ既定のログインを使います。候補が1つだけなら、その候補を使います。選んだコマンドに `-p` を足して、新しい会話を始めます。

Codex は、次のように起動します。

- 動いている会話へ届けるときは、ログインのコマンドの後ろに `queue --thread … --message …` を足します。
- 新しい会話を始めるときは、`exec -C <tasks_repo> -` を足します。一覧の `unattended` が `true` のログインでは、承認とサンドボックスを外すフラグ（`--dangerously-bypass-approvals-and-sandbox`）も足します。
- 新しい会話は、その場所で最後に使われたログインで始めます。分からなければ、一覧の既定のログインです。
- 会話がどのログインで動いているかは、会話が使っている `CODEX_HOME` と、一覧の `codex_home` を照らして見分けます。見分けられない会話には、ログインを順に試します。その会話を知っているログインだけが、届けられるためです。

新しい会話の出力は、通知アプリの状態のディレクトリーの `waits/<HのID>.log` に残ります。

## 別の会話へ依頼する（`lacia tell`）

`lacia tell` は、指定した会話へ仕事を渡す申し送りです。ローカル環境のサーバーの会話へ渡すときは、プロファイルを指定しなければ `local-claude` や `local-codex` が宛先です。別の環境で使う場合は、サーバー自身か、登録した端末の会話を選びます。

```
lacia tell --task T1067 --to local-claude "コピーを復旧してください。手順は local/T1067/brief.md にあります。"
```

- `--to local-claude` のように、会話の名前で届ける先を選びます。場所だけなら、その場所の既定の種類です。種類だけを書くと、`local` という場所でその種類が使えれば優先し、なければサーバーの同じ種類へ届けます。省くと、Claude Code からは Codex へ、Codex からは Claude Code へ届けます。
- 依頼は、タスクの履歴に残ります。登録した端末を宛先にした場合は、端末の `lacia agent` が、30秒ほどで届けます。
- 送った側は `lacia wait show <HのID>` で、相手が受け取りを知らせたかどうかを確かめます。受け取った会話が担当になる条件は、[続きの会話がすること](#続きの会話がすること)にあります。
- 20分たっても受け取りの知らせがなければ、遅れを履歴と一覧に出します。オーナーさんの操作が必要なことが分かっている場合は、`--owner-action "Macで仕事用のアカウントにログインしてください。"` のように具体的な操作を指定できます。
- 外部への送信や共有の許可は、この依頼では、別の会話へ渡せません。

## 重ならないための作り

- 同じタスクの同じ対象を、開いているあいだにもう1度登録しても、待ちは増えません。
- 終了は、1度だけ記録されます。あとから届いた報告は、結果を変えません。
- 続きを始められるのは、1度だけです。サーバーが、最初の1つだけを受け付けます。
- 受け取りの遅れと期限切れは、それぞれ1度ずつ記録します。確認待ちへ出すのは最初の1度です。

## 版を切り替えるとき

旧版の待ちから、新しいWとHへの移行はしません。新版は、旧形式の閉じた待ちを読み込みません。旧形式の有効な待ちが残っていれば、起動時にエラーにして止まります。閉じた旧記録は消さずに残せますが、新しい一覧には出ません。

切り替えの前に、旧形式の有効な待ちと、相手がまだ受け取っていない依頼がないことを確かめます。そのうえで、サーバーと各端末のCLIを同じ版へ入れ替えます。`lacia agent` で申し送りを受ける場合は、それも合わせます。

## 会話の名前と担当

サーバーは、`lacia` コマンドを呼んだ会話を見分けて、名前を付けます。進行中のタスクを、どの会話が進めているのかが、分かるようにするためです。

**名前**は、動いている場所と、種類の組み合わせです。`local-claude`、`work-codex` のようになります。

- 種類は、`codex` か `claude` です。`lacia` コマンドが、自分の親のプロセスを順にたどって、最初に見つかった Codex か Claude Code を、呼び出した会話とします。Codex と Claude Code は互いを呼び出すので、環境変数だけでは、どちらが呼んだのかが分からないためです。
- 場所は、サーバーのプロファイル名か、導入先で別の端末に付けた場所の名前です。会話では環境変数 `LACIA_PROFILE` から読みます。なければ `local` です。
- 同じ名前の会話が同時にあるときは、あとから来た会話に、`local-claude 2` のように番号が付きます。

`lacia busy` は、サーバーを起動し直す前に使います。処理中の依頼と、この数分にコマンドを使ったほかの会話を並べて、1つでもあれば失敗で終わります。起動し直すあいだは、ほかの会話のコマンドが失敗するためです。数える時間は、`--within` で変えられます（既定は5分です）。

監督プロセスが正常終了のあとに起動し直す環境では、`lacia restart --when-idle` を実行すると、再起動を予約できます。コマンドは、`lacia busy` と同じ経路で稼働中のサーバーへ頼み、サーバーが自分の状態ディレクトリーに予約を残します。そのため、頼む側は、状態ディレクトリーの場所も、実行ファイルを置き換える前か後かも、気にしなくて済みます。予約に対応する前の版のサーバーは、対応していないと答えます。再起動の前後で同じアドレスとポートを使う構成を前提とします。受付済みの依頼を保存したまま、新しい会話の開始と別端末での定期実行の開始を待たせます。処理中の依頼、別端末の定期実行、夜の書き直しが終わり、HTTPの着信が途切れてから、監督プロセスに再起動を任せます。ファイル移行中の停止を解除する操作ではありません。

CLIは既存の待ち時間の範囲で、TCPの接続が拒否された場合に接続だけをやり直します。サーバーに送った操作については、応答が切れたりプロキシーがエラーを返したりしても、ほかの操作として送り直さず、必要なら保存先を読み戻します。

**台帳**は、サーバーの `state` のディレクトリーの `sessions.json` です。コマンドが、見分けた結果を、要求のヘッダー（`X-Lacia-Caller`）で送ります。30日のあいだ記録のない会話は、台帳から消します。Git には入りません。

**担当**は、`task.md` の `owner` と `owner_session` です。

- 担当が決まっていないタスクでは、サーバーが `lacia task set <ID> doing` を実行した会話を特定できると、その会話が担当になります。
- 状態が進行中でなくなると、担当は消えます。Web のボタンで進行中にしたときは、担当は入りません。
- 担当と違う会話が状態や項目を変えたり、履歴に書いたりするときは、コマンドが注意書きを出します。`lacia task set <ID> doing` は注意を出すだけで、元の担当を保ちます。項目の変更や履歴への追記は、注意が出ても記録されます。
- 担当を引き継ぐ会話は `lacia task claim <ID>` を使います。履歴に、だれからだれへ替わったのかが残ります。

`lacia who` と、Web の「会話」のページ（`/who`）には、この12時間にコマンドを使った会話と、進行中のタスクを受け持っている会話が並びます。

## 作っていないもの

- 申し送りは、動いている Codex の会話へ届けられます。閉じた会話を再開する機能はありません。
- Job の終了は、端末が確かめます。端末のスリープ中に Job が終わっても、サーバーへ直接知らせる仕組みはありません。
- プルリクエストの CI や、任意のコマンドの終了を待つ機能はありません。
- プロセスが動いているかは、続きを届けるときに端末で確かめます。終了した時点では台帳に反映されません。

## まだ確かめていないこと

- すでに終わった Job で、一連の動きを確かめました。動いている Job の終了を待つ場合と、`lacia job run` で Job を投入する場合は、まだ確かめていません。
- 端末がスリープしているあいだに Job が終わったときの動きも、まだ確かめていません。
