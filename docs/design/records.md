# 記録のリポジトリー

タスク、記憶、定期タスクの定義と履歴は、オーナーさんごとの Git リポジトリーに置きます。これを「記録のリポジトリー」と呼びます。

`lacia` は `--root` で指定した記録を開きます。指定がなければ環境変数 `LACIA_TASKS` を使い、それもなければ、いまのディレクトリーから親へたどって記録を探します。

## 全体の形

```
.lacia/
  config.json               形式の版、領域、ID の頭文字、呼び名など
  serve.conf                サーバーの設定のうち、記録の側に置けるもの
  calendars.json            読むカレンダーの一覧（あれば）
  calendar-overrides.json   予定の表示の上書き（あれば）
  id-map.tsv                古い ID との対応（あれば）
  source/lacia/             コードを直しながら使うときの、コードのクローン（あれば）。Git には入れません
AGENTS.md  CLAUDE.md        会話への案内
README.md
TODO.md                     サーバーが作る一覧
rules/                      各自の決まり
memory/                     長く使う記憶。now.md（いまの状況）、self.md（わたしのこと）など
log/<種類>/<YYYY-MM>/<YYYY-MM-DD>.md   日ごとの記録
areas/
  work/
    tasks/2026-11/T1001-web-rewrite/    タスク
    routines/S1001/                     定期タスクと実行・確認の履歴
    projects/<名前>/project.md          プロジェクト
    knowledge/                          知識
    procedures/                         手順
    memo.md                             タスクを持たない記録の覚え書き（あれば）
  personal/
    tasks/ ...
scripts/                    複数の仕事で使う、各自が管理するスクリプト（あれば）
archive/                    凍結した以前の記録（あれば）
local/                      作業用。Git には入れません
```

`work` と `personal` は「領域」です。領域の名前は、設定で変えられます。領域のディレクトリーは、必ず `areas/` の直下に置きます。関連する説明は、[わたしのこと](self.md)と[決まりと会話の起動](rules.md)にあります。

- `lacia` が読み書きする最上位の名前は、`.lacia`、`AGENTS.md`、`CLAUDE.md`、`README.md`、`TODO.md`、`rules`、`memory`、`log`、`areas`、`archive`、`local` です。形式1までの記録では `routines/` と `schedules/` も使います。これ以外の最上位の名前は、導入先が管理します。
- 複数の仕事で使うスクリプトは、記録の最上位の `scripts/` に置けます。導入先が管理する場所です。特定の定期タスクだけで使うものは、その定期タスクの `scripts/` に置きます。
- `archive/` は、`lacia` が読まず、書かない場所です。点検も、リンクの確認も、ここを対象にしません。
- `.gitignore` には、少なくとも `/local/`、`/.lacia/source/`、`/areas/*/tasks/*/*/files/` を書きます。形式2では、定期タスクの大きな添付を外すために `/areas/*/routines/*/files/` も書きます。`/.lacia/source/` は、コードのクローンを置くときのためです（[README の「コードを直しながら使う」](../../README.md#コードを直しながら使う)）。この行がないと、サーバーの自動保存（`git add --all`）が、クローンを入れ子のリポジトリーとして記録に取り込んでしまいます。

## 記録の形式

記録のリポジトリーの形には、版があります。設定の `format` で決まります。

| 版 | 形 |
| --- | --- |
| 0 | 以前の形です。`format` がないときも、0です。領域を最上位に置き（`work/tasks/…`）、履歴を `log.md` に1行ずつ書きます。古い ID の対応は `migration/id-map.tsv` にあります |
| 1 | 領域を `areas/` の下に置き、履歴を `log.jsonl` に書きます。定期タスクは最上位の `routines/` です |
| 2 | 定期タスクも `areas/<領域>/routines/<ID>/` に置きます。定義の `area` はディレクトリー名で決まります |

設定された版に実行ファイルがまだ対応していなければ、`lacia` は起動を止めて更新を案内します。

サーバーの起動、会話の起動、記録の初期設定、タスクの操作、プロジェクトへの追記には形式2が必要です。形式0か形式1の記録を開くと、書き込みを始める前に移行方法を案内します。`lacia doctor` は旧形式をそのまま点検できます。移行の試行、本番の移行、移行後の操作と診断、`migrate --undo` は、同じ実行ファイルで行えます。

形式0のタスクは、`ReadLegacyTasks` で値と読み取り時の問題を取り出します。移行には `AreaDir(format)`、形式0の設定やプロジェクトの読み取り、履歴の変換、元に戻す記録も使います。旧本文を点検する関数は、元の本文を保った移行と診断に使います。形式0で `lacia doctor` を実行すると、タスク、予約、無視するファイル、指定した場合はリンクを読み取り専用で確かめ、移行を案内します。

会話が埋め込みの決まりを読むかどうかは、[記録の `AGENTS.md`](rules.md#決まりを自分で持つリポジトリー)で決まります。埋め込みの決まりでは、現行の形式2の置き場所を案内します。

## 形を移す（`lacia migrate`）

```
lacia migrate [--root DIR] [--moves FILE] [--dry-run]
lacia migrate --undo [--root DIR]
```

記録を次の形式に移します。形式0からは形式1、形式1からは形式2です。コミットはしません。結果を確かめてから、実行した人が `git add -A` をしてコミットします。

- 書き始める前に、すべてを計画して、検査します。履歴の変換と照合も、先にメモリーの上で行います。1つでも問題があれば、何も書かずに止まります。
- 移行は、対応している次の形式がある、書き込める記録で行います。先に `git status --short` が空で、サーバーが動いていないこと（`.git/lacia-server` がないこと）を確かめます。`local/migrate-journal.jsonl` が残っていないことも確かめます。
- 行ったことを、1つずつ `local/migrate-journal.jsonl` に書き残します。動かした、消した、作った、書き換えた、の4種類を、もとに戻せるだけの中身と一緒に残します。
- `--undo` は、書き残した記録を逆にたどって、もとに戻します。Git に入っていない `files/` も戻します。途中で失敗したときも、コミットしたあとでも使えます。最後に、Git の索引を `HEAD` にそろえます。
- 続きからのやり直しは、しません。途中で失敗したら、`--undo` で戻して、原因を直してから、最初からやり直します。
- `--dry-run` は、計画と検査だけを行い、結果の数と、人が見るべきものの一覧を出します。何も書きません。
- 形式0から形式2へ進むときは、形式1へ移した結果を確かめてコミットし、最初の移行ジャーナルを `local/` の別名に退避してから、次の移行を実行します。

形式2では、定期タスクのディレクトリーを領域の下へ移し、定義に書いた `area` を外します。固定ID、実行時刻、実行先、停止の状態、実行と確認の履歴を引き継ぎます。Markdownのリンクと、現在使う文書に書かれた旧パスを合わせて直し、以前の対応表は `archive/routine-migration-map.json` に移します。形式2へ移す前に、すべてのサーバーと端末で対応版を使えることを確かめます。 `schedules/<名前>.md` に旧定義が残っている場合は、先に[以前の移行手順](routine-migration.md)で固定IDへ移します。

形式0から形式1へ移すときは、次の順です。

| 順 | すること |
| --- | --- |
| 追加の移動 | `--moves` のファイルを読みます。1行が「もとの場所、タブ、新しい場所」です。新しい場所が `-` の行は、消します。場所は、形式0での場所で書きます。空の行と `#` で始まる行は、読み飛ばします。行き先に、領域の中は書けません |
| 領域 | 設定の領域ごとに、`<領域>` を `areas/<領域>` へ動かします。Git に入っていない `files/` も、一緒に動きます |
| 仕組みのファイル | `migration/id-map.tsv` を `.lacia/id-map.tsv` へ、既定の場所の予定の表示の上書きを `.lacia/calendar-overrides.json` へ動かします |
| リンクと場所の書き方 | Markdown の相対リンクを、動かした先に合わせて計算し直します。リポジトリーの最上位からの場所として書かれた文字（`work/tasks/…` など）も、動かした先に書き換えます。履歴と、タスクの成果物の中は、リンクだけを直します。`archive/` の中は直しません。消したファイルを指すものは、そのまま残して、結果に出します |
| 履歴 | タスクとプロジェクトの `log.md` を、`log.jsonl` にします。日時のある行は1件の出来事に、形の決まっていない部分は `legacy` の出来事にします。文は1字も変えません。もとの文と照合して、合わなければ止まります |
| 見出し | `task.md` の「見ていただくもの」を「いまの資料」に、`project.md` の「目的」「方針」「順序」を「めざすこと」「進め方」「取りかかる順」にします。コードの囲みの中は変えません |
| `.gitignore` と設定 | `files/` を外す行を `/areas/*/tasks/*/*/files/` にし、`/local/` と `/.lacia/source/` がなければ足します。設定に `"format": 1` と、なければ `"timezone": "Asia/Tokyo"` を書きます。ほかの項目と並びは変えません |
| 片づけ | 空になったディレクトリーを消し、`TODO.md` を作り直します |

## 形を点検する（`lacia doctor`）

`lacia doctor [--root DIR] [--links] [--state DIR]` は、記録の形を確かめて、結果を出します。直しません。誤りがあれば、失敗で終わります。

この端末にある作業用ファイルの容量は、`lacia doctor local --root DIR` で点検します。`DIR` は記録のリポジトリーです。読み取り専用の記録コピーでも使えます。定期タスクから読むときは `--json` を付けます。

対象は指定した記録の `local/` です。見かけのファイルサイズではなく、ファイルシステムが割り当てたバイト数を集計します。同じハードリンクは1度だけ数え、シンボリックリンクの行き先はたどりません。上限は既定で10 GiBです。`.lacia/local-storage.json` の `limit_gib` で、記録ごとに変えられます。読めなかった場所があれば `complete` を `false` にし、非ゼロで終わります。測った値は点検の材料です。ファイルの削除や通知は行いません。

次のどれかに当たると、`lacia doctor` は誤りを知らせます。形式0の記録では、タスクや予約の定義を読めるかなど、以前の形式にも当てはまる項目を確かめます。

- 形式1か2で、領域の名前や置き場所が設定と食い違っています。たとえば、最上位に設定の領域と同名のディレクトリーがある場合、`areas/` の直下に設定した領域がない場合、設定にない領域がある場合です。領域の名前が `lacia` の使う最上位の名前と重なった場合も知らせます。
- `task.md` を読み取れないか、ID とディレクトリー名が合わないか、同じ ID が2つあります。
- タスクのディレクトリーに `task.md`、`notes.md`、`log.jsonl`、`artifacts/`、`files/` 以外のものがあります。以前の `log.md` が残っている場合も知らせます。
- `log.jsonl` に、JSON として読めない行や、`at` か `type` のない行があります。
- `projects/` の下に、`project.md` のないディレクトリーがあります。
- 定期タスクの定義を読み取れません。形式2では、最上位に `routines/` や `schedules/` の旧定義が残っている場合も知らせます。
- 形式2の `areas/<領域>/routines/` の直下に、`routine.md` がある定期タスクのディレクトリー以外のものがあります。定期タスクのディレクトリーに[定期タスク](#定期タスク)の表にない名前がある場合も知らせます。

次の項目は、お知らせとして表示します。

- 形式1か2では、最上位の `scripts/` など、導入先が管理する名前を一覧に出します。スクリプトの中身は点検しません。
- `.gitignore` に、`/local/`、`/.lacia/source/`、`files/` を外す行が足りなければ、そのことを知らせます。形式2では、定期タスクの `files/` の行も確かめます。
- タスクを持たない記録に、閉じていないタスク、`TODO.md`、通常タスクを作る定期タスク（`output: task`）があれば知らせます。覚え書きは通常のMarkdownです。`--links` で相対リンクを点検できます。
- `--links` を付けると、`archive/` と `local/` 以外の Markdown で、リポジトリー内を指す相対リンクを調べます。リンク先がないものの数と、最初の20件を出します。

`doctor` と `task lint` は、未完了のタスクについて、次の状態と条件の組み合わせもお知らせとして出します。状態は変えず、これだけでは失敗にしません。

- 確認待ちか完了確認待ちなのに、`resume_on` が先の日時を指しています。
- `after` で待つ相手が未着手で、`resume_on`、`review_at`、`on_ready` の指定がありません。手動で着手する予定もあるため、着手の仕方を確かめる案内にとどめます。
- `--state DIR` で、この記録を使う `serve` と同じ状態ディレクトリーを指定したときは、進行中のタスクの担当会話について、最後のコマンド利用の記録が12時間以上前なら知らせます。期間は会話一覧と同じです。会話が終了した、作業が止まった、とは判定しません。

会話の点検は、指定した `sessions.json` を1度読むだけで、サーバーへ問い合わせません。指定がないときや、担当の会話の記録がないときは、その会話の活動について知らせません。明示した記録を読めないときはコマンドが失敗します。別のサーバーの記録を混ぜないように、`--root` から状態の場所を推測しません。Macのコピーのタスク履歴や更新時刻は、会話の活動の根拠に使いません。

## 定期タスク

形式2では、1件を `areas/<領域>/routines/<ID>/` に置きます。たとえば、仕事の定期タスク S1001 は `areas/work/routines/S1001/` です。定義の `id` はディレクトリー名とそろえます。領域は置き場所で決まり、定義に `area` を書かずに済みます。

定期タスクのIDは記録のリポジトリー全体で一意です。ひな形に付属する定期タスクには `S0001` から `S0999` を使います。利用者が初めて定期タスクを作るときは `S1001` を選びます。2件目からは、すべての領域で使っている `S1001` 以降の最大番号に1を足します。すでに運用している定期タスクのIDはそのまま使います。

| 名前 | 中身 |
| --- | --- |
| `routine.md` | 実行時刻などの設定と、実行のたびに会話へ渡す本文です |
| `task.md`、`notes.md` | 定期タスクのタスクです。いま何をすべきかを、通常のタスクと同じ形で書きます（[定期タスクのタスク](#定期タスクのタスク)） |
| `procedure.md` | 詳しい手順を、必要に応じて本文に添えます |
| `artifacts/`、`files/` | タスクの成果物と添付資料を置きます。大きなファイルは、Gitから除外する `files/` に置きます |
| `scripts/` | この定期タスクだけで使うスクリプトを置きます |
| `log.jsonl` | タスクの履歴と、定義の変更の経緯です。通常のタスクと同じ形で、`lacia task note` と `lacia task log` で読み書きします |
| `ledger.json` | 導入先が必要に応じて置く台帳です |
| `runs/<YYYY-MM>/runs.jsonl` | サーバーが予定日時、実行結果などを月ごとに記録します |
| `runs/<YYYY-MM>/reviews.jsonl` | サーバーが受付、通知、確認の記録を月ごとに残します |

受付が確認済みかどうかは `reviews.jsonl` から求めます。受付の状態を書いた別の `state.json` を、定期タスクのディレクトリーに置く必要はありません。Webの「定期タスク」で実行と受付をたどれます。定義の各項目と受付の動きは、[定期タスクと予約](schedules.md)にあります。

### 定期タスクのタスク

定期タスクのディレクトリーに `task.md` を置くと、その定期タスクで次にすることを書いておけます。サーバーは、各回の報告から受付を作り、分析結果をそこに保存します。会話は `lacia rules tasks` の書式でタスクの本文を書きます。実行結果の用件を自動で集めるときは、サーバーが集め先の本文にある「実行から分かった対応」を更新します。集める条件は、[受付と、定期タスクのタスク](schedules.md#受付と定期タスクのタスク)で説明しています。

- 冒頭の項目は `id`、`status`、`created` の3つです。題名は `routine.md` の `title` を使い、重ねて書きません。
- 状態は、進行中（`doing`）、待機（`waiting`）、確認待ち（`review`）のどれかです。定期タスクは続いていくので、完了や取りやめにはしません。止めるときは `routine.md` の `enabled: false` を使います。ほかの冒頭の項目（`after`、`resume_on` など）は持ちません。
- 読み書きには、通常のタスクと同じコマンド（`lacia task show`、`write`、`set`、`claim`、`note`、`attach`、`log`、`lint`）を、定期タスクのIDで使います。最初の `lacia task write S1001 task.md <ファイル>` で、サーバーが冒頭の項目を補って作ります。状態は待機から始まります。`notes.md` は、`task.md` を作ってから書けます。
- タスクの一覧（`lacia task list`、Webの「タスク」、`TODO.md`）には載せません。親のタスク（`parent`）や待つタスク（`after`）にも指定できません。定期タスクの次の実行を待つときは、これまでどおり `after_run` を使います。
- Webでは、定期タスクのページの最上部に出ます。`/tasks/S1001` を開くと、定期タスクのページへ移ります。
- 形式1までの記録では使えません。

## タスクを持たない記録の覚え書き

`"tasks": false` の記録では、返事や選択を待っていること、あとで行うと約束した作業を、覚え書きに残します。記録の決まりに置き場所があれば従い、なければ `areas/<領域>/memo.md` を使います。覚え書きは会話が読み書きする文書です。日付を添えても、サーバーの実行予約や通知は作られません。

## タスク

タスクは、1件が1つのディレクトリーです。場所は `areas/<領域>/tasks/<作成した年月>/<ID>-<短い名前>/` です。短い名前は、なくても構いません。完了しても、場所は動かしません。リンクが切れないようにするためです。

| ファイル | 中身 |
| --- | --- |
| `task.md` | 「ひとことで」に続いて、タスクを作ったわけ、次にすること、今回したこと、いまの状況と資料を書きます。人も会話も、最初はこのファイルだけを読みます |
| `notes.md` | 完了の条件、許可の範囲、決まったことや背景を補うときに作ります |
| `log.jsonl` | 履歴を追記していきます。経緯をたどるときに読みます |
| `artifacts/` | オーナーさんに見ていただく成果物を置きます。Git に入ります |
| `files/` | 大きな成果物を置きます。Git には入れません |

ふだん読むファイルを小さくするために、いまの状況と、履歴と、補足を、別のファイルに分けています。タスクのディレクトリーには、この5つ以外を置きません。

### `task.md`

冒頭に機械が読む項目を置き、そのあとに文章を書きます。次は、説明のために作った例です。

```markdown
---
id: T1001
title: 予定の画面に祝日を出す
status: review
created: 2026-11-12
---

## ひとことで

予定の画面に、祝日の名前を出すタスクです。作り終えて、見え方の確認を待っています。

## このタスクを作ったわけ

日付だけでは祝日が分からず、予定を決めにくいことがありました。カレンダーを見比べずに予定を決められるようにします。

## 次にすること
```

| `due`、`priority` | 期限と優先度です。要るときだけ書きます |
| `resume_on` | この日時までタスクを待機にします。繰り返しの確認を登録したタスクでは、次の確認の日時です |
| `review_at` | この日時を条件に加えます。`review_at` の指定だけでは、タスクは待機になりません |

| `after_run` | 指定した定期タスクの、設定より後の回が実行を終えるまで待ちます |
| `after_run_since` | サーバーやコマンドが `after_run` と一緒に書く設定時刻です |

| `recheck_every` | 外部の変化を確かめる間隔です。`1d`（毎日）や `3h` のように、日か時間で書きます |
| `recheck_until` | 確認を続ける期限です。この日時が来ると、サーバーが確認待ちへ出します |
| `recheck_asked` | サーバーが確認を頼んで、まだ結果が残っていない回の日時です |
| `recheck_missed` | 結果が残らなかった回と、確かめられなかった回が、続いている回数です |
| `recheck_last` | 最後に「変化なし」と確かめられた日時です |
| `ready_since` | 条件がそろって、サーバーが確認待ちへ出した日時です |
| `stopped_at` | 同じ書き込みの繰り返しを、サーバーが止めた日時です |
| `owner`、`owner_session` | 進行中のタスクを進めている会話です |

必須は、最初の4つだけです。`id` から `created` までと、`done`、`ready_since`、`stopped_at`、`owner`、`owner_session`、`recheck_` で始まる項目は、サーバーとコマンドが書きます。冒頭の項目を手で書き換えずに、`lacia task set` や `lacia task field` を使います。サーバーと会話が、同じ箇所を同時に書き換えないようにするためです。

本文の見出しは、「ひとことで」「このタスクを作ったわけ」「次にすること」「今回したこと」「いまの状況」「いまの資料」の6つです。この順に置き、段はすべて `## ` にします。書き方は、埋め込みの決まり（`lacia rules tasks`）にあります。

- 新しいタスクの最初の本文は、「ひとことで」と「次にすること」の2つで、中身は「（まだ書かれていません）」です。サーバーが依頼や引き継ぎから作るタスクも、「ひとことで」から始めます。
- 一覧と通知は、「次にすること」の最初の段落を読みます。
- 「このタスクを作ったわけ」は、きっかけと解決したい困りごとを1〜3文で書きます。書くときは「ひとことで」の直後、「次にすること」の前に置きます。用件が明らかな小さなタスクでは省略できます。細かな前提と許可は補足へ、日ごとの経過は履歴へ置きます。新規タスクから使い、既存では背景がないと判断しにくい確認待ちを優先します。ほかの未完了タスクは次の本文更新で整え、重複する背景はこの節へまとめます。
- `lacia task lint` は、6つの見出しだけを受け付けます。「ひとことで」か「いまの状況」のどちらかがあれば、要る節があると見なします。形式1へ移す前からあるタスクには「ひとことで」がないためです。
- 本文は、100行までを目安にします。超えると、`lacia task lint` が知らせます。
- 移行前の形式0では、「いまの状況」「次にすること」「見ていただくもの」の3つを使い、「いまの状況」から書き始めていました。

### 状態

状態は、いまだれの番なのかを表します。

| 状態 | 意味 |
| --- | --- |
| `todo` | まだ着手していません |
| `doing` | レイシアが進めています |
| `waiting` | 日時、依存先のタスク、外部の処理、ほかの人の返事などを待っています |
| `review` | オーナーさんの判断、回答、操作を待っています |
| `closing` | 作業は終わっていて、オーナーさんに、これで完了にしてよいかを確かめていただくのを待っています |
| `done` | 完了しました |
| `cancelled` | 取りやめました |

状態を変えると、サーバーが履歴に1件を書きます。状態の移り方に、コードの制限は1つだけあります。`waiting` へ変えるときは、戻る条件が要ります（[外部待ちには条件が要る](#外部待ちには条件が要る)）。ほかは、どの状態からどの状態へも変えられます。

オーナーさんの番を表す状態は、`review`（表示は「確認待ち」）と `closing`（表示は「完了確認待ち」）の2つです。作業を終えたレイシアが、お願いすることに合わせて選びます。判断、回答、操作のお願いが残るときは `review`、お願いが「これで完了にしてよいか」の確認だけのときは `closing` です。選び方は、決まり（`lacia rules core` の「状態」）にあります。

- ホームでは、`review` を「要対応」に、`closing` をそのすぐ下の「完了確認待ち」に分けて出します。どちらの行にも、「次にすること」の最初の段落を出します。「完了確認待ち」の行には「完了にする」のボタンがあり、ホームから離れずに、その1件を完了にできます。押した直後の案内には「取り消す」が出て、完了確認待ちへ戻せます。
- `closing` のタスクに依頼が届くと、ほかの状態と同じく、サーバーが進行中に変えます。記録だけを直す依頼（`status_policy` が `keep`）では、状態を保ちます。
- サーバーがタスクを `closing` にすることはありません。条件がそろったとき、待ちや申し送りの結果を出すとき、同じ書き込みの繰り返しを止めたときは、`closing` のタスクも `review` へ移します。オーナーさんに読んでいただく新しい用件ができたためです。
- ほかのタスクの完了を待つ指定（`after`）が残っていても、`review` と `closing` のタスクは「待機」へ回しません。先の `resume_on` があるときは、どちらも「待機」に出します。
- この状態を知らない版の実行ファイルは、`closing` のタスクを読めず、読めないタスクとして一覧から外します。記録を読むすべての実行ファイルを新しい版にしてから、使い始めます。

ホームとタスク一覧では、着手の日時や依存先のタスクを表示します。作業が止まり条件を待つ `waiting` は「待機」に出し、監視で処理が実行中と分かったタスクは「進行中」に残します。監視対象に入らない処理は、実行中を確かめたうえで `doing` とし、次に確かめる日時があれば `review_at` に書きます。

担当が決まっておらず、ひも付く依頼が会話の順番を待っているときは、そのことを表示して「待機」に出します。実行中の依頼があるときは、順番待ちの表示は出ません。記録だけの依頼はこの判定から外します。一覧での表示は、タスクに保存した状態や、着手の条件がそろったときの動作を書き換えません。

### ID

新しいタスクの ID は、頭文字1つと通し番号です。既定では `T1001` から始まります。頭文字は、設定の `id_prefix` で変えられます。

- 次の番号は、リポジトリーにある同じ頭文字のいちばん大きい番号から求めます。台帳のファイルは持ちません。
- 番号を決めるのは、サーバーか、サーバーがないときのコマンドです。会話は、自分で番号を決めてディレクトリーを作りません。
- ID に意味は持たせていません。どの領域のタスクかは、置き場所で決まります。
- `.lacia/id-map.tsv` に「古い ID、タブ、新しい ID」を1行ずつ書くと、古い ID でも同じタスクを開けます。形式0では、`migration/id-map.tsv` です。

### 条件がそろったら、確認待ちへ出すか、着手する

日時やほかのタスク、定期タスクの実行を待つときは、条件（`resume_on`、`review_at`、`after`、`after_run`）を指定します。条件がそろったらレイシアに着手してほしい場合は、`on_ready` も指定します。

サーバーはファイルの変更を取り込むたびに（既定は10秒ごと）、条件がすべてそろったかを確かめます。停止中に過ぎた日時は、再起動後に扱います。条件がそろえば該当する項目を消し、履歴に理由を残します。

```sh
lacia task field T1001 after_run S1001
```

`after_run` は、設定時刻より後に予定された回のうち、実行が終了した記録を待ちます。定期タスクが端末で実行された場合も、サーバーが受け取った同じ実行履歴を使います。結果が成功や新着0件なら、ほかの条件がそろったあとに `on_ready` に従います。失敗や一部未確認で終わった回では、要対応に出してその結果を確認できるようにします。見送りや未実行が記録された回では待ち続けます。`after_run` は1回分の条件です。待機を解くときに、どの回を見たのかを履歴に残します。

`on_ready` がなければ、タスクを確認待ち（`review`）にします。このとき確認待ちに変わったタスクには `ready_since` に日時が入り、画面に「着手を頼む」のボタンが出ます。

`on_ready` に `start` と書いたタスクは、条件がそろうと、サーバーが「着手を頼む」のボタンと同じ依頼を、窓口の会話へ出します。宛先を選ぶときは、`start local-codex` のように値に続けます。場所だけを書くと、その場所の既定の種類です。

```sh
lacia task field T1001 on_ready "start local-codex"
```

サーバーの会話が着手の依頼を受け付けると、タスクは進行中（`doing`）になります。宛先が別の端末なら、[申し送り](waits.md#続きの会話がすること)として届け、そちらの会話が受け取りを知らせたときに進行中になります。`on_ready` は条件がそろった時点で消えます。

- 依頼の文章は決まった形で、タスクのことは書いてありません。会話は、`task.md` の「次にすること」と `notes.md` を読んで進めます。そのときにすること、許可の範囲、止める条件は、条件を決めるときに、そこへ書いておきます。
- 依頼を出せなかったとき（依頼を受け付けないサーバーなど）は、理由を履歴に残して、確認待ちへ出します。
- 1回だけ行う仕事のための予約（`schedules/` の `at`）は、この形に置き換えて、なくしました。日時とすることが2か所に分かれ、同じ日時を両方に登録する必要があったためです。

### 外部の変化を繰り返し確かめる

プルリクエストの取り込み、Issue への返事、審査の結果のように、外部の変化を待つタスクは、変化があるまで何度か確かめることになります。このときは、タスクに確認の間隔と期限を登録します。次の確認の日時は、サーバーが入れます。

```sh
lacia task recheck T1001 --every 1d --until 2027-01-15 --next "2026-11-28 09:00"
```

- `--every` は間隔です。`1d`（毎日）や `3h` のように、日（`d`）か時間（`h`）で書きます。1時間より短くはできません。確認は1回ごとに会話を1つ使うので、ふだんは `1d` にします。
- `--until` は期限です。必ず指定します。期限が来ると、サーバーが確認を止めて、タスクを確認待ち（`review`）へ出します。待ち続けるか、やめるかを、オーナーさんに決めていただくためです。
- `--next` は最初の確認の日時です。省くと、いまから間隔1回分のあとです。毎日の確認は、ここで決めた時刻に続きます。
- 登録すると、タスクは外部待ち（`waiting`）になります。次の確認の日時は `resume_on` に入ります。Web では、タスクのページの「着手の条件」から登録できます。
- `after`、`after_run`、`review_at`、`on_ready` とは、一緒に使えません。タスクを戻すのは、次の確認の回だけにするためです。

何を確かめるのかと、何が起きたらオーナーさんにお知らせするのかは、`task.md` の「次にすること」に書きます。確認する会話は経緯を知らないので、対象の場所（URL など）と、変化と見なす条件を、そこだけで分かるように書きます。許可の範囲は `notes.md` に書きます。

次の確認の日時が来ると、サーバーは次の順に判定します。見回りは、条件を確かめるときと同じ間隔です。

1. 期限を過ぎていれば、確認の項目を消して、確認待ちへ出します。
2. 結果が残らなかった回と、確かめられなかった回が、合わせて2回続いていれば、同じく確認待ちへ出します。確認の方法を見直すためです。
3. どちらでもなければ、**先に** `resume_on` を次の回へ進めて、確認を頼んだことを履歴に残します。そのあとで、別の会話（定期タスクの `conversation: side` と同じ並び）へ確認の依頼を出します。タスクは外部待ちのままで、担当も変わりません。

次の回を先に書くのは、確認する会話が結果を残し忘れても、途中で落ちても、次の回が来るようにするためです。次の日時を入れるのを会話に任せると、入れ忘れたときに、タスクがだれにも気づかれないまま止まります。

- サーバーが止まっていたあいだに過ぎた回は、まとめて1回にします。次の回は、いまより後の、最初の回です。
- 次の回が期限を越えるときは、次の回を期限の日時にします。その日時に、上の1で確認待ちへ出ます。
- 前の回の依頼が、まだ順番待ちか処理中のときは、次の回の日時から1時間まで待ちます。それでも終わらなければ、結果が残らなかった回として数えます。
- 依頼を出せなかったとき（依頼を受け付けないサーバーなど）は、理由を履歴に残して、確認待ちへ出します。
- 依頼の ID は、タスクと回の日時から決まります。次の回を書いてから依頼を出すまでのあいだにサーバーが止まっても、同じ回の依頼は1つです。

確認の依頼の文章は、決まった形です。本文と補足を読むこと、読み取りだけで確かめること、外部への送信や書き込みをしないこと、結果を次のコマンドで残すことが書いてあります。

```sh
lacia task rechecked T1001 same "Issue を最後のページまで読み、新しいコメントはありませんでした。"
```

| 結果 | 意味 | サーバーがすること |
| --- | --- | --- |
| `same` | 確かめて、お知らせする変化がなかった | 履歴に残し、`recheck_last` に日時を入れます。続いていた回数を0に戻します。状態は変えません |
| `changed` | オーナーさんの判断や操作が要る変化があった | 確認の項目を消して、確認待ちへ出します。会話は、その前に「次にすること」へ、見ていただくものと、決めていただきたいことを書きます |
| `unknown` | 対象を読めなかった（認証切れ、通信の失敗など） | 履歴に残し、続いている回数を1つ増やします。状態は変えません。読めなかった回を、変化なしとは扱いません |

- 会話は、次の確認の日時だけを `lacia task field <ID> resume_on "日時"` で変えられます。相手が返事をする日を書いていたときなどに使います。期限より後にはできず、消すこともできません。
- タスクが外部待ちを離れると、どの経路でも、サーバーが確認の項目と `resume_on` を消して、履歴に残します。確認をやめるときは、状態を変えます。続けるときは、登録し直します。
- 一覧と `TODO.md` には、「毎日 09:00 に確認（2027-01-15 まで）」のような間隔と期限に続けて、いまの様子を出します。結果が届いたら「11/28 09:02 に確かめたときは、変化がありませんでした。」のように、確かめられた日時と結果を知らせます。初回の確認を待っているとき、前回確かめられなかったとき、依頼した回の結果を待っているときも、その状況を出します。続いて次の確認日時を知らせます。次が期限なら、その日時に「要対応」に出ることを知らせます。
- 点検（`lacia task lint`、`lacia doctor`）は、前回の確認ができなかったタスク、次の確認の予定を間隔1回分より長く過ぎたタスク、外部待ちではないのに確認の項目が残っているタスクを知らせます。
- この項目を知らない版のサーバーは、次の確認の日時を、ふつうの `resume_on` として扱います。その日時に、タスクを確認待ちへ出します。

定期タスクとの使い分けは、[定期タスクと予約](schedules.md#書き方)にあります。1つのタスクのための確認は、ここに書いた形を使い、定期タスクは作りません。

### 進めている会話

担当が決まっていないタスクに着手するときは、会話から `lacia task set <ID> doing` を実行します。サーバーがその会話を特定できると、名前を `owner` に記録し、一覧に表示します。ほかの会話が担当しているときに同じコマンドを実行すると、注意が出て、元の会話が引き続き担当します。引き継ぐときは `lacia task claim <ID>` を使います。 [会話の名前と担当](waits.md#会話の名前と担当)

### タスク画面で履歴と成果物をたどる

形式1のタスク画面には、本文の下に「これまでの資料」を畳んで出します。保存済みの `handover.body` にあって、現在の本文にはないリンクを、最後に載っていた日時と一緒に並べます。同じリンクは1件にまとめます。リンクはMarkdownの構文として読み、相対リンクは元のタスクの場所から解決します。

タスクの履歴と履歴の専用ページは、`request` ごとにまとまりを分け、新しい依頼から並べます。まとまりの中は記録された順に並べます。最初の依頼より前の記録も残し、`handover.body` は「このときの本文」から開けます。依頼原文は新しく保存しません。読み取れない行と、移行前の記録も隠しません。

`artifacts/` と `files/` の成果物には、最後の `file` の `put` に記録された日時を添え、新しい順に並べます。最後の `request` よりあとに置いたものには「今回」を付けます。Markdownの文書は最初の見出しを題名にし、見出しのないファイルにはファイル名を使います。見出しを探す範囲は先頭 64 KiB です。日時の記録がないときは「日時不明」と表示し、ファイルの更新時刻からは補いません。

ホームで最近閉じたタスクを振り返る欄には、完了と取りやめを合わせて、新しいものから8件までが出ます。

確認待ちと完了確認待ちのタスクの個別ページには、いまの状態が始まった日時を添えます。作成時からその状態だったときは `created`、状態が変わったときは `status`、`woke`、`stopped`、`recheck` を使います。履歴で確かめられないときは「日時不明」と表示します。形式0の記録も同じ表示にします。

### 履歴（`log.jsonl`）

履歴は、1行が1つの JSON のオブジェクトです。文字コードは UTF-8、改行は LF で、追記だけを行います。日本語などの文字と、`<`、`>`、`&` は、`\u` の形に変えません。文章の中の改行は、JSON の `\n` として持ちます。

どの出来事にもある項目です。

| 項目 | 要るか | 中身 |
| --- | --- | --- |
| `at` | 必ず | 日時です。秒と時差まで書きます（`2026-11-24T09:15:02+09:00`）。記録の設定の時間帯で書きます |
| `type` | 必ず | 出来事の種類です |
| `by` | あれば | 書いた会話や画面の名前です（`local-claude`、`Web` など）。サーバーが自分で書いた出来事では、省きます |
| `text` | あれば | 人が読む文です。`by` のかっこは付けません |
| `imported` | 移したものだけ | `log.md` から移した出来事に、`true` を付けます |

種類と、種類ごとの項目です。`from`、`to`、`status` の値は、`todo` などの状態の名前です。

| `type` | 書かれるとき | 種類ごとの項目 |
| --- | --- | --- |
| `created` | タスクを作ったとき | `status` |
| `status` | 状態を変えたとき。担当を決めて進行中にしたときも、これです | `from`、`to`。担当を決めたときは `owner`、`session` も |
| `claimed` | 状態を変えずに、担当だけを決めたか替えたとき | `owner`、`session`、替えたときは `previous` |
| `field` | 冒頭の項目を変えたとき | `key`、`value`（消したときは空の文字列） |
| `file` | ファイルを置いた、消した、残す指定を変えた、期限で消したとき。本文か補足を `lacia task write` で書き換えたとき | `action`（`put`、`removed`、`kept`、`unkept`、`purged`、`wrote`）。`put`、`removed`、`wrote` は `path`。`put` と `wrote` は `bytes` と `sha256`（先頭の16文字） |
| `request` | 依頼を受け付けたとき | `request`（依頼の ID）、`via`（受け付けた経路）。依頼の文面は入れません |
| `note` | 会話が `lacia task note` で書いたとき | なし |
| `woke` | サーバーが、待ちの結果や、日時や依存の条件がそろったことを記録したとき | 状態が変わったときは `from`、`to` |
| `stopped` | 繰り返しの書き込みを、サーバーが止めたとき | 状態が変わったときは `from`、`to` |
| `recheck` | 繰り返しの確認を登録したとき、サーバーが確認を頼んだとき、確認の結果を残したとき、確認を終えたとき | `action`（`registered`、`asked`、`same`、`unknown`、`changed`、`expired`、`missed`、`failed`）。状態が変わったときは `from`、`to` |
| `peer` | 相手のプロファイルとの伝言を記録するとき | なし |
| `wait` | 計算の終了を待つ仕事の登録、結果、取り消しを記録するとき | `wait`（待ちの ID） |
| `handover` | 別の会話への申し送りを預かったときや、受け取りなどの経過を記録するとき | `handover`（申し送りの ID）。待ちの結果から作ったときは `wait` も |
| `handover` | 状態が進行中からほかの状態へ変わり、そのときの本文を残すとき | `from`、`to`、`body`（そのときの `task.md` の本文。最大10万バイト） |
| `legacy` | 移行のときだけ | なし。`log.md` にあった、形の決まっていない部分を、そのまま `text` に入れます |
| `order` | プロジェクトの取りかかる順を画面で動かしたとき（プロジェクトの履歴だけ） | `task`、`direction`（`up` か `down`） |

```
{"at":"2026-11-24T09:15:02+09:00","type":"created","by":"local-claude","status":"todo","text":"タスクを作りました。状態は「未着手」です。"}
{"at":"2026-11-24T09:41:00+09:00","type":"status","by":"local-claude","from":"doing","to":"review","text":"状態を「進行中」から「確認待ち」に変えました。"}
{"at":"2026-11-24T09:41:00+09:00","type":"handover","from":"doing","to":"review","body":"## ひとことで\n\n…"}
```

- `lacia task log <ID> [--tail N]` は、1件を `- 2026-11-24 09:15 <text>（<by>）` の形で出します。移したもの（`imported`）は、`text` に以前のかっこが入っているので、`by` を重ねません。`legacy` は `text` をそのまま表示します。`handover` は、申し送りならその経過を、本文の控えなら「このときの本文を残しました。」と表示します。
- `lacia task log <ID> --json` は、行をそのまま出します。
- 知らない `type` と、知らない項目は、エラーにしません。`text` があれば、それを出します。なければ、行をそのまま出します。
- Web のタスクのページの「履歴をすべて見る」は、すべての出来事を同じ見た目で並べたページ（`/tasks/<ID>/log`）を開きます。プロジェクトも同じです（`/projects/<領域>/<名前>/log`）。

形式0の `log.md` は、移行時にだけ読みます。通常運用のタスクとプロジェクトは `log.jsonl` に書き、形式0への書き込みは行いません。

### 本文と補足を、コマンドで保存する

`lacia task write <ID> <task.md か notes.md> [ファイル]` は、`task.md` の本文か、`notes.md` の全体を、渡した中身に書き換えます。ファイルを省くか `-` と書くと、標準入力から読みます。

```sh
lacia task write T1001 task.md body.md
lacia task write T1001 notes.md < notes.md
```

記録のリポジトリーを直接編集できない会話（読み取り専用のコピーで動く会話）が、書いた文章を保存するためのコマンドです。サーバーが書き込むので、窓口の会話への依頼（`lacia ask --keep-status`）を通りません。待ち行列に並ばず、渡した文がそのまま保存されます。直接編集できる会話は、これまでどおりファイルを編集して構いません。

- `task.md` に渡すのは、本文だけです。冒頭の項目は、サーバーがいまのものを保ちます。冒頭の項目（`---` で始まる部分）が入っている中身は、保存せずに断ります。
- 状態は変えません。担当も変えません。ほかの会話が進めているタスクへ書いたときは、`lacia task note` と同じ注意書きを出します。
- 書き方に誤りがあると、サーバーは保存を断り、直す箇所を返します。`task.md` では見出しの名前、段、重複と、任意の「このタスクを作ったわけ」の位置を、共通の `task.ShapeProblems` で確かめます。CLIの直接保存、サーバーへの保存、Webの点検で同じ判定を使います。「ひとことで」は必須で、まだ閉じていないタスクでは「次にすること」も必要です。`notes.md` の1行目は `# ` で始まる題名にします。
- 文章の気になる点（`lacia task lint` が出すもののうち、上に当たらないもの）は、保存したうえで、指摘として返します。
- 改行を LF にそろえ、前後の空白を取り除いて、末尾に改行を1つ付けます。この形で 256 KiB まで保存できます。
- 履歴には、だれがどのファイルを書き換えたのかが、種類 `file`、`action` が `wrote` の出来事として残ります。この出来事には、書き換える前の本文を含めません。
- サーバーは、受け取った全文がどの版をもとにしているか確かめません。ほかの会話の修正を上書きしないよう、本文なら `lacia task show <ID>`、補足ならタスクのページか記録の `notes.md` で現在の内容を読んでから書きます。コミット済みの版は Git の履歴から戻せます。
- API は、`PUT /api/tasks/<ID>/doc?name=<task.md か notes.md>` です。本体に、中身をそのまま入れます。

### 成果物の置き場所

| 置き場所 | Git | 置くもの |
| --- | --- | --- |
| `artifacts/` | 入ります | 報告、比較表、手順など、文章が中心の小さなもの |
| `files/` | 入りません | 画像を埋め込んだ HTML や大きなデータなど、200 KiB を超えるものや、機械が作ったもの |

- `files/` は、サーバーの手元にだけあります。作り直せるものだけを置きます。記録のリポジトリーの `.gitignore` で、Git から外しておきます。
- `lacia task attach <ID> <ファイル>` で置きます。既定の置き場所は `files/` で、`--to artifacts` を付けると `artifacts/` に置きます。置いたファイルの名前と大きさは、履歴に残ります。
- 書き直していく文書（設計、計画）は、日付のない名前（`design.md`、`plan.md`）にします。その時点の記録（結果、比較、PDF）は、`<何であるか>-<YYYY-MM-DD>.<拡張子>` にします。
- `files/` の上限は、1つのファイルが 50 MiB、1つのタスクで合わせて 500 MiB です。
- タスクを閉じてから90日たつと、サーバーが `files/` を消します。残したいタスクは、タスクのページで指定します（`files/.keep` が置かれます）。
- HTML の成果物は、サーバーの画面から切り離した形（`sandbox allow-scripts`）で表示します。スクリプトは動きますが、レイシアの画面や API には触れられません。

## プロジェクト

プロジェクトは、いくつかのタスクを、めざすこと、進め方、取りかかる順と一緒にまとめたものです。`areas/<領域>/projects/<名前>/project.md` を置くと、そのディレクトリーがプロジェクトになります。`projects/` の下には、`project.md` のないディレクトリーを置きません。

```markdown
---
title: 予定の画面の作り直し
status: active
---

## めざすこと

## いまの状況

## 進め方

## 取りかかる順

1. T1001 — 表示の仕方を決める前に、祝日のデータを選びます。
2. T1002

## いまの資料
```

- タスクは、冒頭の `project: <名前>` で、プロジェクトに属します。
- 状態は `active`、`paused`、`done` の3つです。ホームに出るのは `active` だけです。
- ホームには、進行中のプロジェクトごとに、全タスクのうち何件が完了か取りやめになったかと、「次の1件」が出ます。「次の1件」は、取りかかる順に並ぶ未着手のタスクのうち、`after` の条件をすべて満たし、`resume_on` の指定がない最初のタスクです。
- 実行ファイルが読むのは、タスクの並びを書いた節だけです。形式1では「取りかかる順」を、形式0では「順序」を読みます。両方を探すことはしません。
- プロジェクトの履歴は、同じディレクトリーの `log.jsonl` です。形は、タスクの履歴と同じです。形式0では `log.md` です。会話は、`lacia project note <名前> "文章"` で書きます。読み取り専用のコピーからは、タスクの `task note` と同じく、サーバーへ送られます。

## `TODO.md`

`TODO.md` は、サーバーがタスクから作る一覧です。Web の画面を使わない読み手のためのファイルで、だれも手では編集しません。`lacia todo` で、作り直せます。

## 記録の設定（`.lacia/config.json`）

リポジトリーの形を決める設定です。ファイルがなければ、すべて既定の値になります。

```json
{
  "format": 1,
  "areas": ["work", "personal"],
  "area_labels": {"work": "仕事", "personal": "私用"},
  "id_prefix": "T",
  "user": "田中さん",
  "reviewers": ["佐藤さん"],
  "handoff_area": "work",
  "timezone": "Asia/Tokyo",
  "tasks": true
}
```

| 項目 | 既定 | 中身 |
| --- | --- | --- |
| `format` | 0 | 記録の形式の版です。上の「記録の形式」にあります |
| `areas` | `["work", "personal"]` | タスクを置く領域です。`areas/` の下のディレクトリーの名前です。形式0では、リポジトリーの直下のディレクトリーの名前です |
| `area_labels` | なし | 画面と `TODO.md` に出す、領域の表示名です。なければ、領域の名前をそのまま出します |
| `id_prefix` | `T` | 新しい ID の頭文字です。英大文字1つです |
| `user` | 「オーナーさん」 | レイシアがオーナーさんを呼ぶ名前です |
| `reviewers` | なし | オーナーさんのほかに、確認待ちのタスクの「次にすること」に名前を書ける人です |
| `handoff_area` | 下の説明 | 相手のプロファイルから引き継がれたタスクを作る領域です |
| `tasks` | `true` | タスクを持つかどうかです。`false` にすると、返事で用件を終え、続きを覚え書きに残す使い方になります。下の説明にあります |
| `calendar_hidden` | なし | 題名で表示から外す予定の規則です。書き方は、[予定の連携](calendar.md)にあります |
| `timezone` | `Asia/Tokyo` | 記録の時間帯の、IANA の名前です。予約、タスクの日付と復帰判定、一覧、履歴、日ごとのログ、予定の取得と表示に使います |

`handoff_area` がないときは、最初の領域へ作ります。

`tasks` を `false` にした記録では、決まり、会話への指示、画面、点検が、タスクを持たない使い方に切り替わります。新しいタスクを作ることと、タスクの状態を変えることはできません。以前に作ったタスクは、そのまま読めます。続きがあることは、[覚え書き](#タスクを持たない記録の覚え書き)に残します。切り替わるものの一覧は、[決まりと会話の起動](rules.md#タスクを持つ運用と持たない運用を分ける)にあります。

呼び名は、次の順で決まります。

1. 環境変数 `LACIA_USER`。`lacia serve --user 田中さん` とすると、サーバーが、自分の会話にこの環境変数を渡します。
2. `.lacia/config.json` の `user`。ふつうは、ここに書きます。
3. どちらもなければ、「オーナーさん」です。

決まりの文書、会話への指示、依頼の冒頭、画面の説明、文章の点検が、この名前を使います。確認待ちのタスクの点検（`lacia task lint`）は、「次にすること」に、呼び名か `reviewers` の名前があることを確かめます。完了確認待ちのタスクには、この点検をしません。欄の説明が、だれの番かを示すためです。

点検は、2つの状態の取り違えにも注意を出します。確認待ちでは、「次にすること」の最初の文が「ご確認いただきます」のように終わり、最初の段落に、決めていただくことや、していただくことを表す言葉がないときです。完了確認待ちでは、最初の段落に「決めて」「ご判断」のような言葉があるときです。どちらも言葉を見るだけの案内で、保存は止めません。

`lacia init` を実行すると、呼び名を尋ねて、`user` に書きます。[決まりと会話の起動](rules.md#記録の初期設定lacia-init)に説明があります。

## サーバーの設定のうち、記録の側に置けるもの（`.lacia/serve.conf`）

`lacia serve` は、記録のリポジトリーに `.lacia/serve.conf` があれば、指定がなくても読みます。書き方は、`--config` の設定ファイルと同じです。

会話は、記録のリポジトリーへ書き込めます。そのため、このファイルで指定できる設定を、プロファイルの呼び名や予定の連携などに限っています。待ち受けるアドレス、起動するコマンド、サンドボックス、プッシュなどは、指定しても読み飛ばします。制限される側が、自分で制限を緩められないようにするためです。指定できる設定の一覧は、[設定の一覧](settings.md#記録の側に置ける設定)にあります。

## Git への保存

記録のリポジトリーを Git に自動で保存する役割は、サーバーが受け持ちます。会話は、コミットもプッシュもしません。サーバーに `git-sync = true` を指定すると、自動保存が有効になります。画面の表示と記録への書き込みは、どちらの構成でも自動保存を設定する前から使えます。

- 画面に出す内容は、ファイルから直接読みます。表示は、コミットを待ちません。
- サーバーは、変更をまとめてコミットします。コミットの前に、`TODO.md` を作り直します。
- 上流（`@{upstream}`）のないリポジトリーでは、コミットだけを行います。手元だけで記録を持つ形です。
- 1つのタスクへ同じような書き込みが続いても、コミットが際限なく増えないように、タスクごとに上限があります。[安全のための仕組み](safety.md#コミットの数に上限を置く)にあります。

### 読み取り専用のコピー

ローカル環境で使う場合は、サーバーと会話で、書き込める記録を共用します。サーバーを別の環境で動かし、手元でも記録のファイルを読みたいときは、手元の端末に読み取り専用のコピーを置けます。コピーは、プッシュの宛先を `disabled://` で始まるアドレスにして、プッシュできないようにします。`lacia` のコマンドは、この設定で読み取り専用のコピーを見分けます。

- コピーでの `lacia task set` などの変更は、サーバーへ送ります。既定では、コマンドを実行する環境の `http://127.0.0.1:18190` に用意した転送先へつなぎます。別のアドレスを使う場合は `LACIA_API` に指定します。
- `task.md` の本文と `notes.md` は、`lacia task write` でサーバーへ送って保存します。[本文と補足を、コマンドで保存する](#本文と補足をコマンドで保存する)にあります。
- `lacia task show` と `lacia task list` がサーバーから読むのは、読み取り専用として設定したコピーを開いているときです。接続できない場合は、その旨を伝えてコピーの内容を表示します。書き込める記録でこれらのコマンドを実行すると、その記録から読みます。
- コピーを端末の `lacia agent` で同期する場合は、コピーのプッシュ先を `disabled://lacia-local-readonly` にします。サーバーで Git への保存とプッシュが動き、手元の端末で同じ履歴を取得できることも必要です。 [Mac の通知](notifications.md#記録のコピーを最新にする)

### 手元のサーバーを、コマンドが見つける

依頼を受け付けるサーバーは、起動のときに、記録のリポジトリーの `.git/lacia-server` へ、自分のアドレスを書きます。`.git` の下なので、コミットされません。止まるときに消します。

ローカル環境で同じ記録を使うときは、環境変数 `LACIA_API` を用意しなくても、`lacia task new` などのコマンドが書き置きを読みます。ID の採番と画面の更新が、サーバーの1か所にまとまります。サーバーの指定と書き置きがないときは、書き込める記録をコマンドが直接扱います。


### 時間帯を渡す場所

`Config.Location()` と `Store.Location()` が、記録の時間帯を返します。タスクの作成月と日付、終了日、復帰と確認の日時、履歴の表示、成果物を消す日を、この時間帯で扱います。タスクAPIには、日付だけの復帰条件を通知側でも判定できるように、計算した `Timezone` を添えます。この値は、`task.md` の冒頭には書きません。

夜の自分についての記録、日ごとのログ、Discordの1日の区切り、待ちの期限と説明、WebとCLIの日時表示にも、同じ時間帯を渡します。日時に時差が付くJSONの記録は、その瞬間を保ち、表示するときに設定した時間帯へ直します。既存の引数のない日時の補助関数は、日本時間を既定として保ちます。

## 一覧と文書の点検

ホームの状態ごとの一覧と「すべてのタスク」では、タスクIDの下に、いまの状態になってからの時間を表示します。各一覧の中では状態が変わった時刻が新しいタスクから並べます。ホームでは従来の領域ごとのまとまりを使います。作成や状態変更の履歴を使い、同じ状態のまま担当が替わったときや、メモを追記したときは、時刻を変えません。順番待ちから進行中になった場合は、状態を変えた依頼と結びつけられれば、その依頼が処理を始めた時刻を使います。起点が分からないタスクは経過時間を空欄にし、時刻が分かるタスクの後ろに並べます。

Web の青い表示は、タスクの日時と依存先、会話の順番、監視中の処理、申し送りの記録から作ります。「2026-11-26 05:00以降再開」はその日時以降に自動で着手を頼む指定です。「T1132終了後要対応」は、依存先が完了か取りやめになったあとに「要対応」へ出す指定です。日時と依存先が両方あるときは、両方がそろうことを示します。日時を2つ指定したときは、両方がそろう後の日時を表示します。進行中のタスクで確認日時がその条件を決める場合は「次の確認日時」を添えます。「次にすること」の本文は、その下で作業の内容を説明します。

待機中に再開条件を見つけられなければ「再開条件が未登録」と表示します。受領が遅れ、自動で再配信されない申し送りや、開始期限を過ぎた申し送りには、再割り当てが必要だと表示します。進行中のタスクで担当がなく、関連依頼が終わり、ほかの再開条件も見つからない場合は、状態の確認を促します。依頼が引き続き動いている場合や、タスクの状態を保つ指定で受け付けた依頼には、この表示を使いません。サーバーが生成する `TODO.md` にも同じ情報を載せます。

`lacia task lint` で待機中のタスクを点検するときも、同じ条件で知らせます。サーバーに接続している場合はサーバー上の待ちを使います。点検で `--state` を指定すると、その場所にある待ちや申し送り、依頼の状態を使います。

### 外部待ちには条件が要る

条件のない外部待ちは、だれにも気づかれないまま止まります。そのため、タスクを `waiting` にする操作は、戻る条件が登録されているときだけ受け付けます。コマンド（`lacia task set`）、Web の「待機にする」、API のどれも同じです。

条件として数えるのは、次のものです。

- 冒頭の項目の `resume_on`、`review_at`、`after`、`after_run`
- 繰り返しの確認（`lacia task recheck`）。次の確認の日時が `resume_on` に入ります
- サーバーが見張っている待ち（`lacia wait add`）と、まだ受け取られていない申し送り（`lacia tell`）

どれもないときは、理由と、条件を入れるコマンドの例を返して断ります。オーナーさんの判断や操作を待つ場合は、確認待ち（`review`）にするよう案内します。返事を待つだけで確かめる手立てがない場合は、「この日まで何もなければ要対応に出す」日時を `review_at` に入れます。

- `lacia wait add` は、待ちを登録してからタスクを外部待ちにするので、そのまま通ります。
- 会話の順番を待つ依頼や、処理中の依頼は、ここでは条件に数えません。処理中の依頼は、これからタスクを外部待ちにしようとしている、その会話自身のことが多いためです。一覧の「再開条件が未登録」の表示では、これまでどおり、依頼が動いているあいだは注意を出しません。
- 外部待ちのタスクから最後の条件を外す操作（`lacia task field <ID> resume_on` のように値を省く操作）も、同じ理由で断ります。先に状態を変えます。
- タスクを、外部待ちの状態で新しく作ることもできません。
- 定期タスクのタスクは、定期タスク自身が次の実行を決めるので、条件を求めません。
- この決まりができる前から条件なしで待っているタスクは、そのまま読み込みます。記録は書き換えず、一覧と点検に「再開条件が未登録」を出します。待ちや申し送りが終わって条件がなくなったタスクも、同じ表示で知らせます。
- サーバーを使わずにコマンドだけで動かすときは、`--state` で状態のディレクトリーを指定すると、そこにある待ちと申し送りを条件に数えます。

`lacia task list --json` は、通常の一覧と同じ絞り込みと順で、タスクの配列を出します。`--status`、`--area`、`--all` を一緒に使えます。対象がないときは `[]` です。要素の形は既存のタスクAPIと同じで、`ID`、`Title`、`Status`、`Area`、`Dir`、`Body` などを含みます。

`lacia task show <ID> --json` は、詳細APIと同じ `Dir`、`Markdown`、`Files`、`Children` を含むオブジェクトを出します。`Markdown` には冒頭の項目も含む原文が入ります。読み取り専用のコピーでは、通常表示と同じくサーバーから読み、通信できないときは標準エラーへ事情を書いてコピーを読みます。通常表示と、`task log --json` のJSON Linesの形は保ちます。

知識と手順の冒頭には、題名の `title`、読むときの `when`、更新日の `updated` を置きます。更新日は `YYYY-MM-DD` です。独自の項目は `x_` で始めます。ファイルを自動で書き換えることはありません。

```yaml
---
title: 勤務表の入力
when: 勤務表を入力するときに読みます。
updated: 2026-11-24
---
```

`lacia knowledge list` と `lacia procedures list` は、設定にある各領域の文書をパスの順に一覧にします。`--area` で領域を絞れます。入れ子に置いた手順も対象にします。`--json` の各要素は `path`、`area`、`title`、`when`、`updated` です。題名がない既存文書は、最初の `# ` の見出しを表示に使います。`when` と `updated` は、取得できた値だけを出します。

`lacia task lint` は、「ひとことで」か「このタスクを作ったわけ」が3文を超えたときと、「次にすること」の最初の段落が140字を超えたときに知らせます。「いまの資料」では、リンクが12個を超えていないか、資料の名前に「最新」のような時間とともに意味が変わる言葉がないかを確かめます。補足では、先頭の2つの見出しと、日付や「今回」を使った見出しを点検し、全体が60行を超えたときも知らせます。

形式1と2の `lacia doctor` は、まだ閉じていないタスクの本文と補足のほか、次の文書の書き方にも助言します。

| 文書 | 知らせる条件 |
| --- | --- |
| 進行中のプロジェクト | 「進め方」の箇条書きが日付から始まっています |
| 定期タスクの `routine.md` と移行前の予約の定義 | 「めざすこと」か「ふだんの状況」に内容がありません。「すること」が5行を超えたときも知らせます |
| 手順 | 「大まかな流れ」に内容がありません |
| 知識と手順 | 必要な冒頭項目がないか、更新日の書き方に誤りがあります |

独自の冒頭項目は `x_` で始めます。`doctor` は、見慣れない名前にこの接頭辞がなければ、付け方を案内します。

これらの助言が出ても、文書は保存でき、`doctor` の終了状態は変わりません。保存を断る構造上の誤りは、[本文と補足を、コマンドで保存する](#本文と補足をコマンドで保存する)で説明しています。`archive/`、タスクの成果物、閉じたタスクの本文と補足には、書き方の助言を出しません。
