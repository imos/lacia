# タスクのファイルの書き方

タスクを作るときと、タスクのファイルを書き換えるときに読みます。

ここにある形から外れると、Webの画面やほかの担当が、タスクを正しく読めなくなります。文章そのものの書き方は、`lacia rules writing` で読めます。

書き終えたら、`lacia task lint <ID>` で点検してください。形の崩れと、文章の気になる点が出ます。

## ファイルの役割

タスクは、`areas/<領域>/tasks/<作成した年月>/<ID>-<短い名前>/` のディレクトリーです。短い名前は、なくても構いません。完了しても、場所は動かしません。

| ファイル | 書く人 | 中身 |
| --- | --- | --- |
| `task.md` | 担当のレイシア | ひとことで、このタスクを作ったわけ、次にすること、今回したこと、いまの状況、いまの資料 |
| `notes.md` | 担当のレイシア | これからも守る約束ごとや背景があるときに書きます |
| `log.jsonl` | サーバーと担当のレイシア | 起きたことを1行に1件ずつ記録します。`lacia task note` で書き、`lacia task log` で読みます |
| `artifacts/` | 担当のレイシア | {{呼び名}}に見ていただく成果物 |
| `files/` | 担当のレイシア | 大きな成果物を置きます。Gitには入りません |

タスクのディレクトリーには、この5つ以外を置きません。作業用のファイルは、Gitに入れない `local/` に置きます。

## タスクを作る

`lacia task new --area work --title "題名"` で作ります。ID とディレクトリーは、コマンドが決めます。自分で番号を決めたり、ディレクトリーを作ったりしないでください。

題名は、何をするタスクなのかが分かる1行にします。略語や内部の呼び名だけの題名にしません。

## task.md

冒頭の `---` で囲まれた部分は、サーバーが読み書きする項目です。**手で書き換えないでください。** 変えるときは、次のコマンドを使います。

| 変えたいもの | コマンド |
| --- | --- |
| 状態 | `lacia task set <ID> <状態>` |
| 期限 | `lacia task field <ID> due 2026-12-01` |
| 親のタスク | `lacia task field <ID> parent T1001` |
| プロジェクト | `lacia task field <ID> project <名前>`（プロジェクトの決まりは、`lacia rules projects` で読めます） |
| 条件（日時、ほかのタスクの完了）を決めて「要対応」へ出す | 下の節を見てください |
| 題名 | `lacia task field <ID> title 新しい題名` |

各自で項目を足すときは、`x_` で始まる名前にします。`lacia` は、`x_` で始まる項目を使いません。

### ファイルを直接編集できないとき

記録のリポジトリーが読み取り専用のコピーになっている環境では、`task.md` の本文と `notes.md` を、コマンドで保存します。

```
lacia task write T1001 task.md body.md     本文を、ファイルの中身に書き換える
lacia task write T1001 notes.md notes.md   補足を、ファイルの中身に書き換える
```

- `task.md` に渡すのは、本文だけです。冒頭の項目は書きません。状態は変わりません。
- コマンドには、直したあとの全文を渡します。ほかの会話が直した箇所を上書きしないよう、先に現在の内容を読みます。タスクの本文は `lacia task show <ID>` で、補足はタスクのページか記録の `notes.md` で確かめられます。
- 見出しが決まりと違うなど、形が崩れているときは、保存されずに、直すところが出ます。文章の気になる点は、保存されたうえで出ます。出た箇所を直して、もう1度保存します。
- 作業用のファイルは、Gitに入れない `local/` に置きます。
- 成果物は、`lacia task attach <ID> <ファイル>` で置きます。小さな成果物を `artifacts/` へ置くときは、`--to artifacts` を付けます。

タスクのファイルのほかの記録（決まり、記憶、知識、手順、プロジェクトの文書）を直したいときは、記録を書き込める側の会話に頼みます。

```
lacia ask --task T1001 --keep-status "依頼の文章"
```

- `--keep-status` は、記録だけを直してもらう依頼に付けます。受け付けから終わりまで、タスクの状態が保たれます。直した内容を読み戻して確かめたあと、状態を変えるのは、頼んだ側です。実装や調査を新しく始めてもらう依頼には付けません。
- 依頼の文章も、ふだんの返事と同じ口調で、省略せずに書きます。何をどう直してほしいのかと、その理由を書きます。長い本文や表は、依頼の文章で口述せずに、タスクの成果物や本文に置いて、その場所を伝えます。
- サーバーへつながらないときは、依頼をGitに入れない場所に保存して、つながってから送ります。コピーを直接書き換えて済ませることはしません。つながらないことが作業の妨げになるときは、{{呼び名}}に伝えます。
- 届いたかどうか分からない依頼は、確かめないまま、新しい依頼として送り直しません。送り直すときは、コマンドが示した `--id` を付けて、同じ依頼として送ります。

### 条件を決めて「要対応」へ出す

タスクが日時やほかのタスクを待つときは、次の条件を使います。自動で着手する指定がなければ、すべての条件がそろったときに、サーバーがタスクを確認待ち（`review`）にします。タスクは「要対応」に出ます。通知を使う構成では、確認待ちに変わると{{呼び名}}に通知が届きます。

| したいこと | コマンド |
| --- | --- |
| 指定した日時まで待機にする | `lacia task field <ID> resume_on "2026-12-10 15:00"` |
| いまの一覧（着手待ちなど）に載せたまま、その日時に「要対応」へ出す | `lacia task field <ID> review_at "2026-12-10 15:00"` |
| 指定したタスクがすべて完了か取りやめになるまで待つ | `lacia task field <ID> after "X58, X61"` |
| 定期タスクの次の実行が終わるまで待つ | `lacia task field <ID> after_run S1001` |
| 外部の変化を、繰り返し確かめながら待つ | `lacia task recheck <ID> --every 1d --until 2026-12-31` |

- 日時は記録の `timezone` の時間帯で書きます。設定を省いたときは日本時間です。時刻を省いて `2026-12-10` と書くと、その日の0時すぎに出ます。
- 待っていたタスクが取りやめになれば、条件がそろったときに、その ID と取りやめになったことが履歴に残ります。続きのタスクがまだ必要かどうかは、{{呼び名}}が判断します。
- 条件を2つ以上書いたときは、すべてがそろったときに出ます。
- 指定を外すときは、値を付けずに `lacia task field <ID> after` のように実行します。
- 条件がそろって確認待ちに変わったタスクには、画面に「着手を頼む」が出ます。{{呼び名}}がこのボタンを押すと、レイシアに着手の依頼が届き、タスクは進行中になります。
- 条件を決めるときに、「次にすること」へ、そのときにだれが何をするのかを書いておきます。上がってきたときに、{{呼び名}}がそれを読んで判断するためです。
- 最後の行の、繰り返し確かめながら待つ形は、ほかの条件と動きが違います。下の「外部の変化を、繰り返し確かめながら待つ」に書きました。
- 外部待ち（`waiting`）にするタスクには、この表の条件か、登録した待ち（`lacia wait add`）か、まだ受け取られていない申し送り（`lacia tell`）のどれかが要ります。どれもないと、`lacia task set <ID> waiting` は理由と直し方を示して断ります。条件を先に入れてから、もう1度実行します。外部待ちのタスクから最後の条件を外すことも、同じ理由でできません。先に状態を変えます。
- 返事を待つだけで、確かめる手立てがないときは、「この日まで何もなければ要対応に出す」日時を `review_at` に入れます。その日に、{{呼び名}}に続け方を伺います。

定期タスクを待つときは、定期タスクの固定IDを `after_run` に指定します。登録した時刻より後に予定された回で、最初に終了を確認できる実行が対象です。以前の回が遅れて届いた場合と、実行を見送った場合は待ち続けます。成功や新着0件なら残りの条件と `on_ready` に従います。失敗や一部未確認なら「要対応」に出し、該当の実行結果を確認できるようにします。

#### 外部の変化を、繰り返し確かめながら待つ

プルリクエストの取り込み、Issue への返事、審査の結果のように、外部の変化を待つときは、タスクに確認の間隔と期限を登録します。

```
lacia task recheck <ID> --every 1d --until 2026-12-31 --next "2026-12-01 09:00"
```

- 登録すると、タスクは外部待ちになります。決めた間隔で、サーバーが別の会話に、読み取りの確認を頼みます。次の確認の日時は、サーバーが先に入れます。確認する会話が入れ直す必要はありません。
- 間隔（`--every`）は、ふだん `1d`（毎日）にします。確認は1回ごとに会話を1つ使います。`3h` のような短い間隔は、急ぐ理由があるときだけにします。1時間より短くはできません。
- 期限（`--until`）は、必ず決めます。期限が来ると、サーバーが確認を止めて「要対応」へ出します。待ち続けるかどうかを、{{呼び名}}に決めていただくためです。締め切りや、返事が来るはずの時期から決めます。
- 最初の確認（`--next`）を省くと、いまから間隔1回分のあとになります。
- 登録するときに、「次にすること」へ、何を確かめるのか（対象の URL など）と、何が起きたら{{呼び名}}にお知らせするのかを書きます。確認する会話は、経緯を知りません。許可の範囲は `notes.md` に書きます。
- 確認は、読み取りだけです。読むだけで確かめられる対象なら、自分の判断で登録して構いません。外部への送信や書き込みが要る確認は、登録しません。
- `after`、`after_run`、`review_at`、`on_ready` とは、一緒に使えません。

確認を頼まれた会話は、本文と補足を読み、対象を読み取りだけで確かめて、結果を1つ残します。

| 分かったこと | コマンド | そのあと |
| --- | --- | --- |
| お知らせする変化がなかった | `lacia task rechecked <ID> same "見たものと結果"` | 外部待ちのまま、次の回を待ちます |
| {{呼び名}}の判断や操作が要る変化があった | `lacia task rechecked <ID> changed "何が変わったか"` | 確認が止まり、「要対応」に出ます。実行する前に、「次にすること」へ、見ていただくものへのリンクと、決めていただきたいことを書きます |
| 対象を読めなかった | `lacia task rechecked <ID> unknown "確かめられなかった範囲と理由"` | 外部待ちのまま、次の回を待ちます。読めなかった回を、変化なしとは扱いません |

- 結果を残さずに終えた回と、`unknown` の回が、合わせて2回続くと、サーバーが「要対応」へ出します。
- 次の回を別の日時にしたほうがよいと分かったときだけ、`lacia task field <ID> resume_on "日時"` で変えます。相手が返事をする日を書いていたときなどです。期限より後にはできません。
- 確認をやめるときは、状態を変えます。外部待ちを離れると、確認は止まります。続けるときは、登録し直します。
- 1つのタスクのための確認に、定期タスクを作りません。定期タスクは、1つのタスクに属さない巡回に使います。

#### そろったら、レイシアが着手する

条件に加えて `lacia task field <ID> on_ready start` を指定すると、条件がそろったときに、「要対応」へ出す代わりに、サーバーが着手の依頼を出します。宛先を省くと、記録を持つサーバーの窓口に届きます。別の宛先へ届けるときは、`lacia task field <ID> on_ready "start local-codex"` のように、導入先にある場所と種類を続けて書きます。サーバーの会話が依頼を受け付けると、状態は「進行中」になります。別端末への申し送りになるときは、宛先の会話が受け取りを知らせると「進行中」になります。

- **この印を付けるのは、その日時や条件でレイシアが動くことを、{{呼び名}}が指示したときだけです。** 自分の判断では付けません。
- 着手を知らせる依頼には、個々の作業の経緯や手順は書かれません。印を付けるときに、`task.md` の「次にすること」へ着手後の作業を、`notes.md` へ許可の範囲と止める条件を書いておきます。
- 着手した会話は、最初に「次にすること」、補足、履歴の最後を読みます。指示が取り消されている、すでに済んでいる、別の会話が進めている、のどれかなら、重ねて進めずに、理由を履歴に書いて状態を戻します。
- 決めてあった日時から大きく遅れているときは、いまも役に立つのかを確かめてから進めます。
- 外すときは、値を付けずに `lacia task field <ID> on_ready` を実行します。条件だけが残り、そろうと「要対応」へ出ます。
- 1回だけ行う仕事を、予約（`schedules/`）に書きません。予約は、繰り返す仕事だけに使います。1つのタスクで日時が続くときは、着手した会話が、次の日時を決め直します。外部の変化を確かめるために日時が続くときは、上の、繰り返し確かめながら待つ形を使います。次の日時は、サーバーが入れます。

- 締め切りを表す `due` は、これとは別です。`due` の日が来ても、状態は変わりません。
- `ready_since` は、サーバーが書く項目です。手で書きません。
- Webのタスクのページからも、同じ指定ができます。

### 本文

本文に使う見出しは、次の6つだけです。この順に置き、段はすべて `## ` にします。ほかの見出しは足しません。

| 見出し | 書くこと | 要るとき |
| --- | --- | --- |
| ひとことで | 何のタスクで、全体のどこまで来ているのかを3文までで説明します | いつも |
| このタスクを作ったわけ | きっかけと、解決したい困りごとを1〜3文で書きます | 用件が明らかな小さなタスクでは省略できます |
| 次にすること | だれが何をするのかを書きます。選択肢があれば、おすすめを最初にして番号を付けます | 閉じていないタスク |
| 今回したこと | どの依頼を受けて何をしたのかを書きます。新しく置いたものや、置き換えたものも示します | 作業をしたあと |
| いまの状況 | 「済んでいること」「残っていること」「まだ確かめていないこと」に分けて書きます | あれば |
| いまの資料 | いま有効な資料だけを載せます。置き換えた版は外します | あれば |

小さなタスクは、「ひとことで」と「次にすること」の2つだけで足ります。次は、説明のために作った例です。

```markdown
## ひとことで

確定申告の書類をそろえて、申告書の下書きを作るタスクです。ふるさと納税の証明書が、3件のうち2件集まりました。

## このタスクを作ったわけ

申告の直前に足りない書類へ気づくことがありました。早めに書類をそろえて、余裕を持って申告できるようにします。

## 次にすること

○○市の証明書が郵便で届いているか、{{呼び名}}に確かめていただきます。届いていれば、わたしが申告書の下書きを作ります。

## 今回したこと

2026-11-12にいただいた、書類を集めておいてほしいというご依頼への対応です。

- 源泉徴収票と医療費の領収書を、共有のフォルダーから集めました。
- ふるさと納税の証明書は、3件のうち2件が見つかりました。

新しく置いたものは、[集まった書類の一覧](artifacts/documents.md)です。

## いまの状況

**済んでいること**

- 源泉徴収票と、医療費の領収書が集まっています。

**残っていること**

- ○○市のふるさと納税の証明書は、共有のフォルダーにありません。郵便で届いているかは、まだ分かりません。

## いまの資料

- 2026-11-12 [集まった書類の一覧](artifacts/documents.md)
```

節ごとの書き方です。

- **ひとことで**：目的と、全体の中での位置を書きます。個々の依頼の日付や、確かめた細かい結果は書きません。段階が変わったときだけ書き直します。完了したタスクでは、何をして、どうなったのかを書きます。
- **このタスクを作ったわけ**：「ひとことで」の直後、「次にすること」の前に置きます。何がきっかけで、どの困りごとを解決したいのかを書きます。細かな前提と許可は `notes.md` に、日ごとの経過は履歴に置きます。ほかの節や補足に同じ背景があれば、この節へ移して重複を減らします。
- **次にすること**：最初の1文で、だれが何をするのかを言い切ります。本人に向けて結果や次にすることを案内するときは、その方の呼び名を書きます。一覧と通知は、この節の最初の段落を読みます。状態を `review` にするときは、{{呼び名}}に何を見て、何を決めていただくのかを書き、見ていただきたいものへ直接リンクします。決めていただくことや、していただくことは最初の文に書き、「ご確認いただきます」だけで終えません。状態を `closing` にするときは、だれが何をするのかの代わりに、最初の段落に、終わったこと、見ていただけるもの、まだ確かめていないことを書きます。`review` で選択肢があれば、番号を付けて2つか3つ挙げ、レイシアがすすめるものを最初に置きます。{{呼び名}}が「それで進めて」か「2番目で」と返すだけで、次へ進めるようにするためです。完了したタスクでは、この見出しごと消します。
- **今回したこと**：1行目に、どのご依頼への対応なのかを、日付と一緒に書きます。したことを箇条書きにして、最後に、新しく置いたものと、置き換えたものを、リンクで並べます。次の依頼に取りかかったら、全体を書き直します。前の回の本文は、状態が「進行中」から変わったときに、サーバーが履歴に残しています。
- **いまの状況**：いまどうなっているのかを書きます。「〜を受けて、〜しました」という経緯の書き方をしません。追記せずに、変わったところを書き直します。中は、「済んでいること」「残っていること」「まだ確かめていないこと」の3つの言葉で分けます。当てはまらない言葉は省きます。詳しい内容を成果物や補足に置いたときは、その場でリンクします。
- **いまの資料**：いま有効な資料だけを並べます。版のあるもの（PDF、コミット、報告）は、行の先頭に日付を書いて、新しい順に並べます。いつも最新が見られる場所（リポジトリー、プルリクエスト）は、そのあとにまとめます。名前に、「今回」「前回」「けさ」「最新」「旧版」のような、時がたつと意味が変わる言葉を使いません。置き換えた版は、一覧から外します。ファイルは消しません。
- 全体で100行ほどまでにします。超えるときは、詳しい内容を `notes.md` か成果物へ移します。
- コミットの番号、依頼のID、検証の細かい数値は、ここには書きません。履歴に書きます。
- 「このタスクを作ったわけ」は、新しいタスクから使います。既存のタスクでは、背景がないと判断しにくい確認待ちを優先して整えます。ほかの未完了タスクは、次に本文を書き直すときに整えます。背景のない既存の本文も引き続き保存できます。（2026-11-25の決定）
- 以前の形（「いまの状況」から始まる形）のタスクは、次に本文を書き直すときに、この形にします。

## notes.md

作業の前に確かめる約束ごとを書きます。完了の条件、してよいことと許可が要ること、決まったこと、知っていると判断が変わることです。

1行目は `# <ID> の補足` にします。見出しは、次の5つです。上の3つは、この順で先頭に置きます。

| 見出し | 書くこと |
| --- | --- |
| ここまでできたら完了 | 何ができたら、だれが完了にするのかを書きます |
| してよいことと、お尋ねすること | 「してよいこと」と「お尋ねすること」に分けて書きます |
| 決まったこと | {{呼び名}}が決めたことに、出どころを添えます。変わったら、古いほうを消します |
| 知っておくとよいこと | 判断に関わる背景や、対象のアカウント、期限の事情を書きます |
| つながりのあるタスク | 親、子、前後のタスクを示します |

最初の2つの節は、たとえば次のように書きます。

```markdown
# T1005 の補足

## ここまでできたら完了

申告書を提出して、受付の通知を確かめたら完了です。完了にするのは、{{呼び名}}です。

## してよいことと、お尋ねすること

**してよいこと**

- 書類の整理と、申告書の下書きの作成は、わたしが進めます。

**お尋ねすること**

- e-Tax への送信は、{{呼び名}}が行います。わたしは送信しません。
```

- そのあとに、タスクに固有の節を足して構いません。
- その回の報告、日付の入った見出し、「今回」の入った見出しは、ここに書きません。報告は「今回したこと」と履歴に書きます。育っていく設計や仕様は、成果物（`artifacts/design.md` など）にして、「いまの資料」からリンクします。
- 条件が変わったら、古い記述を消して書き直します。経緯は残しません。
- 全体で60行ほどまでにします。書くことがなければ、ファイルを作りません。

## 履歴（log.jsonl）

起きたことを、起きた順に残します。1行が1件の JSON で、書き換えたり、消したり、並べ替えたりしません。

- 書くときは、`lacia task note <ID> "文章"` を使います。日時と、だれが書いたのかは、コマンドが付けます。`log.jsonl` を直接編集しないでください。
- 読むときは、`lacia task log <ID> --tail 20` を使います。`--json` を付けると、行をそのまま出します。
- 状態を変えたこと、依頼を受け付けたこと、ファイルを置いたことは、サーバーが自動で書きます。同じことを重ねて書きません。状態が「進行中」からほかへ変わったときは、そのときの `task.md` の本文も、サーバーが残します。
- 最初の1文で、何をして、どうなったのかを言い切ります。根拠にした指示、コミットの番号、確かめた値は、そのあとに書きます。改行や箇条書きを使って構いません。
- 1件には、1つのことを書きます。長い調査の結果は、成果物にして、ここには要点とリンクを書きます。

## artifacts/

{{呼び名}}に見ていただくものを置きます。Webのタスクのページに、ここにあるファイルが自動で並びます。

- ファイル名は、中身が分かる英数字とハイフンにします。
- 書き直していく文書（設計、計画）は、日付のない名前（`design.md`、`plan.md`）にして、同じファイルを書き直します。古い版が要るときは、Gitの履歴にあります。
- その時点の記録（結果、比較、PDF）は、`<何であるか>-<YYYY-MM-DD>.<拡張子>` の名前にします（例: `comparison-2026-11-12.md`）。同じ日に置き直すときは、`-2`、`-3` を付けます。
- いまあるファイルの名前は、変えません。リンクが切れるためです。
- Markdown の成果物は、最初の見出しを題名にして、最初の段落で、何の文書で、いつの時点のものかを書きます。
- 評価、調査、比較の報告は、評価、調査、比較の報告の書き方（`lacia rules reports`）に従います。
- 作業の記録や、機械が出したログは、ここに置きません。

## files/

大きな成果物を置きます。ここにあるものは、Gitに入りません。Webのタスクのページに「大きな成果物」として並びます。

- **200 KiB を超えるもの、機械が生成したもの、画像やデータを埋め込んだHTMLは、`artifacts/` ではなく、ここに置きます。** 文章が中心の小さな報告は、これまでどおり `artifacts/` です。
- **作り直せるものだけを置きます。** 控えは取っていません。元になるデータやスクリプトは、コードのリポジトリーか `artifacts/` に置いて、どうすれば作り直せるのかを `notes.md` か報告に1行書いておきます。
- 置くときは、`lacia task attach <ID> <ファイルかディレクトリー>` を使います。ファイル名、大きさ、ハッシュが、履歴に自動で残ります。ディレクトリーを渡すと、その名前のまま中身ごと置かれるので、HTMLと、それが読み込む画像やスクリプトを一緒に置けます。小さな成果物を `artifacts/` へ置くときは、`--to artifacts` を付けます。
- Git に入らないので、比べたい版は、日付を付けた別の名前で置きます。
- `task.md` からは、`[結果のグラフ](files/chart/index.html)` のようにリンクします。
- HTMLの中のスクリプトは動きます。ただし、外部への通信はできません。地図やフォント、ライブラリーを外部から読み込むHTMLは、表示が崩れます。必要なものは、ファイルに埋め込むか、同じディレクトリーに置いてください。
- 上限は、1つのファイルが 50 MiB、1つのタスクで合わせて 500 MiB です。それより大きなデータは、元の環境に置いたまま、場所を報告に書きます。
- タスクを閉じてから90日で、サーバーが消します。残す必要があるものは、{{呼び名}}がタスクのページで指定します。

## 状態を変えるとき

| するとき | 状態 | あわせて書くこと |
| --- | --- | --- |
| 着手した | `doing` | 「ひとことで」と「次にすること」 |
| 確認待ち、完了確認待ち、外部待ちで追加の指示を受け、実作業を再開した | すぐ `doing` | 作業の長さにかかわらず戻します。状態を保つ個別の指示があるときは、その指示に従います。詳しくは、`lacia rules core` の「状態」をご覧ください。 |
| 日時やほかのタスクを待つ、外部の処理や返事を待つ | `waiting` | 先に、戻る条件を登録します。条件がないと、サーバーは受け付けません。「次にすること」に、何を待ち、条件がそろったらだれが何をするのかを書きます |
| 作業が済んで、判断、回答、操作をお願いする | `review` | 「次にすること」に、見ていただくものへのリンクと、決めていただきたいことを書きます。選択肢があれば、おすすめを最初に置きます。「今回したこと」も書きます |
| 作業が済んで、お願いが、これで完了にしてよいかの確認だけになった | `closing` | 「次にすること」の最初の段落に、終わったこと、見ていただけるもの、まだ確かめていないことを書きます。「今回したこと」も書きます |
| 取りやめる | `cancelled` | 「ひとことで」に、取りやめた理由を書きます |

完了を判断するのは{{呼び名}}です。`review` と `closing` の選び方は、`lacia rules core` の「状態」にあります。完了確認待ち（`closing`）のタスクは、「確認しました」という返事で `done` にします。確認待ち（`review`）でも、完了の確認だけをお願いしていたときは、同じです。「終わったら完了にしてよい」と個別に言われたら、その許可を `notes.md` に残します。完了の方針が `memory/profile.md` にあるときは、それに従います。完了や取りやめにしたら、「次にすること」を消して、「ひとことで」に結果を書きます。「今回したこと」には、最後の回の内容を残します。

## 定期タスクのタスク

定期タスクのディレクトリー（`areas/<領域>/routines/<ID>/`）にも、`task.md` と `notes.md` を置けます。定期タスクについて、いまだれが何をすべきかを書く場所です。実行のたびの分析結果は受付に残ります。サーバーは、実行結果から対応を集めるとき、本文の「実行から分かった対応」だけを更新します。受付を読んだかどうかは管理しません。

- 書き方は、通常のタスクと同じです。見出し、点検、コマンド（`lacia task show`、`write`、`set`、`claim`、`note`、`attach`、`log`、`lint`）に、定期タスクのIDをそのまま使います。
- 最初に `lacia task write S1001 task.md <ファイル>` で本文を保存すると、サーバーが冒頭の項目を補って作ります。題名は `routine.md` の `title` を使います。
- 状態は、進行中（`doing`）、待機（`waiting`）、確認待ち（`review`）の3つだけです。ふだんは待機で、次の実行を待っています。{{呼び名}}にお願いすることができたら、「次にすること」に書いて確認待ちにします。定期タスクのページと要対応に出ます。対応していただいたら、待機に戻します。完了や取りやめにはしません。止めるときは `routine.md` の `enabled` を使います。
- 「ひとことで」には、何のための定期タスクで、いまどうなっているかを書きます。「次にすること」には、いまだれが何をするかを書きます。お願いすることがなければ、「次の実行で確かめます。{{呼び名}}にお願いすることはありません。」のように書きます。
- 本文は、すべきことが変わったときだけ書き直します。どの受付を受けて直したのかは、`lacia task note <ID>` で履歴に残し、本文からは受付（`/routines/S1001/receipts/3` など）へリンクします。
- 定期実行で見つかり、実行のあとも残る用件は、その定期タスクのタスクで追います。実行の会話は、用件を実行結果の `matters` に書き、通常のタスクを新しく作りません。サーバーが、`matters` の用件を本文の「実行から分かった対応」へ集めます。
- 通常のタスクへつなぐのは、同じ用件をすでに追っている通常のタスクがあるときと、定義（`routine.md`）の「すること」が通常のタスクを作ると名前を挙げて書いているときだけです。そのときは、実行結果の `handoffs` に書きます。
- 定義の冒頭に `matters_task: S1001` のように別の定期タスクのIDがあるときは、用件はその定期タスクのタスクに集まります。朝と夕方のように、同じ仕事を分けている定期タスクで使います。同じ用件には、どの回も同じ `key` を使います。
- 定期タスクのタスクは、通常のタスクの親（`parent`）や待つ相手（`after`）にはなりません。
