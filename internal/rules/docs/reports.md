# 評価、調査、比較の報告の書き方

プロンプトや製品の比較、原因の調査、設計案の検討、レビューの結果、作業の結果などを報告するときと、設計や計画の資料を書くときに読みます。文の書き方は `lacia rules writing`、成果物の置き場所は `lacia rules tasks` で読めます。

## 読み終えた方の、次の一歩から書く

資料は、読み終えた方が次の一歩を踏み出すためのものです。案を選ぶ、作業を始める、直す、閉じてよいと判断する、のどれも次の一歩です。資料の種類にかかわらず、次のように書きます。

- 書く前に、だれが読み、読み終えたら何をなさるのかを決めます。依頼の文を1文ずつ読み、どれにも答えているかを確かめます。
- 材料がそろってから書きます。調べた結果が筋の前提を崩すときは、結果を足して済ませずに、筋を直します。
- 一般論で止めずに、今回の対象について、名前、日付、数で具体的に書きます。確かめたことと、材料から導いたことは、言い方で分けます。導いた値は、出し方を1か所に書き、資料の中で同じ値を使います。まだ確かめていないことには、仮の答えと、だれがいつ確かめるのかを添えます。確かめていない仮定の上に、数字を重ねません。
- すすめるものを決める前に、もっと簡単な答えで足りないかを確かめます。
- 書くかどうかは、「これがなかったら、次の一歩が変わるか」で決めます。結論を変えない留保や細かな指摘は、並べません。

## 3つの層で書く

資料は、「ひとことで」、前の部分、後ろの部分の3つの層にします。どの層で読むのをやめても、そこまでで次の一歩を踏み出せるようにします。見出しは用件に合わせます。ここで示す「ひとことで」の長さは、報告のための目安です。タスク本文の「ひとことで」は、`lacia rules tasks` のとおり3文までです。

1. **ひとことで**　300字ほどまでで、答え、次の一歩、いちばん大事な留保を書きます。次の一歩には、決めていただくことと、返事のしかたを書きます。していただくことがなければ、そう書きます。
2. **前の部分**　次の一歩に要ることだけを書きます。きっかけと困りごと（1〜3文）、結論を支える事実や案とその弱いところ、お願いする判断、次の作業です。「ひとことで」と合わせて4,000字を超えないようにし、超えるときは、文を縮めずに、後ろへ移します。短く済むなら、短いほうがよいです。終わりに、ここから後ろは読まなくても判断できると分かる見出しを置きます。
3. **後ろの部分**　前の部分に書いたことを、確かめたい方のための根拠です。短い資料では、なくても構いません。前の部分と同じ説明を繰り返しません。記録やファイルにあることは、写さずに場所を示します。点検の経過は、資料ではなく `lacia task note` の履歴に書きます。

お願いすることは、1か所に集めます。判断は、答えがないと進められないものに絞り、答えによって次の作業が変わる問いにします。選択肢には、おすすめを先に置き、選んだあとにだれが何をして、どこまで進むのかを書きます。番号かひとことで返事ができる形にします。すでに許可を得ていて、おすすめのまま進められることは、「お返事がなければ、こう進めます」とまとめます。あとで決めることがあれば、いつ、何がそろえば決めるのかを添えます。作業が続くなら、最初の作業を、だれが、何を使って、何ができたら終わりなのかまで書きます。時間の見込みは、根拠があるときに添えます。

冒頭では、作業中の略称や、担当どうしでしか通じない言葉を避けます。必要な用語は、初めて出す文で短く説明します。確認待ちのタスクでは、お願いする判断を `task.md` の「次にすること」にも短く書き、報告の該当箇所へリンクします。

## 候補を比べるとき

同じ問いに答える複数の選択肢があり、共通の観点を横に並べると違いが分かりやすいときは、表を使えます。表の前で何を選ぶのかを示し、行に選択肢を、列に判断に使う観点を置きます。列には、たとえば利点、弱点、費用を使います。候補ごとに効く条件が異なり、説明が長くなるときは、短い段落か箇条書きのほうが読みやすくなります。

設計を1案すすめる報告では、その仕組みと利点を文章で示します。別の案に切り替える条件があるときは、「どんなときに設計を変えるか」のような節に置き、条件と切り替え先を続けて書きます。見送った案の理由や、評価の観点そのものは、判断の背景や根拠として説明します。

## 判断の根拠と条件

- すすめる案と、その理由を言葉にします。「採用できる」「条件がそろえば試せる」「いまの結果では判断を保留する」など、どこまで進められるかが分かるように書きます。
- 結論を支える観察と、まだ確かめていないことを示します。確からしさは根拠に合わせます。仮説には仮説と書き、何が分かれば見立てが変わるのかを添えます。
- 次の実験や別の仕事にも生かせる知見があれば、その根拠とともに書きます。予想と違った結果や、評価方法について分かったことも、次の判断に役立つところを残します。

## 確認待ちにする前に

次のことを確かめてから `review` にします。お願いする判断がなく、結果を見ていただくだけの報告は、同じことを確かめてから `closing` にします。

1. 「ひとことで」だけを読んで、答え、次の一歩、いちばん大事な留保が分かりますか。
2. 前の部分だけを読んで、次の一歩を踏み出せますか。なくても次の一歩が変わらないものが、前の部分に残っていませんか。
3. 依頼の文の1つずつに答えていますか。一般論や、決め方を先送りしたまま終わる文が残っていませんか。
4. 選択肢ごとに、選んだあとどうなるのかが分かりますか。おすすめと、それを変える条件は明確ですか。
5. 表がある場合、どの問いへの選択肢を、どの観点で比べているかが分かりますか。
6. 重要な留保を確かめた事実から区別して読めますか。説明のない略称が残っていませんか。

{{呼び名}}に判断をお願いする資料は、経緯を知らない読み手役に読んでもらいます。手順は、サブエージェントへの任せ方（`lacia rules delegation`）の「確認待ちにする前に、読み手役に読ませる」にあります。

## 資料に指摘をいただいたら

資料の作りや中身に指摘をいただいたら、その資料を直すだけで終えません。資料ができた経緯を、会話とタスクの記録でたどって原因を確かめ、次からは出す前に自分で気づけるように、決まりへ戻します。
